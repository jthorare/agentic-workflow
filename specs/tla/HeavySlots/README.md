# HeavySlots

- **Models:** the box-wide heavy-job slots: `<locks>/heavy-job.lock` (slot 1) and `heavy-job.lock.k` (slot k), mkdir mutexes shared by three takers.
  - The `heavy` wrapper, which is **not in the repo**: `~/.agentic-workflow/bin-r1b/heavy` at sha256 `9675fdb3bc70eb411597c6b2088ecac5bb59fa6cc877eb11680d443f6d60010b` (165 lines, 2026-11-04). `acquire box-wide` reads the cap file once per job and the meta reserve on every pass. It does mkdir, then the owner write. To reclaim a slot it reads `owner`, then unlinks it, rmdirs and mkdirs again, with no mutex.
  - `config/lib/locks.sh` `acquire_any_lock`: uses `AW_HEAVY_SLOTS` (default 2) and never reads the cap file or the reserve. Its record is `<dir>/pid`. To reclaim, it moves the record aside first (`_lock_reclaim_dead`).
  - `DirectoryHeavySlots.cs`: reads the cap once at serve start (the `HeavyLockSettings` singleton) and never reads the reserve. Its record is `<dir>/owner`, and it reclaims by renaming the record aside (`Claim`) and then a non-recursive delete. `HeavySlotLease` leaves alone a slot whose owner names another process.

  Each syscall is one step, except a rename-aside reclaim (move, read, delete), which is one step: so a SIGKILL inside it isn't modelled (#2065). Also simpler than the code: a release checks the job (`who`), where Sindri's `IsOurs` / `HeavySlotLease` compare only the pid, which every job in one serve shares (matters with 2+ Sindri jobs). Each other syscall is one step. A process can be SIGKILLed at any step: its folder and record stay, and its pid is never reused. Not modelled: the per-session `heavy-session/<pid>.lock` pool, the memory guard (it only skips slots), timeouts, the 6 h no-record grace and the TS `holder.json`.
- **Checks:** `OneHolderPerSlot` (no two live processes hold one slot folder) and `SomeoneRuns` (the box never locks up among the live jobs). `TakeWithinCap` (nobody takes a slot above the cap file as it reads at that moment) and `ReserveHonored` (a non-meta job never takes a slot meta reserved) are in `HeavySlots.cfg` too, but there they can't fail: its cap never changes and no job is meta. They only bite in `gaps/StaleCap.cfg` and `gaps/IgnoredReserve.cfg`. Also, checked only as witnesses on the gap cfgs: `NoStarvation` (every waiter gets a slot) and `OrphanReclaimed` (a slot whose holder died is freed).
- **Bounds:** `HeavySlots.cfg`: one wrapper job, one locks.sh holder, one Sindri job, 2 slots, every cap 2, no reserve, no SIGKILL, weak fairness; about 1k states. `HeavySlotsReclaim.cfg`: two locks.sh holders and one Sindri job on 1 slot, 1 SIGKILL anywhere. Their rename-aside reclaims never let two processes hold one slot (about 1k states).
