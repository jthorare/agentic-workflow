Every file path below is one the author opened on main (af8c954). Every command, route, event, key and type is marked **existing** or **new**.

**Not in scope: notes.** The owner keeps notes in Obsidian (owner, 2026-11-07). A todo is one line, with an optional due date and optional links. It has no body, no checklist and no formatting. The one Obsidian note this spec touches is a list of those lines (§4.5).

## The owner's steps: install -> works

1. **See what's next.** Open Sindri. The top of Home is your todo panel: the next five open todos, overdue first, then today, then upcoming (todos with no date after those). Focus starts in Needs you, as today; `G T` from any page lands you in the panel.
2. **Add one from anywhere.** Press `N` (on Workflows, where `N` starts a workflow, press `Ctrl+Shift+N`). A one-line box opens at the top of the window. Type "reply to Sam about the offsite fri" and press Enter. The todo is saved with Friday as its due date, and the box closes. Esc closes it without saving.
3. **Check one off.** Tab into the panel, `J`/`K` moves between rows and `X` checks the row off. A "Done. Undo (Ctrl+Z)" toast stays for 10 seconds.
4. **Keep it in Obsidian too (once, on the work laptop only).** Add your Obsidian vault in Settings → Library if it isn't there. Then Settings → Connections → **Obsidian todo note**: pick the vault, name the note (`Todo.md`), **Check note**. The card says what's in it. **Import and start syncing** (or **Start syncing** when the note has no open tasks) saves the setting, which applies at once (Sindri v2 drops profile approval, #2258), and adopts the note's open tasks. Cancel changes nothing. From then on Sindri keeps the note in step while it's running: it writes your todos into it as `- [ ]` lines and reads back what you change there. Phone changes show up about a minute after Obsidian Sync brings them to this laptop.
5. **If you changed the same todo in both places**, Sindri doesn't guess. The panel shows "Changed in Sindri and in Obsidian" with both versions side by side, and you pick one (with Undo). If you delete, edit or un-tick more than 3 todos in the note in one go, Sindri holds those and asks first: apply them in Sindri, or put them back in the note. Ticking never asks.
6. **From the terminal or an agent.** `sindri todo add "rotate the staging key" --due 2026-11-10`, `sindri todos`, `sindri todo done td_…`. Agent sessions have the same access through the `sindri_todos` and `sindri_todo` MCP tools (D2).

## 0. Why

The owner runs their day from Sindri: PR reviews, workflows, agents, docs, Linear (owner goals, 2026-11-04: "personal mega app on the work laptop"). Sindri already tracks what's waiting on the owner (Needs you, PRs waiting on review, Linear issues assigned to them). It has no place for the owner's own todos, things like "reply to Sam" or "renew the cert", that have no repo and no run. Today those live in Obsidian, so the owner's plate is split across two apps.

The owner's ranking (§12 Q7): **seeing what's next must feel instant**, more than capture speed. That's why the list sits at the top of Home, the page Sindri opens on, and not behind a tab.

**Why not Sindri's items?** An item (`sindri item add <title> [--repo]`, existing, `docs/csharp/sindri.md:42`) is a unit of agent work. It belongs to a repo of the profile (`SND-CLI-003` otherwise), it moves through the queue's groups (`waitingOnYou`, `running`, `queued`, ...), and recipes run on it. A personal todo has none of that. Making todos items would put "call the dentist" in the Work queue and need a fake repo.

**Why not make the Obsidian note the store** and have Sindri only read and edit that file? It would drop the merge, the base file and conflicts. It fails on four things the owner asked for: (1) the panel's first render is one `views.db` read (D12); parsing a vault file on every Home open is slower and fails while Obsidian Sync is mid-download. (2) Undo and stale-write refusal need a version per todo; a file has none. (3) Agents write through MCP (D2); concurrent agents editing one markdown file is the lost-edit problem without a ledger to recover from. (4) The note is optional (step 4): todos must work with no vault at all. So the store is Sindri's, and the note is a two-way mirror of it.

## 2. Goals and non-goals

**Problem.** The owner's plate is split: Sindri shows what agents, PRs and Linear need from them, but their own todos live in Obsidian, so no one screen answers "what do I do next?"

**Who and when.** The owner, at the start of the day and between reviews, with Sindri already open on the work laptop; on their phone, in Obsidian, away from the laptop. Agent sessions, when a run turns up something the owner has to do later.

**Ideal.** Opening Sindri shows the next thing at the top with no wait. Adding a todo takes under two seconds from any page without losing your place. A todo ticked on the phone in Obsidian is ticked in Sindri the next time the laptop syncs. Nothing pulled in from elsewhere can be closed by a stray keypress, and nothing typed in either place is silently thrown away.

**Requirements** (EARS):

- REQ-U1 The app shall show, at the top of Home, the owner's next five open todos (Overdue, then Today, then Upcoming, then No date; each by due date, then by when it was added) and a count of the rest.
- REQ-U2 The panel shall show a read-only From elsewhere line with the count of PRs waiting on the owner's review, of Linear issues assigned to the owner, and of the Needs you rows below it.
- REQ-U3 Sindri shall store todos so they survive a restart and a `views rebuild`, and the CLI, the MCP tools and the app shall show the same list.
- REQ-U4 Where an Obsidian todo note is set, Sindri shall keep every todo as one line of that note, and the note shall show the same todos as the app within 10 seconds of a change on either side while Sindri is running and the note has been still for 2 seconds, except for the lines a pick names during its 10-second Undo window (D11) and the lines an open hold names (REQ-E7).
- REQ-E1 When the owner presses `N` on any page but Workflows, or `Ctrl+Shift+N` on any page, with no modal form open, the app shall open the quick-add box with focus in it. When they press Enter on non-empty text, it shall save the todo and close the box, keeping focus where it was before.
- REQ-E2 When the owner checks a todo off, deletes it, or picks a side in a conflict or a hold, the app shall show Undo for 10 seconds, and Undo shall bring back the todo (or the open conflict or hold) as it was. A check-off or delete toast pauses while the pointer or focus is on it; a pick's toast runs on Sindri's 10-second clock (D11), shows its countdown, and isn't replaced by a newer toast until it ends.
- REQ-E3 When local midnight passes while the app is open, the groups and the overdue count shall move without a restart, and focus shall stay on the same todo.
- REQ-E4 When the note gains a top-level `- [ ]` line with no `^td-` id after the first sync, Sindri shall add it as a todo and write the id onto that line.
- REQ-E5 When a sync finds one todo changed in both places since the last sync, Sindri shall show both versions in the panel and change neither until the owner picks one.
- REQ-E6 When a todo note is first set and it already holds task lines, Sindri shall write nothing to it and add no todo until the owner confirms the import, and shall then import only the open (`- [ ]`) top-level lines.
- REQ-E7 When one sync pass would remove or edit open todos, or reopen done ones (a `- [x]` line back to `- [ ]`), more than 3 in all, or more than half of the base's open todos when the base has 6 or more, Sindri shall apply none of those changes and ask the owner in the panel ("The note changed 14 todos. Apply that in Sindri too, or put them back in the note?"). Ticks (open to done) never count and always apply; removing or editing a line that stays `- [x]` doesn't count, so clearing out ticked lines never asks.
- REQ-S1 While Sindri isn't running, the panel shall show the existing Not running card, and `N` shall say "Sindri isn't running" instead of opening a box it can't save.
- REQ-S2 While a link points at something that no longer exists, its chip shall say so in words ("PR #12 not found") and the todo shall stay.
- REQ-S3 While the note can't be read or written (file missing, vault gone, permission), todos shall keep working in Sindri, no todo shall be removed because of it, the panel shall say "Obsidian note: <reason>", and `sindri doctor`'s `todo` row shall warn.
- REQ-O1 Where a todo has links, the row shall show one chip per link, each opening the linked page.
- REQ-O2 Where a todo has a due date, the row shall show it as a relative word for the next 6 days ("Fri") and as a date after that.
- REQ-O3 Where an agent session or a piped CLI call (`via: pipe`) added a todo, the row shall say so ("agent"), whoever edited it since; where one last edited a todo the owner added, it shall say "edited by an agent".
- REQ-W1 If a save fails (stale version, Sindri unreachable), the app shall keep the typed text in the box and say why.
- REQ-W2 If the text holds a secret-shaped string, from any writer including the note, Sindri shall scrub it before it's stored, and the merge shall compare scrubbed text on both sides.
- REQ-W3 If any caller that isn't the owner (`CallerContext.Class` not `Human`: an MCP session, a Sindri-launched session, a session with no launch header, the note service) tries to pick a side in a conflict or a hold, undo a pick, or import the note, Sindri shall refuse it with `SND-AUTH-002` and change nothing.

**Non-goals.** Notes. Syncing more than one Obsidian note, or one note from two machines (§12 Q9). Reminders that pop up. Recurring todos. Sharing todos with anyone. Moving items, issues or decisions into the todo store. Drag-to-reorder in the app. A Todo tab.

**Later** (each waits for a week of real use after Ph5). Recurring todos. Manual order in the app. Indented sub-tasks in the note. Links pasted into the quick-add box (refs parsed out of the text). A due-date picker key. "Done today" in the panel. Showing the last list from a local copy before Sindri answers (only if TP-7's cold-start number is over 2 s, §11). Usage counts by writer as a command (TP-14 reads them from the ledger by hand). "Show which" on the hold row (v1 names three changes and `sindri todo note` prints them all). CLI verbs for a pick's Undo and the hold picks (the app has them). `sindri todo add --from-file`. A failure counter in `sindri todo note --json` (v1 has `lastError`). Pruning removed and long-done rows from `view_todo` (v1 keeps them; routes filter by state). Detecting a second machine syncing the note.

**Success measure.** After a week of real use (TP-14), two things. **The numbers**, read by hand from `sindri ledger --type 'todo.*'` (no new code): todos added per writer (`human:ui`, `human:cli`, `obsidian`, sessions), `todo.conflicted` count, `todo.note.held` count, and Undos (a reverse event within 10 s of the one it reverses). If conflicts plus holds are more than 1 per 10 todo changes, the two-way sync is costing more than it gives, and the owner picks between keeping it two-way and making the note Sindri → Obsidian only. **The answer** to one line: "When you want to know what's next, do you open Sindri or Obsidian?" Sindri is the target. If it's Obsidian, the Later list stays shut and the note sync gets no more work beyond fixes.

### 3.1 The panel

Full width of Home's column, above the Needs you list. Header: "Todo", the count line ("11 open · 1 overdue", plus "· 1 to sort out" while a conflict is open), the hint "N New todo", and, when a note is set, a quiet sync line ("Synced with Obsidian 10:05", or "Obsidian note: can't read, Todo.md is missing" in the warning text colour). Then up to five rows, overdue first, and "Show all 11", which expands the panel in place (capped at half the page height, its own scroll, D13) to the grouped list: Overdue, Today, Upcoming, No date, and a "Show done" toggle at its foot (a `J`/`K` stop; Enter or Space toggles it) that adds a Done group: todos done in the last 7 days (`X` reopens one) and, under a "Removed" label, todos removed in the last 24 hours (`X` restores one), so a removal whose toast was replaced has a way back in the app. With neither, the group says "Nothing done in the last 7 days" and the toggle stays. Esc or "Show less" folds the panel back, and folding hides the Done group again. Home's decisions filter (`G D`) hides the panel.

A row is a checkbox, the text, the link chips (up to three drawn, then "+7"), an "agent" tag when an agent added it ("edited by an agent" when one last changed the owner's todo, REQ-O3), and the due word on the right. Under the rows, the From elsewhere line: "2 PRs waiting on your review · 1 Linear issue assigned · 3 need you, below". Each part is a link: Reviews, Work → Linear, or focus to the Needs you list. It's a single focus stop; `X`, Delete and Space do nothing on it.

**A both-places conflict** replaces that todo's normal row, at the top of the panel above Overdue, with the attention tint: "Changed in Sindri and in Obsidian", then two columns, **Sindri** and **Obsidian**, each with that version's text, due word and done state, and a button under each that draws its key: **1 Keep Sindri's** and **2 Keep Obsidian's**. Both picks have the 10 s Undo window (D11): Put back rewrites the lines when the window closes, Apply's events are undone by Undo, and in both cases nothing is written to the note before then. `sindri todo note` prints every held change. There is one open hold at a time; while it's open the note's other todos keep syncing, the lines it names are left alone, and each pass re-counts it: lines put back by hand shrink it ("The note changed 9 todos", announced again), and under the threshold it dissolves with nothing to pick, focus moving to the next row.

`by` is the caller's `CallerContext.Actor` plus its launch id when there is one (`human:ui`, `human:cli`, `session:mcp`, `session:cli:launch-…`), `service:todo-note` for a pass's own bookkeeping, or `obsidian` for an edit read from the note. Every write event also carries `via: "pipe"` when the request came with `fence=1` (the CLI with no terminal on stdout), else no `via`: the ledger can then tell the owner typing `sindri todo add` from the same command in an agent's Bash loop, both of which are `human:cli`. No todo text goes into `EventCatalog`'s templates; the catalog says "Todo added", never what it says. `addedBy` and `addedVia` on the row are the `by` and `via` of `todo.added`, `lastBy` and `lastVia` those of the last write; the "agent" tag reads them (REQ-O3). `text` passes through `Aw.Redaction` before the event is written, whoever wrote it.

Idempotency key for `todo.added`: `todo.added:client:<clientId>` (1 to 64 of `[A-Za-z0-9_-]`, else `SND-TODO-001`). The app sends one per Enter, the CLI one per invocation (`--client-id` overrides), MCP takes an optional `clientId`; a retried call after a lost answer makes one todo, and doesn't count again against the hourly limit. A todo adopted from the note gets its id **before** its event: the pass mints the id once (keyed by the line's text and index in that pass, and reused by every retry swap in the pass), writes it onto the line, and appends `todo.added` keyed `todo.added:<id>` only after the write's step 3 ends with nothing new having come out. A crash between the two leaves a line carrying an id Sindri doesn't know, which the next pass adopts under the same key (§4.5's "an id Sindri doesn't know" row), so a re-run never makes a second todo and retyped text is always a new one.

### 4.2 Projection

`TodosProjection : IProjection` (new, `Aw.Sindri.Core/Todos/`) folds the events into `view_todo` (the existing `key, row_json, seq` shape; the row holds `id`, `text`, `due`, `links`, `addedAt`, `addedBy`, `addedVia`, `doneAt`, `removed` (and `removedBy`), `lastLineHash` (a removed todo's last note line, which tells a stale copy from an owner re-add, §4.5), `version`, `lastBy`, `lastVia`, `conflict` or null), plus one `view_todo_note` row (the open hold, the import state, the last sync), in migration `0011_todos.sql` (the number is taken when Ph1a merges; a migration merged first moves it to the next free one) with `ViewSchema.Version` bumped and the row shapes pinned in `ViewRowShapeTests`. The panel reads all rows and sorts in memory (TP-7: 200 rows). It's a pure fold, rebuilt by `sindri views rebuild`, and invalidates `ApiViews.Todos` (new).

### 4.3 Links

A link is one of: an item (`ITM-…`), a PR (`<owner>/<repo>#<n>`, owner and repo each `[A-Za-z0-9._-]` and never `..`, or its https url on a configured forge host: the url is parsed, the host compared exactly, a user name refused, as `LinearText` does), a Linear issue key (`ENG-12`), or a workflow address (the existing address shape, `[a-z0-9-]` segments). It's stored as the deep link the app already opens (`sindri://item/…`, `sindri://reviews/<owner>/<repo>/<n>`, `sindri://linear/ENG-12`, `sindri://workflow/…`). The server checks only the shape (`SND-TODO-004`), never whether the thing exists, so a link to something not synced yet is allowed. The chip resolves it when drawn (REQ-S2). Duplicates are dropped; an 11th is `SND-TODO-004`.

An argument that doesn't match the schema (missing, wrong type) is the binder's `SND-CONTEXT-022`, as for every other tool; a rule the schema can't say (`change` with no field, no `version`) is `SND-TODO-001` naming it. An error result is `McpToolError`'s code and message only, so on `-409` and `-423` the tool says to call `sindri_todos` rather than carrying the row. `due: ""` clears the due date on the route and over MCP; `null` or absent leaves it.

**Fencing.** Every text field the routes return is fenced (source `sindri:todo`, author the row's `lastBy`) for a session caller, and for any caller that asks with `?fence=1`: `todos[].text`, an echoed `text`, a conflict's `sindri.text` and `obsidian.text`, a hold's per-todo text, and the note route's per-line error text. The CLI sends `?fence=1` whenever its stdout isn't a terminal, so an agent the owner started by hand that runs `sindri todos` in Bash gets fenced text while the owner's own terminal stays plain. `--fence` forces it; `--no-fence` turns it off for the owner's own pipes (`sindri todos --json --no-fence | jq …`) and needs the readable per-start human token, as `profile set` does (a session gets `SND-AUTH-002` from the CLI). A fenced field holds the wrapped string in place of the text, in `--json` as in plain output, as Projects' fenced routes do. The fence is a CLI heuristic, not a boundary: an agent harness that runs the CLI under a pseudo-terminal gets plain text. `GET /sindri/ledger` takes `fence=1` too, and `sindri ledger` sends it the same way; for `todo.*` events it fences by shape, every string in the payload but ids, hashes, enum values, dates, `by` and `via`, which covers `text`, both conflict sides, `baseLine` and a hold's `changes`. A test seeds a todo with a canary string and walks every todo route and the ledger as an MCP session, a Sindri-launched session and `human:cli` with `fence=1`, and fails on any response that holds the canary outside a fence. `FencePlan` gains rows for both tools. There is no `keep`, `import` or hold tool (D2). `McpSurfaceTests`' allow-list gains the six request-class todo commands and nothing else. `sindri_todo` waits for the views like `sindri_request` does (`SindriTools.WaitForViews`).

**The hourly limit** counts `todo.added` events in the ledger over the last hour per `by` and launch id, for session callers and for events with `via: pipe`; the owner's terminal and the app never count. It survives a restart because it reads the ledger. The add service does the idempotency lookup first (a retried add with the same `clientId` returns the same todo and doesn't count), then counts and appends inside one lock keyed by the actor, so 25 adds at once make exactly 20. The refusal says who it's for: a session "An agent can add 20 todos an hour. Try again after 10:42."; a piped CLI call "20 adds an hour without a terminal. Try again after 10:42, or add from a terminal or the app."

### 4.5 The Obsidian note (context lane)

**Setting it.** A new profile key, `todo.obsidian` (`{ vault, note }`): `vault` is the `name` of one of `context.sources.library.vaults`; `note` is a vault-relative path ending `.md`, no leading `/`, no `..`, not inside a dot folder and not matched by that vault's `deny` globs. The note must not be a symlink or have more than one hard link. A bad value is `SND-TODO-002` with the key path, raised by the profile reader, so `profile validate`, `profile set` and `todo note set` all refuse it (exit 2). The Settings card and `sindri todo note set <vault> <note>` write both fields in one validated write, and the edit is live on save (Sindri v2, #2258 D1: no profile approval; `--if-hash` guards a concurrent edit). The service reads the live profile. With no key set, nothing below runs. **One Sindri per machine, and only the work laptop syncs the note** (owner, §12 Q9): `docs/sindri/todo-note.md` says so; v1 detects nothing, and a second machine syncing the same vault would read the first one's writes as Obsidian edits.

**First sync and import** (REQ-E6). With no base yet, the service reads the note and writes nothing. A missing note: the card says it will be created, and the first write creates it with a `# Todo` heading. A note with no open task lines: syncing starts. A note with open task lines: the app's card counts them before any key is saved (**Check note**) and saves the key only with **Import and start syncing**; a key set from the terminal finds the service waiting ("Waiting for import") until `sindri todo note import --expect N`. Import re-reads the note and refuses with `SND-TODO-409` when its open count isn't the one the owner saw, adopts each open top-level `- [ ]` line (done lines and lines under a fenced block, quote or callout are left alone; a line that breaks D3 stays as text and the doctor row names it), writes the ids onto them, appends Sindri's todos after the last one, and records `todo.note.imported`. Adopted lines count against the 500 open cap; past it the rest stay as text and the doctor row says how many. Changing the note (**Change**) drops the base and starts this step again for the new note; the old note is left as it is.

**The note's format** ([Obsidian Tasks](https://publish.obsidian.md/tasks/) style, so the note also works with that plugin, though it doesn't need it):

```markdown
# Todo

- [ ] reply to Sam about the offsite 📅 2026-11-14 ^td-01jc5a8xq0n4w7ms2t9r3vbk6e
- [ ] rotate the staging key 📅 2026-11-10 [PR #12](sindri://reviews/jthorare/agentic-workflow/12) [ENG-12](sindri://linear/ENG-12) ^td-01jc5b2kz8m3r6tq1w9xh4dn7y
- [ ] call the dentist ^td-01jc5c90a2b7k4m8q1r6t3w9xz
- [x] renew the cert ✅ 2026-11-07 ^td-01jc5917f3h8n2p5s9v4x1z6bq
```

- One top-level `- [ ]` / `- [x]` line per todo. Due is `📅 YYYY-MM-DD`; done is `[x]` plus `✅ YYYY-MM-DD`; each link is a markdown link to its `sindri://` deep link; the id is the trailing Obsidian block id `^td-<the full ulid, lowercase>` (Obsidian keeps block ids through edits, and they're invisible in reading view). An id that isn't 26 lowercase ULID characters isn't an id: the line is a new line. One syntax only; Dataview-style fields are text.
- Task lines inside a fenced code block, a quote or callout, or indented under another line are not todos. Everything that isn't a top-level task line (headings, prose, blank lines, indented lines) is kept byte for byte. Sindri only touches task lines that carry a `^td-` id, plus lines it adopts.
- **A line that breaks D3.** A new line that would parse as a todo but breaks D3 (two ids, two due markers, a marker inside the text, a pasted markdown link, a forbidden character) is kept as text and the doctor row names its line number. A line with a **known** id that breaks D3 (the owner pasted a link into it) is **held**: Sindri keeps the todo as it is, removes nothing, and says "line 14 can't sync: it has a markdown link" on the panel's sync line and the doctor row. It syncs again once the line is valid.
- **Escaping.** Obsidian markup that runs or embeds is escaped with a backslash wherever it appears in text Sindri writes: `` ` ``, `<`, `![[`, `[[`, `%%`, `$=`. The parser unescapes exactly that set, so render then parse gives the same todo (a property test in Ph3a, whose generator includes every escaped sequence). A line adopted from the note keeps the owner's raw text until the todo's text changes in Sindri; only then is it written escaped.
- **Order is the owner's.** Sindri never reorders lines. A todo added in Sindri goes after the last todo line (or at the end of the note when it has none). Sindri never removes a line by itself (D8); a removed todo's line is removed only when the removal came from Sindri.

**Reading.** `TodoNoteWatch` (new, a lease-holding host like `ProfileWatch`) runs while the control plane holds the lease. It checks the note every 60 s and at start, and a non-recursive `FileSystemWatcher` on the note's folder triggers an earlier check (a trigger only: watchers miss events on some file systems). A built-in service `todo-note` with a 24 h cadence (`BuiltInService` has no manual cadence; the watch host does the real polling) lets `sindri services run todo-note` force a pass. When the note's sha256 differs from the last `todo.note.synced` hash, it waits until the file has been unchanged for 2 s (Obsidian saves as you type), parses it, scrubs each line's text, and runs the three-way merge below. **Obsidian Sync edits arrive the same way.** An edit made on the phone while the laptop was shut lands when Obsidian next syncs here, and the merge treats it like a local edit made at that moment. A note that is missing, unreadable or 0 bytes while the base isn't empty is "can't read" (REQ-S3), never "every line was deleted".

**The base** is the note's top-level task lines as Sindri last synced them (not the prose), stored scrubbed, at `$AW_SINDRI_HOME/todo/note-base-<hash>.md`, mode 0600, named by its own hash; the last `todo.note.synced` names it (`baseHash`). The pass reads the base that event names, so a crash between saving a base and appending the event leaves the previous base in force. A missing base, or one whose hash doesn't match, counts as no base: the pass adopts and appends, never removes, and a todo whose text differs on the two sides becomes a conflict, not a silent winner. Older base files are deleted after the event lands.

**The three-way merge**, per todo id, between the **base**, the **note** now, and **Sindri** now (the projection), comparing scrubbed text:

| Note vs base | Sindri vs base | Result |
|---|---|---|
| same | same | nothing |
| changed (text, due, links, ticked, removed) | same | the matching event, `by: obsidian` |
| same | changed | the note's line is rewritten from Sindri |
| changed | changed, to the same values | nothing (both already agree) |
| changed | changed, differently | `todo.conflicted` (D11): Sindri keeps its version, the note's line is left as is, neither side syncs that todo until `keep` |
| after a pick | — | the base line for that id is the pick's `baseLine` (the note line it was resolved against). `keep sindri`: note = base, Sindri changed → the line is rewritten from Sindri once the Undo time is over. `keep obsidian`: Sindri now equals the note → nothing |
| a known id on a line that breaks D3 | — | held (above): nothing changes on either side, the sync line and doctor say why |
| new line, no `^td-` | — | adopted: the id is minted and written onto the line in this pass's swap, then `todo.added` `by: obsidian` (§4.1's key) |
| the same `^td-` id on two or more lines | — | the first in file order keeps the id; each later one is a new line (adopted, new id written) |
| an id Sindri doesn't know | — | adopted as a new todo with that id (also how a crash between the swap and the event heals) |
| an id Sindri has as removed | — | removed in Sindri (`removedBy` isn't `obsidian`): compared with the row's `lastLineHash`, the same line is a stale copy (an old note restored, a sync lagging) and is dropped from the note again; a different line is an owner re-add (`todo.restored` `by: obsidian`, then the edit). Removed in the note: any line coming back is the owner's (an undo in Obsidian, a paste), `todo.restored` `by: obsidian` |

**The hold** (REQ-E7). Before any events are written, the pass counts the changes it would apply from the note that are open todos removed, open todos edited (text, due, links) and done todos reopened (`[x]` back to `[ ]`). More than 3, or more than half the base's open todos when the base has 6 or more, and it applies none of those, records `todo.note.held` with what each change is, and asks. Ticks (open to done), adds, and removing or editing a line that stays `[x]` don't count, and the pass still applies them, plus every change to todos the hold doesn't name. While the hold is open the writer leaves the lines it names as the note has them, and **every base saved keeps those ids' old base lines** (and `lastLineHash`): otherwise a write for some other todo would save the held Obsidian lines as the base, the next pass would read them as "Sindri changed only", overwrite them and dissolve the hold unasked (/autoplan round 3). Each pass re-counts: lines put back by hand drop out, a smaller set replaces the hold, under the threshold it dissolves, and dissolving or replacing it updates those ids' base lines. **Apply** and **Put them back** send the `noteHash` the row was drawn from; the service re-reads the note first and acts only on held changes still true in the file, and when the set is smaller or different it refuses with `SND-TODO-409` and the row refreshes ("4 of 6 are back; 2 left"), so Apply can't remove lines the owner just pasted back. Both picks have D11's Undo window: Apply's events are appended at once and Undo reverses them; Put back's rewrite of those lines happens when the window closes; in both, nothing is written to the note before then and Undo reopens the hold (`todo.note.held.reopened`).

Events the sync writes use the version-key append like every other writer; a `SND-TODO-409` on its own event re-runs the merge from a fresh read.

**Writing.** A write is due after any todo event not `by: obsidian`, after a merge, and when a pick's Undo window closes (D11). Every write leaves alone the lines named by a pick whose window is open and by an open hold. It waits until the note has been unchanged for 2 s (up to 30 s, then writes anyway), and events arriving in that wait share one write. Then:

1. Build the new note from the merged state in memory, editing only the lines that need it, and hash it. Write the intent file `$AW_SINDRI_HOME/todo/writing` holding that hash (replacing any older one), then write the build to `.<note name>.sindri-tmp` beside the note (a dot file, which Obsidian doesn't show or sync), created exclusive and without following links, with the note's file mode.
2. **Swap** it with the note in one system call (`renameat2(RENAME_EXCHANGE)` on Linux, `renamex_np(RENAME_SWAP)` on macOS). The tmp path now holds exactly what was at the note's path at that instant.
3. Wait until what came out has been unchanged for 2 s (an editor that opened the note before the swap may still be writing to it), then hash it. If it equals what the pass merged, delete it: nothing was lost. If it differs, Obsidian saved in between: merge that content as the note (a normal note edit against the same base; a shorter file is a delete like any other, and the hold catches a mass one) and write again from step 1, reusing the pass's minted ids. A came-out file of 0 bytes while the note the pass merged wasn't empty is never read as an edit: after 30 s still empty, it's kept as `.<note name>.sindri-tmp.keep-<time>`, the pass stops with "can't read" (REQ-S3) and writes nothing more. (Rev 4 also waited on any shorter file; the TLA+ model `NoteWrite4.tla` deadlocks on that, since a real delete never "settles".) Each retry compares against what the previous swap wrote, and after 3 swaps in one pass the pass stops with "note busy" and tries again at the next 60 s check.
4. Save the base and record `todo.note.synced` (`hash` = what was written), then delete the intent file.
5. At start, a leftover tmp file is read against the intent file: with no intent file, or its hash equal to the intent, the swap never ran (delete it unread); otherwise it's what came out, merged as in step 3 (the same 0-byte exit), then deleted.

This closes the window a rename over the note leaves open (/autoplan round 1, the TLA+ model `NoteWrite.tla` found an edit saved between the hash check and the rename lost; round 2's `NoteWrite3.tla` passes the swap for an editor that writes in place and needs step 3's 2 s settle for one that opens before the swap and writes after it). What remains: an edit still in Obsidian's editor buffer, not yet saved, when the file changes on disk; Obsidian reloads and that keystroke can be lost from the editor. The 2 s quiet wait makes that rare; Ph3b tries it by hand with Obsidian open and reports. **No fallback:** on a file system without the swap call, the note is read into Sindri but never written: ticks, edits and removals of lines that already carry an id arrive, a bare line is **not** adopted (its id can't be written, so each pass would adopt it again as a new todo; it stays text and the doctor row counts it), Import is off, and the doctor row, the sync line and the Settings card say so ("Obsidian → Sindri only: can't write to this disk"). A rename after a hash check is the rev 2 bug (round 2's model shows it losing an edit), so it isn't offered.

**Failures.** The vault folder gone, the note missing or unreadable, the swap refused: no event, no removal, the `todo` doctor row warns with the reason, the panel's sync line says it, and todos keep working in Sindri. The next change or the 60 s check tries again. `lastCheckAt` and `lastError` live in memory in the control plane (reset by a restart); `lastSyncAt` comes from the ledger. The doctor row warns after 3 failed passes in a row. Every pass writes one JSON log line through `Aw.Kernel.Telemetry` (note path relative to the vault, note hash, lines read, events written, lines written, conflicts, duration, outcome; never todo text) inside a `todo.note.pass` span: debug for a pass that changed nothing, info for one that did, warning for a failure.

**Limits.** The note is read up to 1 MB (bigger: "can't read, the note is over 1 MB" on the doctor row; the row warns "note nearly full" at 800 KB); a pass adopts at most 200 new lines (the rest wait for the next pass).

**Stopping.** Removing `todo.obsidian` (Settings' **Stop syncing**, or `sindri todo note stop`) stops the service. Neither can go through `profile set`, which refuses a key that holds a map (`SND-PROFILE-002`, `docs/csharp/sindri.md:69`), so `IProfileKeyWriter` (`Core/Setup`) gains a key removal with `profile set`'s rules (edit in place keeping comments and order, validate the edited text before the atomic write, an absent key is "unchanged"). The service stops once the profile no longer has the key, deletes the base files, and leaves the note exactly as it was.

## 7. Security

- **Agents have the owner's access to todos** (D2). The worst a mistaken session can do is add, edit or soft-delete todos, every one undoable, every one recorded with who did it, bounded by the open cap and the hourly add limit. It can't sort out a conflict, run the import, pick on a held note change, or set or stop the sync: each of those services checks `CallerContext.Class == Human` itself, because desk class alone admits a session with no launch header.
- **Untrusted text is fenced** for every session caller and for the CLI when its output isn't a terminal (§4.4), on every route that returns todo text and on the ledger's `todo.*` events (by shape, every string but ids, hashes, enums, dates, `by` and `via`), with a canary test that walks them all as three kinds of caller. The CLI's choice is a heuristic: an agent under a pseudo-terminal gets plain text. A todo that says "ignore your instructions" is data to the next session that reads it, including an agent the owner started by hand. The "agent" tag follows who added a todo, and "edited by an agent" who last changed it, so an owner's typo fix doesn't make an agent's text look like the owner's and an agent's edit to the owner's todo doesn't hide.
- **Text is scrubbed** (REQ-W2) before the event is written, whoever wrote it, the note included; the merge compares scrubbed text, `todo.conflicted` payloads and the base file are scrubbed. The note itself still holds what the owner typed there until Sindri next writes that line.
- **Text in the note can't act or hide.** D3 refuses the note's markers and the Control and Format characters (tag characters, bidi overrides), from every writer, and Sindri escapes Obsidian markup that runs code or embeds other notes wherever it appears in text it writes (§4.5).
- **One file in one vault.** The note service writes only the configured note, its dot-file twin and its own files under `$AW_SINDRI_HOME/todo/`, never follows a symlink, refuses a hard-linked note, refuses a note path matched by the vault's `deny` globs, checks the real path stays inside the vault before every write, and reads the live profile. The base holds scrubbed task lines only, mode 0600. A `^td-` id is read only as 26 lowercase ULID characters.
- **A rewritten note can't silently undo the owner's day.** Restoring an old copy of the note, or a mass delete, changes more than 3 todos and holds (REQ-E7); removals, edits and un-ticks count, ticks don't. While a hold is open its lines keep their old base lines, so no write can quietly turn the held change into Sindri's, and a pick re-reads the note first.
- **Links are shape-checked** and only ever open Sindri's own pages or an https PR url on a configured forge host (exact host, no user name). A `sindri://` link typed in the note is checked the same way; anything else in a todo line stays as text.
- **Every agent session can read the whole list** (owner's decision, D2): a private todo reaches every session and its model provider. The import step keeps a mistaken note choice from pulling a vault's worth of tasks in.

## 11. Open risks

- **`X` in two meanings on one page.** Needs you's `X` rejects; the panel's checks off. The focus-region rule, the quiet window and TP-8 stop the key from crossing over, but the owner's hands may expect one meaning. Meta's UX pass and Ph0's mockups decide whether the panel needs a different key, with Space as the fallback.
- **An unsaved keystroke in Obsidian's editor.** The swap (§4.5) loses nothing on disk. A keystroke still in the editor's buffer when Sindri writes can be lost when Obsidian reloads; the 2 s quiet wait makes it rare. Ph3b tries it by hand with Obsidian open and reports.
- **The swap call.** `renameat2` and `renamex_np` are P/Invoke from the framework-dependent Sindri host; Ph3b checks both on the owner's file systems (ext4, APFS). There is no fallback write (§4.5): a disk without the call syncs one way, and the doctor row says so.
- **Emoji in the note.** `📅` and `✅` are the Tasks plugin's markers. If the owner finds them noisy, the fallback is Dataview-style `[due:: 2026-11-14]` (the UX pass; one syntax either way).
- **Cold start.** D12's budget holds while Sindri is running. When the app opens before serve is up, the panel shows the Not running card like every other page. TP-7 measures that cold start (bare `sindri` after a reboot to the panel's rows); if it's over 2 s (a guess, the owner's call), the Later item (draw the last list from a local copy) comes forward.
