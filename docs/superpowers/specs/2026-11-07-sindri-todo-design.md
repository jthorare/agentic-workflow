Every file path below is one the author opened on main (af8c954). Every command, route, event, key and type is marked **existing** or **new**.

**Not in scope: notes.** The owner keeps notes in Obsidian (owner, 2026-11-07). A todo is one line, with an optional due date and optional links. It has no body, no checklist and no formatting. The one Obsidian note this spec touches is a list of those lines (§4.5).

## The owner's steps: install -> works

1. **See what's next.** Open Sindri. The top of Home is your todo panel: the next five open todos, overdue first, then today, then upcoming. Focus starts in Needs you, as today; `G T` from any page lands you in the panel.
2. **Add one from anywhere.** Press `N` (on Workflows, where `N` starts a workflow, press `Ctrl+Shift+N`). A one-line box opens at the top of the window. Type "reply to Sam about the offsite fri" and press Enter. The todo is saved with Friday as its due date, and the box closes. Esc closes it without saving.
3. **Check one off.** Tab into the panel, `J`/`K` moves between rows and `X` checks the row off. A "Done. Undo (Ctrl+Z)" toast stays for 10 seconds.
4. **Keep it in Obsidian too (once).** Settings → Connections → **Obsidian todo note**: pick one of your library vaults, name the note (`Todo.md`), **Save**. If the note already has tasks, the card says how many and asks before importing them. From then on Sindri writes your todos into that note as `- [ ]` lines and reads back what you change there, from this laptop or through Obsidian Sync from your phone.
5. **If you changed the same todo in both places**, Sindri doesn't guess. The panel shows "Changed in Sindri and in Obsidian" with both versions side by side, and you pick one (with Undo).
6. **From the terminal or an agent.** `sindri todo add "rotate the staging key" --due 2026-11-10`, `sindri todos`, `sindri todo done td_…`. Agent sessions have the same access through the `sindri_todos` and `sindri_todo` MCP tools (D2).

## 0. Why

The owner runs their day from Sindri: PR reviews, workflows, agents, docs, Linear (owner goals, 2026-11-04: "personal mega app on the work laptop"). Sindri already tracks what's waiting on the owner (Needs you, PRs waiting on review, Linear issues assigned to them). It has no place for the owner's own todos, things like "reply to Sam" or "renew the cert", that have no repo and no run. Today those live in Obsidian, so the owner's plate is split across two apps.

The owner's ranking (§12 Q7): **seeing what's next must feel instant**, more than capture speed. That's why the list sits at the top of Home, the page Sindri opens on, and not behind a tab.

**Why not Sindri's items?** An item (`sindri item add <title> [--repo]`, existing, `docs/csharp/sindri.md:42`) is a unit of agent work. It belongs to a repo of the approved profile (`SND-CLI-003` otherwise), it moves through the queue's groups (`waitingOnYou`, `running`, `queued`, ...), and recipes run on it. A personal todo has none of that. Making todos items would put "call the dentist" in the Work queue and need a fake repo.

**Why not make the Obsidian note the store** and have Sindri only read and edit that file? It would drop the merge, the base file and conflicts. It fails on four things the owner asked for: (1) the panel's first render is one `views.db` read (D12); parsing a vault file on every Home open is slower and fails while Obsidian Sync is mid-download. (2) Undo and stale-write refusal need a version per todo; a file has none. (3) Agents write through MCP (D2); concurrent agents editing one markdown file is the lost-edit problem without a ledger to recover from. (4) The note is optional (step 4): todos must work with no vault at all. So the store is Sindri's, and the note is a two-way mirror of it.

## 1. Decisions

| # | Decision | Reason |
|---|---|---|
| D1 | **Todos are their own store**, not items and not the note: ledger events (§4.1) folded into one view. No repo, no queue, no recipe | §0 |
| D2 | **Agent sessions have the same access as the owner, reads and writes** (owner, 2026-11-07, §12 Q6). The six todo writes (add, change, done, reopen, remove, restore) are **request** class, so the app, the terminal, MCP sessions, Sindri-launched sessions and the note service (`service:todo-note`) can all make them; the reads sit in the same class. Desk class would refuse a launched session (`Authorization.cs:27`), and `NeedsTerminal` would refuse the app's buttons. Two MCP tools serve them (`sindri_todos`, `sindri_todo`, §4.4). `McpSurfaceTests`' allow-list grows by the six write commands, and its "a human decides" summary gains "todos excepted (todo spec D2)". This is the opposite of the Linear-write rule (Linear hub D3) on purpose: a todo list can't change anything outside Sindri. Guards that bound a mistaken loop without taking access away: every event records who wrote it (`by`), the row keeps who **added** it (`addedBy`) and who last changed it (`lastBy`), the panel tags a todo an agent added or last edited (REQ-O3), todo text is fenced for every session caller and for the CLI whenever its output isn't a terminal (§4.4), at most 500 open todos (`SND-TODO-006`), and at most 20 adds an hour per session and per non-terminal CLI caller (`SND-TODO-429`). **Two exceptions:** picking a side in a both-places conflict (D11, and its Undo) and the first import are the owner's alone (`SND-AUTH-002`), because the owner asked to be asked. They are desk class plus the per-start human token check `profile set` uses, so the app (`human:ui`) and the owner's terminal (`human:cli`) pass and MCP and Sindri-launched sessions don't; an agent the owner started by hand that runs the CLI in a shell is a human caller (the toolkit's honest-mistake threat model) | §12 Q6 |
| D3 | **A todo is one line**: text (1 to 280 characters; no character of the Control or Format categories and no line or paragraph separator, the `SafeText` rule (`SafeText.cs:120`), which also stops tag characters and bidi overrides; none of the note's markers `📅` `✅` `^td-`, and no markdown link; passed through `Aw.Redaction` before the event is written; every writer, the note included, is held to this), an optional due **date** (no time), and 0 to 10 links (D10). | D5 | **Two-way sync with one Obsidian note** (owner, §12 Q2). The owner names one note in one library vault. Sindri writes every open and done todo into it as a Tasks-style `- [ ]` line carrying the todo's id as an Obsidian block id (`^td-…`), and reads back adds, ticks, edits and deletes made there. It's the only file Sindri ever writes in a vault; the library feed stays read-only and skips that note. One Sindri per machine, and only the work laptop syncs the note (owner, §12 Q9); nothing detects a second one in v1 | §12 Q2, Q9 |
| D6 | **A panel at the top of Home, no new tab** (owner, §12 Q3). `G T` opens Home with focus in the panel; Home otherwise opens with focus in Needs you, as today. `N` opens the quick-add box from any page but Workflows, and `Ctrl+Shift+N` (⌘⇧N) from every page. The panel and the Needs you list are **two focus regions**: a key acts only on the region that has focus, so `X` in the panel checks a todo off and can never reach Needs you's Reject (§3.3) | §12 Q3. Home already uses `X` for Reject; Workflows already uses `N` |
| D7 | **Due dates are local calendar days.** Overdue = before today in the machine's time zone. The quick-add box and the CLI read a trailing due word ("today", "tomorrow", "mon".."sun" meaning the next one, never today, "11-10" meaning the next 10 November, so next year once it has passed, "2026-11-10") with one parser in Core, and show the date they read. Routes and MCP take an ISO date, or `""` to clear it (`null` reads as absent in the MCP binder). Groups: Overdue, Today, Upcoming, No date. The tray tooltip shows the overdue count. No pop-ups | §12 Q4 |
| D8 | **Done is soft.** `todo.done` sets `doneAt`; the row leaves the panel (Undo in the toast); `sindri todos --done` lists done ones. `Delete` is `todo.removed` (Undo re-adds the same id with `todo.restored`). In the note a done todo stays as `- [x]` until the owner deletes the line there; Sindri never removes a line by itself | Undo must work and must not lose the id or the links. Sindri removing lines would be a write the owner didn't make |
| D9 | **Stale writes are refused.** Each write carries the todo's version, and a stale one is `SND-TODO-409` (the `SND-PROJECT-409` rule). The app reloads the row and keeps the typed edit in the box. A caller that sends no version (MCP, an agent) gets the current one for `done`, `reopen`, `remove` and `restore` (last writer wins, `by` recorded); `change` requires it | Two windows, the CLI, an agent and the note can all edit the same todo |
| D10 | **Many links** (owner, §12 Q5). A todo links to 0 to 10 Sindri things: items, PRs, Linear issues, workflows. Each is a chip on the row. | D11 | **Edited in both places: ask, every time** (owner, §12 Q2b). Different todos changed on each side merge without asking. A pick sets that todo's base line to the note line it was resolved against, so the next pass sees "Sindri changed only" (or nothing) and never asks again; the note write that follows a pick waits until the pick's Undo has expired (10 s), so Undo never has to put Obsidian's side back into the file | §12 Q2b: no silent winner |

| D13 | **The panel never moves Needs you under the owner's hands.** Collapsed, the panel has a fixed height (five rows plus the From elsewhere line, with a placeholder while its counts load). After any row change the owner didn't make (a sync, an agent, midnight), the panel's keys and Needs you's are quiet for `KeyQuiet` (500 ms), the existing Needs you rule | Home's `A` and `X` act on decisions; a list that jumps under them makes a wrong click |

## 2. Goals and non-goals

**Problem.** The owner's plate is split: Sindri shows what agents, PRs and Linear need from them, but their own todos live in Obsidian, so no one screen answers "what do I do next?"

**Who and when.** The owner, at the start of the day and between reviews, with Sindri already open on the work laptop; on their phone, in Obsidian, away from the laptop. Agent sessions, when a run turns up something the owner has to do later.

**Ideal.** Opening Sindri shows the next thing at the top with no wait. Adding a todo takes under two seconds from any page without losing your place. A todo ticked on the phone in Obsidian is ticked in Sindri the next time the laptop syncs. Nothing pulled in from elsewhere can be closed by a stray keypress, and nothing typed in either place is silently thrown away.

**Requirements** (EARS):

- REQ-U1 The app shall show, at the top of Home, the owner's next five open todos (Overdue, then Today, then Upcoming, then No date; each by due date, then by when it was added) and a count of the rest.
- REQ-U2 The panel shall show a read-only From elsewhere line with the count of PRs waiting on the owner's review, of Linear issues assigned to the owner, and of the Needs you rows below it.
- REQ-U3 Sindri shall store todos so they survive a restart and a `views rebuild`, and the CLI, the MCP tools and the app shall show the same list.
- REQ-U4 Where an Obsidian todo note is set, Sindri shall keep every todo as one line of that note, and the note shall show the same todos as the app within 10 seconds of a change on either side while Sindri is running and the note has been still for 2 seconds, except for the 10 seconds after a conflict pick (D11).
- REQ-E1 When the owner presses `N` on any page but Workflows, or `Ctrl+Shift+N` on any page, the app shall open the quick-add box with focus in it. When they press Enter on non-empty text, it shall save the todo and close the box, keeping focus where it was before.
- REQ-E2 When the owner checks a todo off, deletes it, or picks a side in a conflict, the app shall show Undo for 10 seconds (paused while the pointer or focus is on the toast), and Undo shall bring back the todo (or the open conflict) as it was.
- REQ-E3 When local midnight passes while the app is open, the groups and the overdue count shall move without a restart, and focus shall stay on the same todo.
- REQ-E4 When the note gains a top-level `- [ ]` line with no `^td-` id after the first sync, Sindri shall add it as a todo and write the id onto that line.
- REQ-E5 When a sync finds one todo changed in both places since the last sync, Sindri shall show both versions in the panel and change neither until the owner picks one.
- REQ-E6 When a todo note is first set and it already holds task lines, Sindri shall write nothing to it and add no todo until the owner confirms the import, and shall then import only the open (`- [ ]`) top-level lines.
- REQ-E7 When one sync pass would remove, tick or edit more than 3 open todos, or more than half of the open todos in the base, Sindri shall apply nothing from that pass and ask the owner in the panel ("The note changed 14 todos. Apply that in Sindri too, or put them back in the note?"). Removing or editing done (`- [x]`) lines doesn't count, so clearing out ticked lines never asks.
- REQ-S1 While Sindri isn't running, the panel shall show the existing Not running card, and `N` shall say "Sindri isn't running" instead of opening a box it can't save.
- REQ-S2 While a link points at something that no longer exists, its chip shall say so in words ("PR #12 not found") and the todo shall stay.
- REQ-S3 While the note can't be read or written (file missing, vault gone, permission), todos shall keep working in Sindri, no todo shall be removed because of it, the panel shall say "Obsidian note: <reason>", and `sindri doctor`'s `todo` row shall warn.
- REQ-O1 Where a todo has links, the row shall show one chip per link, each opening the linked page.
- REQ-O2 Where a todo has a due date, the row shall show it as a relative word for the next 6 days ("Fri") and as a date after that.
- REQ-O3 Where an agent session added a todo, the row shall say so ("agent"), whoever edited it since; where an agent session last edited a todo the owner added, it shall say "edited by an agent".
- REQ-W1 If a save fails (stale version, Sindri unreachable), the app shall keep the typed text in the box and say why.
- REQ-W2 If the text holds a secret-shaped string, from any writer including the note, Sindri shall scrub it before it's stored, and the merge shall compare scrubbed text on both sides.
- REQ-W3 If an MCP or Sindri-launched session tries to pick a side in a both-places conflict, Sindri shall refuse it with `SND-AUTH-002` and change nothing.

**Non-goals.** Notes. Syncing more than one Obsidian note, or one note from two machines (§12 Q9). Reminders that pop up. Recurring todos. Sharing todos with anyone. Moving items, issues or decisions into the todo store. Drag-to-reorder in the app. A Todo tab.

**Later** (each waits for a week of real use after Ph5). Recurring todos. Manual order in the app. Indented sub-tasks in the note. Links pasted into the quick-add box (refs parsed out of the text). A due-date picker key. "Done today" in the panel. Showing the last list from a local copy before Sindri answers (only if TP-7 shows the cold start hurts). Usage counts by writer. A failure counter in `sindri todo note --json` (v1 has `lastError`). Pruning removed and long-done rows from `view_todo` (v1 keeps them; routes filter by state). Detecting a second machine syncing the note.

**Success measure.** After a week of real use (TP-14), the owner answers one line: "When you want to know what's next, do you open Sindri or Obsidian?" Sindri is the target. If it's Obsidian, the Later list stays shut and the note sync gets no more work beyond fixes.

### 3.1 The panel

Full width of Home's column, above the Needs you list. Header: "Todo", the count line ("4 open · 1 overdue", plus "· 1 to sort out" while a conflict is open), the hint "N New todo", and, when a note is set, a quiet sync line ("Synced with Obsidian 10:05", or "Obsidian note: can't read, Todo.md is missing" in the warning text colour). Then up to five rows, overdue first, and "Show all 11", which expands the panel in place (capped at half the page height, its own scroll, D13) to the grouped list: Overdue, Today, Upcoming, No date, and a "Show done" toggle at its foot that adds a Done group (done in the last 7 days; `X` reopens one). Esc or "Show less" folds it back. Home's decisions filter (`G D`) hides the panel.

A row is a checkbox, the text, the link chips (up to three drawn, then "+7"), an "agent" tag when an agent added it ("edited by an agent" when one last changed the owner's todo, REQ-O3), and the due word on the right. Under the rows, the From elsewhere line: "2 PRs waiting on your review · 1 Linear issue assigned · 3 need you, below". Each part is a link: Reviews, Work → Linear, or focus to the Needs you list. It's a single focus stop; `X`, Delete and Space do nothing on it.

**A both-places conflict** replaces that todo's normal row, at the top of the panel above Overdue, with the attention tint: "Changed in Sindri and in Obsidian", then two columns, **Sindri** and **Obsidian**, each with that version's text, due word and done state, and a button under each: **Keep Sindri's** and **Keep Obsidian's**. A removal on one side is the same row with different words: the removed side's column says "Removed", and its button reads **Remove it** (or **Keep it removed**). After a pick the toast says "Kept Obsidian's version. Undo", and Undo reopens the conflict from the stored versions. The note isn't rewritten until the toast has gone (D11), so Undo writes nothing to the note.

**A mass change** (REQ-E7) uses the same slot: "The note changed 14 todos", with **Apply in Sindri too** / **Put them back in the note**, and "Show which", which expands the row in place to one line per todo (what changed, its text); `J`/`K` move through them, Esc folds it. Keys `1` / `2` pick, as on a conflict row. Apply has Undo; put back has none (it's a write to the note). There is one open hold at a time; while it's open the note's other todos keep syncing, the lines it names are left alone, and each pass re-counts it: lines put back by hand shrink it, and under the threshold it dissolves with nothing to pick.

### 3.2 The quick-add box

A 560 px box under the top bar, over the page, which stays visible behind it. One text field with the placeholder "New todo… (add a day: fri, tomorrow, 11-10)". As you type, a line under it shows what will be saved: "Due Fri 11-14" or "No date". Ending the text with a quote mark (`"`) keeps a trailing day word as text (typing `call mon"` saves "call mon", no date). Enter saves. Esc closes and drops the text. The box opens over sheets and the palette closes first. `N` does nothing while a page holds a form open (the Start, Create and New issue forms set `KeysBlocked`); `Ctrl+Shift+N` still opens the box over them.

`by` is the caller's `CallerContext.Actor` plus its launch id when there is one (`human:ui`, `human:cli`, `session:mcp`, `session:cli:launch-…`), `service:todo-note` for a pass's own bookkeeping, or `obsidian` for an edit read from the note. No todo text goes into `EventCatalog`'s templates; the catalog says "Todo added", never what it says. `addedBy` on the row is the `by` of `todo.added`; the "agent" tag reads it (REQ-O3). `text` passes through `Aw.Redaction` before the event is written, whoever wrote it.

Idempotency key for `todo.added`: `todo.added:client:<clientId>` (1 to 64 of `[A-Za-z0-9_-]`, else `SND-TODO-001`). The app sends one per Enter, the CLI one per invocation (`--client-id` overrides), MCP takes an optional `clientId`; a retried call after a lost answer makes one todo, and doesn't count again against the hourly limit. A todo adopted from the note gets its id **before** its event: the pass mints the id, writes it onto the line in this pass's swap, and only then appends `todo.added` keyed `todo.added:<id>`. A crash between the two leaves a line carrying an id Sindri doesn't know, which the next pass adopts under the same key (§4.5's "an id Sindri doesn't know" row), so a re-run never makes a second todo and retyped text is always a new one.

### 4.2 Projection

`TodosProjection : IProjection` (new, `Aw.Sindri.Core/Todos/`) folds the events into `view_todo` (the existing `key, row_json, seq` shape; the row holds `id`, `text`, `due`, `links`, `addedAt`, `addedBy`, `doneAt`, `removed`, `lastLineHash` (a removed todo's last note line, which tells a stale copy from an owner re-add, §4.5), `version`, `lastBy`, `conflict` or null), plus one `view_todo_note` row (the open hold, the import state, the last sync), in migration `0011_todos.sql` (the number is taken when Ph1a merges; a migration merged first moves it to the next free one) with `ViewSchema.Version` bumped and the row shapes pinned in `ViewRowShapeTests`. The panel reads all rows and sorts in memory (TP-7: 200 rows). It's a pure fold, rebuilt by `sindri views rebuild`, and invalidates `ApiViews.Todos` (new).

### 4.3 Links

A link is one of: an item (`ITM-…`), a PR (`<owner>/<repo>#<n>`, owner and repo each `[A-Za-z0-9._-]` and never `..`, or its https url on a configured forge host: the url is parsed, the host compared exactly, a user name refused, as `LinearText` does), a Linear issue key (`ENG-12`), or a workflow address (the existing address shape, `[a-z0-9-]` segments). It's stored as the deep link the app already opens (`sindri://item/…`, `sindri://reviews/<owner>/<repo>/<n>`, `sindri://linear/ENG-12`, `sindri://workflow/…`). The server checks only the shape (`SND-TODO-004`), never whether the thing exists, so a link to something not synced yet is allowed. The chip resolves it when drawn (REQ-S2). Duplicates are dropped; an 11th is `SND-TODO-004`.

**Fencing.** Every text field the routes return is fenced (source `sindri:todo`, author the row's `lastBy`) for a session caller, and for any caller that asks with `?fence=1`: `todos[].text`, an echoed `text`, a conflict's `sindri.text` and `obsidian.text`, a hold's per-todo text, and the note route's per-line error text. A retried add with the same `clientId` adds no event, so it doesn't count.

### 4.5 The Obsidian note (context lane)

**Setting it.** A new profile key, `todo.obsidian` (`{ vault, note }`): `vault` is the `name` of one of `context.sources.library.vaults`; `note` is a vault-relative path ending `.md`, no leading `/`, no `..`, not inside a dot folder and not matched by that vault's `deny` globs. The note must not be a symlink or have more than one hard link. A bad value is `SND-TODO-002` with the key path. The Settings card writes it and approves just that change, with the Linear card's rule (Linear hub §5.1). The service reads the **approved** profile snapshot only, so a drifted live file can't point Sindri's writes elsewhere. With no key set, nothing below runs. **One Sindri per machine, and only the work laptop syncs the note** (owner, §12 Q9): `docs/sindri/todo-note.md` says so; v1 detects nothing, and a second machine syncing the same vault would read the first one's writes as Obsidian edits.

**First sync and import** (REQ-E6). With no base yet, the service reads the note and writes nothing. A missing note: the card says it will be created, and the first write creates it with a `# Todo` heading. A note with no open task lines: syncing starts. A note with open task lines: the card shows the counts and waits for **Import** (or `sindri todo note import`). Import re-reads the note, adopts each open top-level `- [ ]` line (done lines and lines under a fenced block, quote or callout are left alone; a line that breaks D3 stays as text and the doctor row names it), writes the ids onto them, appends Sindri's todos after the last one, and records `todo.note.imported`. Adopted lines count against the 500 open cap; past it the rest stay as text and the doctor row says how many. Changing the note (**Change**) drops the base and starts this step again for the new note; the old note is left as it is.

**The note's format** ([Obsidian Tasks](https://publish.obsidian.md/tasks/) style, so the note also works with that plugin, though it doesn't need it):

```markdown
# Todo

- [ ] reply to Sam about the offsite 📅 2026-11-14 ^td-01jc5a8xq0n4w7ms2t9r3vbk6e
- [ ] rotate the staging key 📅 2026-11-10 [PR #12](sindri://reviews/jthorare/agentic-workflow/12) [ENG-12](sindri://linear/ENG-12) ^td-01jc5b2kz8m3r6tq1w9xh4dn7y
- [ ] call the dentist ^td-01jc5c90a2b7k4m8q1r6t3w9xz
- [x] renew the cert ✅ 2026-11-07 ^td-01jc5917f3h8n2p5s9v4x1z6bq
```

- One top-level `- [ ]` / `- [x]` line per todo. Due is `📅 YYYY-MM-DD`; done is `[x]` plus `✅ YYYY-MM-DD`; each link is a markdown link to its `sindri://` deep link; the id is the trailing Obsidian block id `^td-<the full ulid, lowercase>` (Obsidian keeps block ids through edits, and they're invisible in reading view). An id that isn't 26 lowercase ULID characters isn't an id: the line is a new line. One syntax only; Dataview-style fields are text.
- Task lines inside a fenced code block, a quote or callout, or indented under another line are not todos. Everything that isn't a top-level task line (headings, prose, blank lines, indented lines) is kept byte for byte. Sindri only touches task lines that carry a `^td-` id, plus lines it adopts.
- **A line that breaks D3.** A new line that would parse as a todo but breaks D3 (two ids, two due markers, a marker inside the text, a pasted markdown link, a forbidden character) is kept as text and the doctor row names its line number. A line with a **known** id that breaks D3 (the owner pasted a link into it) is **held**: Sindri keeps the todo as it is, removes nothing, and says "line 14 can't sync: it has a markdown link" on the panel's sync line and the doctor row. It syncs again once the line is valid.
- **Escaping.** Obsidian markup that runs or embeds is escaped with a backslash wherever it appears in text Sindri writes: `` ` ``, `<`, `![[`, `[[`, `%%`, `$=`. The parser unescapes exactly that set, so render then parse gives the same todo (a property test in Ph3, whose generator includes every escaped sequence). A line adopted from the note keeps the owner's raw text until the todo's text changes in Sindri; only then is it written escaped.
- **Order is the owner's.** Sindri never reorders lines. A todo added in Sindri goes after the last todo line (or at the end of the note when it has none). Sindri never removes a line by itself (D8); a removed todo's line is removed only when the removal came from Sindri.

**Reading.** `TodoNoteWatch` (new, a lease-holding host like `ProfileWatch`) runs while the control plane holds the lease. It checks the note every 60 s and at start, and a non-recursive `FileSystemWatcher` on the note's folder triggers an earlier check (a trigger only: watchers miss events on some file systems). A built-in service `todo-note` with a 24 h cadence (`BuiltInService` has no manual cadence; the watch host does the real polling) lets `sindri services run todo-note` force a pass. When the note's sha256 differs from the last `todo.note.synced` hash, it waits until the file has been unchanged for 2 s (Obsidian saves as you type), parses it, scrubs each line's text, and runs the three-way merge below. **Obsidian Sync edits arrive the same way.** An edit made on the phone while the laptop was shut lands when Obsidian next syncs here, and the merge treats it like a local edit made at that moment. A note that is missing, unreadable or 0 bytes while the base isn't empty is "can't read" (REQ-S3), never "every line was deleted".

**The base** is the note's top-level task lines as Sindri last synced them (not the prose), stored scrubbed, at `$AW_SINDRI_HOME/todo/note-base-<hash>.md`, mode 0600, named by its own hash; the last `todo.note.synced` names it (`baseHash`). The pass reads the base that event names, so a crash between saving a base and appending the event leaves the previous base in force. A missing base, or one whose hash doesn't match, counts as no base: the pass adopts and appends, never removes, and a todo whose text differs on the two sides becomes a conflict, not a silent winner. Older base files are deleted after the event lands.

**The three-way merge**, per todo id, between the **base**, the **note** now, and **Sindri** now (the projection), comparing scrubbed text:

| Note vs base | Sindri vs base | Result |
|---|---|---|
| same | same | nothing |
| changed (text, due, links, ticked, removed) | same | the matching event, `by: obsidian` |
| same | changed | the note's line is rewritten from Sindri |
| changed | changed, to the same values | nothing (both already agree) |
| changed | changed, differently | `todo.conflicted` (D11): Sindri keeps its version, the note's line is left as is, neither side syncs that todo until `keep` |
| after a pick | — | the base line for that id is the pick's `baseLine` (the note line it was resolved against). `keep sindri`: note = base, Sindri changed → the line is rewritten from Sindri once the Undo time is over. `keep obsidian`: Sindri now equals the note → nothing |
| a known id on a line that breaks D3 | — | held (above): nothing changes on either side, the sync line and doctor say why |
| new line, no `^td-` | — | adopted: the id is minted and written onto the line in this pass's swap, then `todo.added` `by: obsidian` (§4.1's key) |
| the same `^td-` id on two or more lines | — | the first in file order keeps the id; each later one is a new line (adopted, new id written) |
| an id Sindri doesn't know | — | adopted as a new todo with that id (also how a crash between the swap and the event heals) |
| an id Sindri has as removed | — | compared with the row's `lastLineHash`: the same line is a stale copy (an old note restored, a sync lagging) and is dropped from the note again; a different line is an owner re-add (`todo.restored` `by: obsidian`, then the edit) |

**The hold** (REQ-E7). Before any events are written, the pass counts the **open** todos it would remove, tick or edit from the note: more than 3, or more than half the base's open todos, and it applies none of those, records `todo.note.held` with what each change is, and asks. Changes to done lines and adds don't count, and the pass still applies them, plus every change to todos the hold doesn't name. While the hold is open the writer leaves the lines it names alone. Each pass re-counts: lines put back by hand drop out, a smaller set replaces the hold, and under the threshold it dissolves. **Apply** applies the held changes (with Undo, as one batch); **Put them back** rewrites those lines from Sindri.

Events the sync writes use the version-key append like every other writer; a `SND-TODO-409` on its own event re-runs the merge from a fresh read.

**Writing.** A write is due after any todo event not `by: obsidian`, after a merge, and 10 s after a conflict pick (D11: not before, so Undo has nothing to put back). It waits until the note has been unchanged for 2 s (up to 30 s, then writes anyway), and events arriving in that wait share one write. Then:

1. Build the new note from the merged state, editing only the lines that need it, into `.<note name>.sindri-tmp` beside the note (a dot file, which Obsidian doesn't show or sync), created exclusive and without following links, with the note's file mode. Write the intent file `$AW_SINDRI_HOME/todo/writing` holding the tmp file's hash.
2. **Swap** it with the note in one system call (`renameat2(RENAME_EXCHANGE)` on Linux, `renamex_np(RENAME_SWAP)` on macOS). The tmp path now holds exactly what was at the note's path at that instant.
3. Wait until what came out has been unchanged for 2 s (an editor that opened the note before the swap may still be writing to it), then hash it. Empty or shorter than the note Sindri merged is "not settled yet": wait again, and it's never read as a note edit. If it equals what the pass merged, delete it: nothing was lost. If it differs, Obsidian saved in between: merge that content as the note (a normal note edit against the same base) and write again from step 1. Each retry compares against what the previous swap wrote, and after 3 swaps in one pass the pass stops with "note busy" and tries again at the next 60 s check.
4. Save the base and record `todo.note.synced` (`hash` = what was written), then delete the intent file.
5. At start, a leftover tmp file is read against the intent file: its hash equal to the intent means the swap never ran (delete it, nothing came out); otherwise it's what came out, merged as in step 3, then deleted.

This closes the window a rename over the note leaves open (/autoplan round 1, the TLA+ model `NoteWrite.tla` found an edit saved between the hash check and the rename lost; round 2's `NoteWrite3.tla` passes the swap for an editor that writes in place and needs step 3's 2 s settle for one that opens before the swap and writes after it). What remains: an edit still in Obsidian's editor buffer, not yet saved, when the file changes on disk; Obsidian reloads and that keystroke can be lost from the editor. The 2 s quiet wait makes that rare; Ph3 tries it by hand with Obsidian open and reports. **No fallback:** on a file system without the swap call, the note is read into Sindri (adds, ticks and edits made there still arrive) but never written, and the doctor row and the Settings card say "can't write: no atomic swap on this disk". A rename after a hash check is the rev 2 bug (round 2's model shows it losing an edit), so it isn't offered.

**Failures.** The vault folder gone, the note missing or unreadable, the swap refused: no event, no removal, the `todo` doctor row warns with the reason, the panel's sync line says it, and todos keep working in Sindri. The next change or the 60 s check tries again. `lastCheckAt` and `lastError` live in memory in the control plane (reset by a restart); `lastSyncAt` comes from the ledger. The doctor row warns after 3 failed passes in a row. Every pass writes one JSON log line through `Aw.Kernel.Telemetry` (note path relative to the vault, note hash, lines read, events written, lines written, conflicts, duration, outcome; never todo text) inside a `todo.note.pass` span: debug for a pass that changed nothing, info for one that did, warning for a failure.

**Limits.** The note is read up to 1 MB (bigger: "can't read, the note is over 1 MB" on the doctor row; the row warns "note nearly full" at 800 KB); a pass adopts at most 200 new lines (the rest wait for the next pass).

**Stopping.** Clearing `todo.obsidian` (Settings' **Stop syncing**, or `sindri todo note stop` then `sindri profile approve`) stops the service once the approved profile no longer has the key, deletes the base files, and leaves the note exactly as it was.

## 7. Security

- **Agents have the owner's access to todos** (D2). The worst a mistaken session can do is add, edit or soft-delete todos, every one undoable, every one recorded with who did it, bounded by the open cap and the hourly add limit. It can't sort out a conflict, run the import, pick on a held note change or stop the sync.
- **Untrusted text is fenced** for every session caller and for the CLI when its output isn't a terminal (§4.4), on every route that returns todo text and on the ledger's `todo.*` events, with a test that walks them all. A todo that says "ignore your instructions" is data to the next session that reads it, including an agent the owner started by hand. The "agent" tag follows who added a todo, and "edited by an agent" who last changed it, so an owner's typo fix doesn't make an agent's text look like the owner's and an agent's edit to the owner's todo doesn't hide.
- **Text is scrubbed** (REQ-W2) before the event is written, whoever wrote it, the note included; the merge compares scrubbed text, `todo.conflicted` payloads and the base file are scrubbed. The note itself still holds what the owner typed there until Sindri next writes that line.
- **Text in the note can't act or hide.** D3 refuses the note's markers and the Control and Format characters (tag characters, bidi overrides), from every writer, and Sindri escapes Obsidian markup that runs code or embeds other notes wherever it appears in text it writes (§4.5).
- **One file in one vault.** The note service writes only the configured note, its dot-file twin and its own files under `$AW_SINDRI_HOME/todo/`, never follows a symlink, refuses a hard-linked note, refuses a note path matched by the vault's `deny` globs, checks the real path stays inside the vault before every write, and reads the approved profile only. The base holds scrubbed task lines only, mode 0600. A `^td-` id is read only as 26 lowercase ULID characters.
- **A rewritten note can't silently undo the owner's day.** Restoring an old copy of the note, or a mass delete, changes more than 3 open todos and holds (REQ-E7); ticks and edits count, not only removals.
- **Links are shape-checked** and only ever open Sindri's own pages or an https PR url on a configured forge host (exact host, no user name). A `sindri://` link typed in the note is checked the same way; anything else in a todo line stays as text.
- **Every agent session can read the whole list** (owner's decision, D2): a private todo reaches every session and its model provider. The import step keeps a mistaken note choice from pulling a vault's worth of tasks in.
