## The owner's steps: install -> works

0 lines of YAML, 0 commands. After `./setup.sh` and the first map build (setup-once spec), on the app's Context page:

1. On a concept card, press **Pin this**. A sheet opens filled in from the map: the name, a definition line (the concept's summary), the words people use (aliases, from the concept's terms, each with how many records it would link), and the features it holds. Edit any of them, or leave them.
2. Press **Pin and approve**. Sindri writes the pin into the profile, then the app approves exactly that profile, since the pin is the only change waiting.
3. Nothing else. Within a minute of the approval the map refresh starts by itself (the built-in `context-map-refresh` service already rebuilds when the pins change; about 4 minutes on this repo's 9,111-file map, 0 model calls). While it builds, the card shows the build's own progress (`Pinned · rebuilding the map: resolving calls`); when it lands, the card shows what moved (`+4 features, 3 more records linked here`). An alias-only edit rebuilds nothing: the records are relinked in seconds (§3.4). A definition-only edit rebuilds nothing either: it shows on the card and in `context_concepts` the moment it is approved (§3.4). A name edit does rebuild (the name is the concept node's label), moves no evidence, and the card keeps the old name until it lands; the sheet says so before you press the button.

What the sheet, the cards and Add several look like is the owner's pick from 2-3 mockup variants before any of it is built (phase Q7m, as the Projects page did, #1616 -> B); the build matches the picked mockup.

That is **2 clicks** when the pin is the only waiting change. When other changes wait too, the button says **Pin** and the third click is the needs-you bar's **Review and approve**, which shows every waiting change, the pin among them. **Add several** on the layer's head takes a pasted list (one concept per line, `Name: definition` with optional `(also: word, word)`), shows one sheet row per line with the matching map concept pre-picked, and writes them all in one profile write: one approval and one rebuild for the whole list, the way #1701's owner described it ("this is the list of concepts, let me add these in").

From then on `context_query` questions that use the team's words anchor on the pin, `concept=billing` scopes an answer to it, and the pin survives every rebuild and publish. Editing works the same way: **Edit pin** on a pinned card, the same sheet. **New pin** does it for a concept the map didn't find (it takes typing and a feature search, so it is more than 3 clicks by nature). The profile's YAML (§3.4) is the power path for what the sheet doesn't cover (`paths` globs, `dependsOn`, `owns`); nobody needs it to get started.

**What moves evidence.** The build regroups by the pin's features and paths, and (from Q9) the record linker links records that name one of its aliases. The definition is for people and agents (shown on the card, returned by `context_concepts`); it is read from the approved profile when shown, not from the map, so it moves no evidence and costs no rebuild (§3.4). The sheet says so under the field: `Shown to people and agents; it moves no records and needs no rebuild.`
**Builds on:** `2026-10-27-sindri-context-map-structure-design.md` §10 (pins shape home features and the roll-up; merged), whose §10.5 and Open question 14 left this half to a separate design. `2026-10-10-sindri-context-retrieval-design.md` (D3 Sindri owns ranking, D13 rerank off by default, §8.2 the ranking steps). `2026-10-19-sindri-code-index-design.md` (CI4, CI7, CI13).

## 0. Why

A pin (`index.concepts` in the profile, `ConceptPin`, `Aw.Context.Core/Engine/ConceptPin.cs:11`) is where the owner says how *they* divide the product. Since §10 of the map-structure spec the map build respects pins: home features never span two pins, and pins roll up `depends-on` / `reads` / `writes`. The **query side** still ignores them:

1. `context_query` can't be scoped to a pin. "How do refunds work in billing" returns a `notify` doc about refund emails next to the billing ones.
2. A query can be anchored on a pin (`node=concept:billing` works, `Aw.Sindri.Host/Mcp/ConceptTools.cs:25`), but nothing in ranking prefers the docs and records that sit inside it.
3. The words a team uses for an area ("payments", "invoicing", the old name "ledger") are not on the pin, so a question using them never anchors to it. `AnchorMatch.FromText` (`Aw.Context.Core/Graph/AnchorMatch.cs:77`) matches node labels only.
4. An agent can't tell which concepts are pins: `context_concepts` rows say `derived` or `override` (`ConceptRow.cs:10`).
5. The code index's symbol search (`ICodeIndex.FindSymbols`, `Aw.CodeIndex.Core/Facade/ICodeIndex.cs:54`) can't be scoped to a pin either.
6. A pin can only be made by editing the profile's YAML, then `sindri profile approve`, then waiting for the next refresh. #1701 asks for the opposite: the owner types their company's concepts into the app, with definitions and the words people use, and the map is re-evaluated from that list, with the owner's input surviving rebuilds and kept apart from machine suggestions.

## 1. What the code does today (read from main 70cb128fa)

- **What `context_query` fuses.** `QueryPipeline.Run` (`Aw.Context.Features/QueryContext/QueryPipeline.cs:42-83`) searches the catalog's sources (repo docs, `RepoDocsSource`; Linear, skipped at `:197`) plus the record store's lexical and dense legs (`RecordStoreSource`, `DenseRecordSource`, built in `WithRecordStore`, `QueryPipeline.Lexical.cs:59-85`), fuses their ranks (`RankFusion.Fuse`, RRF, `K = 60`, ties by key, ordinal), then multiplies by `1 + Σ weight × feature` (`FeatureRanker.Boost`, five features in `RankFeatures.cs`), then an optional model rerank (off by default). **Code is not a fused leg.** Code files reach a `context_query` answer as the graph part's candidates (`GraphAnswer` → `GraphPart.Candidates`, the cascade from the anchor), which never enter `Fuse`. `ICodeSearch` / `GitCodeSearch` serve the code lens (`GetCode/LexicalCandidates.cs:22`), not `context_query`.
- **A map version stores a hash of the pins, not the pins** (`MapRuleset.cs:18-36,44-45`). At query time pins come from the approved profile (`ContextScopes` maps the approved profile's repos, each with its `Concepts`, `ContextScopes.cs:10-54`). `MapRuleset.Running(scope)` (`:41`) gives the hash the current pins would build; the map stores the hash it was built with.
- **Aliases on graph nodes are key-to-key** (`NodeAlias(NodeKey Alias, NodeKey Target)`, `NodeAlias.cs:8`), validated as keys (`MapDocumentValidator.cs:101`). A free word like "ledger" can't be one. Concept terms live on the concept node as an attribute (`ConceptTermsAttribute.cs:7-12`), read by `ConceptGlossaryBuilder`.
- **The code index has its own glob matcher**, `InputRules.MatchesAny` (`Aw.CodeIndex.Core/InputRules.cs:86-92,159-185`): `*`, `?`, `**`, `prefix:` / `suffix:` / `regex:`, ignoring case. Context's `PathDenylist.MatchesExactCase` (`PathDenylist.cs:39`), which homing uses (`HomeFeatures.cs:66`), keeps case. The symbol query cuts in SQL (`ORDER BY … LIMIT`, `SqliteIndexReader.Symbols.cs:48`).
- **There is no concept cap.** `MaxConcepts` is gone from the code; `ConceptPlan.cs:11` says "with no fixed number of concepts" and derived concepts are limited by merging small groups (`ConceptGrouping.Merge`). The map-structure spec's mentions of it are stale (fixed in this PR, §8).
- There is no query expansion anywhere.
- **What the app already has** (read from main 934fc1c2c). The Context page opens on the concept layer (`ConceptLayerViewModel`, `ConceptTileViewModel`): one card per concept with its size line, its top terms (`Labels.ContextConceptTerms`, read from `ConceptTermsAttribute`) and a `Set by a person` mark for pinned or overridden concepts (`IsSetByPerson`). The app already writes the profile for the owner: **Add repository** runs the `AddRepo` job, which appends through the versioned profile write and leaves the approval as its own step (`AddRepoService.cs:10-14`). The app approves the profile through the `ApproveProfile` setup step (`Labels.Setup.cs:15`). The map refresh is a job, `RefreshContextMap` (build, settle, publish decision, publish; `RefreshContextMapService.cs:13-19`). The built-in `context-map-refresh` service (`ContextMapRefreshService`, every minute) already queues it when the running ruleset hash differs from the map's (`RulesChanged`, `:186`, registered with `RulesFromScope = true`, `ContextSlicesServiceCollectionExtensions.cs:120`); a pin's name, summary, features and paths are in that hash (`MapRuleset.Pin`), so an approved pin edit already triggers a rebuild within a minute (this spec takes the summary out, §3.4). The build itself makes no model calls; the refresh's cleanup pass (`CleanMapService`) asks a model only about model-made proposals below `CleanupPolicy.KeepAt`, and on this repo's last refresh it had 0 to decide (`cleaning up: 0 to decide`, 3 min 50 s end to end over 9,111 files, scratch home of 2026-10-29). Record links are made at sync time by `RulesLinker` (`Aw.Context.Core/Linking/RulesLinker.cs`), whose name match (`Names()`, `:118-135`) offers feature labels and aliases of two words or more, as a suggestion; `IntentOverlay.Apply` only merges the stored links into the graph at read time (`MapAccess.cs:77`).
- **The other owner-input paths, audited for #1701.** Overrides (`Aw.Context.Core/Overrides`, table `map_override`: accept, reject, rename, merge, move, add, delete, propose, undo) are keyed by node key and applied over every rebuild and import, so they already survive rebuilds; they correct single nodes, not "which evidence belongs to this concept". Importing an authored map (`ImportMapService`) replaces the current version with a file, behind the protected-command gate; it is not a way to keep a concept list. Pins are the only input that changes how the build *groups* evidence (`ConceptPlan.Pinned`), so they are the owner's concept list, and this spec gives them an app surface rather than adding a fourth mechanism. A rename override on a derived concept carries into **Pin this** (the sheet shows the renamed name).

## 2. Goals and non-goals

**Goals**
- G1. `context_query concept=<pin>` (MCP, CLI, HTTP) returns only results inside the pin: fused docs and records, and the graph part's nodes.
- G2. When a query is anchored on a pin, or on a node inside exactly one, the fused docs and records inside that pin rank higher, through fusion, switchable as a backtest arm. (Code needs no boost: the graph part already starts its cascade from the anchor.)
- G3. Pin `aliases` make a question that uses the team's words anchor to the pin; `context_concepts` shows which concepts are pins and their aliases.
- G4. `sindri code-index symbols --concept <pin>` is scoped the same way.
- G5. The owner makes, edits and removes pins from the app's concept cards in at most 3 clicks, with name, definition, aliases and features pre-filled from the map (§3.6). The same writes exist as CLI verbs for scripts and agents to *propose* (a session can write, never approve).
- G6. After an approved pin edit the existing refresh service rebuilds the map by itself; the card shows that build's progress, and the stale-map notes show only while it runs (§3.7).
- G7. The concept layer shows the owner's pins apart from machine suggestions, what each pin covers, what is in no pin, which features two pins claim, and what moved on the last refresh (§3.8).

**Non-goals**
- N1. **No pin column in any store.** Pins are matched at read time against the approved profile (§3.1). A stored pin id needs a code-index schema bump and rebuild, and goes stale on the next pin edit because the code index has no ruleset hash.
- N2. **No concept cap.** The issue asked pins to count against `MaxConcepts`; that cap no longer exists, and the catch-all it guarded against (#1339) is handled by merge-based grouping (Open question 3).
- N3. No query expansion with alias words (Open question 2).
- N4. No change to the map build, homing or the roll-up, and aliases stay out of the map hash. The one linking change is that the record linker matches pin aliases, so a record that says "payments" links to `concept:billing` (§3.4, Q9); that is what makes re-evaluation reassign records, not only features (#1701).
- N6. No named pages and actions (#1701's other half): its own spec.
- N5. No `concept=` on the code lens (`GetCode`) or on `callers` / `callees` / `similar` (Open question 4).

## 3. Design

### 3.1 One pin resolver: `PinScope` (public, `Aw.Context.Core/Concepts/PinScope.cs`)

```csharp
public sealed class PinScope
{
    public bool Holds(RecordKey record);   // a fused item's key: repo docs by path, records by node
    // also public: PinSet.Of(mapped, visible, graph) with PinOf(NodeKey) -> ConceptId? (every visible pin at once, for the counts and the anchor)
    public static Result<PinScope> Of(IReadOnlyList<ContextRepo> mapped, IReadOnlyList<ContextRepo> visible, string id, GraphSnapshot graph);
    public ConceptId Pin { get; }
    public bool HoldsPath(ContextRepoName repo, string repoRelativePath);   // first pin wins, per repo
    public bool HoldsNode(NodeKey key);
    public static ConceptId? PinOf(NodeKey anchor, IReadOnlyList<ContextRepo> mapped, GraphSnapshot graph);   // the anchor's pin, or null
}
```

- **Ids.** `Of` runs the internal `PinIds.Resolve` / `PinIds.Of` (`PinIds.cs:14,32`) over `mapped`, the repos the map is built from (`ScopeRules.Mapped(settings, scope.Repos)`, as `MapRuleset.Running` does), so `concept=billing` names the same pin the map shows, never a `billing-2` made from a smaller set.
- **Visibility.** The lookup and the "nearest ids" of the error consider only pins that apply to a repo in `visible` (the caller's resolved repos). A pin that applies only to repos the caller can't see answers exactly like a typo.
- **`HoldsPath(repo, path)`.** True when the path matches this pin's `paths` in that repo's pin order (`RepoConcepts.For`: the profile's pins, then the repo's) and no earlier pin of that repo matches it: first pin wins, as in homing. Matched with `PathDenylist.MatchesExactCase`, the same matcher homing uses.
- **`HoldsNode(key)`.** Code nodes: through their **home feature** (the one `implements` edge to a home leaf, map spec §2) and that leaf's `belongs-to concept:<id>`, never through tag features. This is the map's own grouping, so path pins and `features:` pins both work. A leaf can `belongs-to` two pins when a `features:` glob and another pin's `paths` both claim it (`ConceptPlan.Pinned` doesn't apply first-pin-wins); `PinSet` then gives it to the first in `RepoConcepts.For` order, so `HoldsNode` and `HoldsPath` agree and a file is in one pin. Features: `belongs-to concept:<id>`. Records and decisions: a `belongs-to` or `mentions` edge to the concept or to a member feature (`EdgeRules.cs:25-27` allows both kinds as sources; the map spec's §11 roll-up adds `record mentions concept`). The concept node itself. Built once per query into a key set; O(1) per check.
- **Stale map.** When the map's stored ruleset hash differs from `MapRuleset.Running(scope)` (computed over the repos the map was built from, not the caller's narrower scope, so it doesn't fire on every query of a session that sees fewer repos; the note names no pin, so an edit to a pin the caller can't see only says that pins were edited), file paths and feature membership can disagree (globs are current, `belongs-to` edges are from the last build). Since the refresh service rebuilds on that difference within a minute (§3.7), this is normally a short window, and the note says so: while a `RefreshContextMap` job is queued or running, (read through Q8's `IMapRebuildState` port, which Sindri implements; a tick that starts nothing doesn't count), `pins changed; map v42 is being built with them, so some features are grouped the old way until it lands`. Only when no such job is running (it failed, or the box was down) does the note carry a fix: `pins changed after map v41 was built and the refresh for them didn't finish (fix: Refresh map on the Context page, or sindri context map refresh)`. No refusal either way.
- **Where it's built.** The map is read inside `AnchorFor` today, and the anchors come out of it. Q1a makes `AnchorFor` also return the `VisibleMap` it read (its `Snapshot` is the whole stored graph, its `Version.Ruleset` the stored hash) and builds `PinContext` right after it: the `PinSet`, the `concept=` `PinScope` and the anchor's pin, handed to the legs, the graph part and the ranker. `PinSet` is cached per (map version, approved profile hash), not rebuilt per query. With `concept=` and no readable map: `SND-CONTEXT-105: concept= needs a built map (fix: sindri context map build)`. `mapped` is `ScopeRules.Mapped(settings, request.Scope.Repos)`. Later phases only read `PinContext`. Q1a also adds `string? Concept = null` to `PipelineInputs` (`PipelineInputs.cs`, which already carries the test override for the ranker); `PinContext` resolves `inputs.Concept ?? request.Query.Concept`, so Q2b and Q2c are tested through it before Q2a exists. With no pins at all, `PinContext` is empty and skips every lookup.
- **Ids and aliases.** `id` may be a pin id, `concept:<id>`, or one of a pin's aliases (§3.4), so `concept=ledger` works wherever `node=ledger` does.
- **Errors.** All four query-side ids (102-105) join `ContextErrors.Attention` (`ContextErrors.cs:262`), so they exit 1 like an unknown anchor or a missing map. `SND-CONTEXT-102` `no pin is named 'bilin' (fix: try billing, auth)`, at most 5 suggestions, from visible pins only. With no pins at all (`SND-CONTEXT-103`): `no pins are set up (fix: add index.concepts to the profile)`. `SND-CONTEXT-104` when the approved profile has the pin but the map version has no `concept:<id>` node yet (checked on the whole map version before it is cut to the caller's scope, so a session whose scoped view has no member of the pin doesn't get it falsely): `pin 'billing' is newer than map v41 (fix: sindri context map build)`; the visibility check runs before it, so it never names a pin of a repo the caller can't see. A pin that matches nothing in this map: no error, the empty-answer note below says so.

### 3.2 `concept=` on `context_query` (G1)

- **Surface.** MCP `context_query` gains the text arg `concept` (the `_texts` allow-list and the error text in `ContextTools.Bind.cs:58`); its description: "a pin id from context_concepts (rows with pinned: true); only results inside that pin". CLI `sindri context query … --concept <id>` (`ContextVerbs.cs`), and its help line. `ContextQuery` gains `Concept` as an `init` property (not positional), which also reaches the HTTP route, `ISindriApi.ContextQuery`, the UI client and `FakeSindriApi` (API goldens change; the Ui tests run in that gate). Combines with `--repo` and with every query shape: with `text`, `node` and `item` it filters the results as below; with `symbol` the symbol is the anchor and its lens is cut to the pin like any graph part; with `diff`, changed files outside the pin are left out of the anchor set and the answer notes `concept billing: 4 of 9 changed files are outside it`.
- **Where it applies**, beside the existing masks, so each leg's limit fills with in-pin results:
  - **Record legs.** `RecordStoreSource` and `DenseRecordSource` take an optional `PinScope` the way they take `AudienceScope`; a record passes when `HoldsNode(record:<key>)`. The audience mask runs first (`DenseRecordSource.cs:22,116`).
  - **Repo docs.** `SourceQuery` (`SourceQuery.cs:8`) gains an optional `init` `Pin` filter, and `SourceDescriptor` a `HonorsPin` flag (the repo's idiom for source traits; no interface in `src` has a default member) so the pipeline knows which sources apply it; `RepoDocsSource` keeps a doc chunk when its record node `HoldsNode` (the doc's record links to the pin or a member feature) or, failing a link, when `HoldsPath(repo, path)` (a `services/billing/README.md` inside the pin's code paths). Docs come in **through links, not globs**: the owner is never asked to add a `docs/**` glob to a pin. A doc under `docs/` with no link is left out until #1373 makes it a linked record (the list below). Sources that ignore the filter (Linear's live source) are left out when `concept=` is set, with a note, rather than returning unscoped hits.
  - **Graph part.** Candidates and nodes outside the pin are dropped, except the anchor itself and edge ends that are other pins or data stores (`thing` nodes, the tables the extractor finds; a billing lens still shows that billing writes `invoices`).
- **Scoped answers say so.** Every answer under `concept=` starts with `scoped to concept billing (map v41)`.
- **Empty is an answer, with a way out.** No in-pin results returns an empty result and a note built only from what the caller may see, after repo scope, audience and deny globs: `concept billing: no results. Of the results read, 7 were in auth and 3 in no pin (fix: concept=auth, or drop concept=)` (visible pins with results, most first, at most 5, then `no pin`); with none at all, `concept billing: no results, and none outside it either`; for a pin whose globs match nothing, `concept billing matches no file in this map (check the paths of pin 'billing' in index.concepts)`. Never a silent fallback to the unscoped search. **How the counts are made:** the lexical record leg and repo docs, while filling their limit, count the rows they skipped for the pin, by the pin they are in (`PinSet.PinOf`); those rows had already passed the audience mask. The dense leg masks inside its vector scan and is left out of the counts. They are counts among the rows read, not totals, and cost no second search. A pin is named only when it applies to a repo the caller can see; any other is counted under `no pin`.
- **A file in no pin is never returned with `concept=`** (strict; Open question 5). Records not linked to the graph have no pin.
- **What v1 covers, and what it leaves out until #1373.** `concept=` ships before #1373 (repo docs and tracker items becoming records linked to features; open, measured there at 583 docs synced, 2 records). Waiting would hold back the half that works now, and the `no pin` count in every empty answer shows the gap honestly. What is in and out:

  | Kind | Under `concept=` in v1 | Why |
  |---|---|---|
  | Code files | in, through their home feature | the map already homes every file (map spec §2) |
  | Features, concepts, data stores | in | `belongs-to` and the roll-up edges are built today |
  | Repo docs inside a pin's code paths | in, by path | no link needed: the path is the evidence |
  | Records the record linker links (link rules, name matches, and from Q9 pin aliases) | in | they have a `mentions` or `belongs-to` edge |
  | Repo docs elsewhere (`docs/**`, top-level READMEs) | **out** until #1373 | only 2 of 583 synced docs are records today, so they have no link to follow |
  | Linear, Slack and GitHub records no rule or name links | **out** until #1373 | same: no edge, so no pin; strict `concept=` won't guess (Open question 5) |

  Q9 (aliases in the record linker) shrinks the last row before #1373 lands: a ticket titled "Retry failed payments" links to billing through the alias "payments".
- **`concept=` and an anchor in another pin.** The filter wins: results are billing's only, the anchor's lens is cut to billing, and the answer notes `anchor concept:auth is outside concept billing, so its lens shows only billing's part`. No error.
- **Aliases respect visibility.** Alias anchoring (`Resolve`, `FromText`) and the hint below consider only pins that apply to a visible repo, like `concept=`.
- **A hint without `concept=`.** When a text question anchors to a pin through an alias and `concept=` is unset, the answer notes `anchored on concept:billing (alias "payments"); add concept=billing to see only billing`.
- **Sessions** read pins from the approved profile only (that is what `ContextScopes` maps). A draft map is human-only today (MCP never reads drafts, `ContextTools.cs:13`), and this keeps it so.

### 3.3 The pin leg in fusion (G2)

- **The anchor's pin.** `PinScope.PinOf(anchor)`: the anchor is a pin, or a node `HoldsNode` for exactly one pin. An anchor in no pin, a text question anchored to several pins, or a query with `concept=` set (every result is already in the pin) gets no leg.
- **The leg, after RRF.** `RankFusion.Fuse` gains an overload taking key-only legs, `Fuse(answers, IReadOnlyList<RankedLeg> legs)`, `RankedLeg(SourceId Source, IReadOnlyList<RecordKey> Keys)`. `PinLeg.Of(fused, scope)` (pure, `Aw.Context.Core/Ranking/PinLeg.cs`) takes the plain fusion's output, keeps the items inside the pin in their fused order, and the overload adds `1/(K + r)` for the r-th of them. No synthetic hits: `FusedItem.Hits` is unchanged, and `Why` gets `rrf:pin#r`, so `context explain` shows why an item rose. Ordering by fused score, not by raw `SourceHit.Rank`, avoids the ties sub-queries make (many hits share rank 1).
- **Strength.** A fixed `1/(K + r)`: the top in-pin item gains as much as a rank-1 hit from one more source. No weight knob until the backtest asks for one.
- **Determinism and safety.** The leg is a pure function of the fused order and keys; ties stay ordinal by key; `RankFusionTests`' cases are unchanged with the leg off. The leg only reorders items that already passed every leg's scrub, audience mask and deadline; a degraded source contributes nothing to it.
- **Switch.** `context.ranker.pinLeg: on | off` (default off until Q6). It touches `RankerSection` and `RankerRules`, `RankerPlan.For`, the profile doc and `ProfileDiff`; the backtest arm `ranker-pin` touches `Arm`, `Arms.Ranker`, `Arms.Name`, `Arms.PendingStage` and the report writers. `context explain` always says whether the leg ran: `pin leg: concept:billing` when it did, otherwise the reason (`pin leg: off (context.ranker.pinLeg)`, `pin leg: anchor in no pin`, `pin leg: anchor in two pins`, `pin leg: not used under concept=`).

**Worked example.** Query "how are payments refunded": the word "payments" is an alias of billing, so the question anchors on `concept:billing` (§3.4). Two legs, repo docs and the record store's lexical leg. ENG-482 is in billing because the intent overlay links it to `feature:billing.refunds` (a v1-covered record, §3.2):

| Item | in billing | docs leg | lexical leg | plain RRF | pin leg | with leg |
|---|---|---|---|---|---|---|
| `notify/docs/refund-emails.md` | no | #1 | #1 | 1/61 + 1/61 = 0.03279 | none | 0.03279 |
| `billing/docs/refunds.md` | yes | #2 | #3 | 1/62 + 1/63 = 0.03200 | #1: 1/61 | 0.04840 |
| `linear:ENG-482` "Refund partial captures" | yes | none | #2 | 1/62 = 0.01613 | #2: 1/62 | 0.03226 |

Plain RRF puts the notify doc first. With the leg, the billing doc is first; ENG-482 stays third but closes most of the gap to the notify doc (0.03226 vs 0.03279), which stays in the answer.

### 3.4 Aliases (G3)

The app's sheet (§3.6) writes this; the YAML is the power path, for scripts and for the keys the sheet shows read-only.

```yaml
index:
  concepts:
    - id: billing
      name: Billing
      paths: ["packages/api/src/services/billing/**"]
      aliases: ["payments", "invoicing", "ledger"]
```

- **Shape.** `ConceptPin` gains `Aliases` as an `init` property with a `WithAliases(..)` method, like its `Declaring(..)` (`ConceptPin.cs`), so its constructor and every existing call stay as they are; `ConceptSettings` (`Aw.Sindri.Core/Profile/ConceptSettings.cs:15`, unmapped members refused) gains `aliases`; the three copy sites (`MapSetupReader.cs:69`, `ContextScopes.cs:54`, `ContextEngineChecks.cs:56`) change in one commit. `PinIds.Identity` includes them. `ProfileDiff.IndexConcepts` (`ProfileDiff.Index.cs:41-44`) shows a change. `MapRuleset.Pin` (`MapRuleset.cs:44`) gains no aliases and drops `Summary` (below). ### 3.7 The rebuild after an approval (G6)

- **No new trigger.** The built-in `context-map-refresh` service already queues `RefreshContextMap` within a minute when the approved pins change the ruleset hash (§1). This spec adds none; a second trigger would race it. An alias-only edit leaves the hash alone and queues `RelinkPinAliases` instead (§3.4).
- **When the service won't start a build.** `RulesChanged` is false while a publish hold is set (`ContextMapRefreshService.cs:186-187`), `MainMoveDecision.Decide` does nothing when no repo is on its default branch (`MainMoveDecision.cs:36`), and it waits out its backoff after failures (`:41`). The card says which, rather than promising a minute.
- **No map yet.** A pin approved on a box with no built map waits for the first build, which setup owns (setup-once spec); the card line is the first-build line setup already shows.
- **A pin with no card yet.** New pin, Add several's `New` rows and a pin a session wrote have no concept node until the rebuild lands, and a Pin this card's id can differ from the pin's (`PinIds` derives it from the name). So the layer builds a **waiting card** for each `index.concepts` entry of the live profile that the current map has no `concept:<id>` node for, at the head of the pinned cards, from the profile entry (name, definition, words) and the §3.7 lines; a Pin this card it came from is hidden while it waits. Its mark is `Set by a person` when it was written in the app or at a terminal and `Written by a script or agent` otherwise (the `pin_writes` view). It sits where the real card will (pinned cards in profile order), so the swap doesn't move it. The rebuild replaces it with the real card under the same automation id (`PinCard.<id>`); focus on the old card moves to the new one's button, and the live region is the layer's one status line, not the card, so `the map is ready` is spoken across the swap.
- **What the card shows**: up to three lines. The first is the first state that applies, prefixed by what was done: `Pinned ·` for a new pin, `Edited ·` for an edit, `Unpinned ·` for a removal (the table shows `Pinned ·`). Then the first problem line (§3.8: gone features, claimed twice, nothing matches) when there is one, then the what-moved line when the last refresh moved something; with neither, the coverage line.

  | When | Line |
  |---|---|
  | written, not approved (another change waits, or an approve was refused) | `Pinned, not approved yet` / `Other changes are waiting, so this needs your review.` with **Review and approve** |
  | approved, but a held map blocks the build | `Pinned · the rebuild waits until you've looked at the held map` with **Open review** |
  | approved, but no repo is on its default branch | `Pinned · the rebuild waits until a repo is back on its main branch` |
  | approved, in the backoff after failed refreshes | `Pinned · the last refreshes failed; the next try is at 14:05` with **Try again** |
  | approved, none of the three above, the refresh not started yet (the service's next tick, up to a minute) | `Pinned · the map rebuild starts within a minute` |
  | the refresh is running | `Pinned · rebuilding the map: <the job's latest progress line>` (`extracting 4,200 of 9,111 files`, `resolving calls`, `cleaning up`) |
  | the relink is running | `Pinned · linking records to its words` |
  | the refresh failed | `Pinned · Couldn't rebuild the map with this pin (SND-…). Try again.` with a **Try again** button (queues `RefreshContextMap`; while a failed job's key is still held it waits for the backoff instead of a second job) |
  | the new map is held by the publish decision | `Pinned · the new map is waiting for your look` with **Open review** (the Context page's existing hold view) |
  | otherwise | the problem and what-moved lines alone, or the coverage line |

### 3.8 What the concept layer shows (G7)

- **Owner's vs suggested.** Pinned cards keep `Set by a person` and come first, in profile order. Derived cards read `Suggested` and sort after them. A suggestion never changes a pin: the build's merge-based grouping only fills what pins leave (`ConceptPlan.Pinned`), and a derived concept that would take a pin's name gets a different id (`PinIds`).
- **Coverage.** A pinned card's size line as today (`4 features · 3 records · 2 decisions · 40 code files`). Below it, when they apply: `2 of its features are gone from the map` (listed keys that no longer exist, a rename in the code; fix: Edit pin), and for a pin nothing matches yet, `Nothing in the map matches this yet. Add features or words with Edit pin.` The card stays, honestly empty; owner input is never dropped for lack of evidence.
- **In no pin.** The layer's head line: `You've pinned 120 of 300 features and 410 of 2,300 records. The rest are in suggestions or in no concept.`; with no pins, `No pins yet. Press Pin this on a concept to make it yours.`
- **Claimed twice.** When a feature is listed by two pins (or matched by one's `features` and another's `paths`, round 3's T2), the second pin's card says `3 features are also listed in Billing. Billing keeps them because it is listed first.`, with Edit pin as the fix.
- **What moved.** After a refresh or relink lands, each pinned card shows what changed in it: features from the previous map version's `belongs-to` edges into the concept vs the new one's, and records from `RelinkPinAliases`, not the refresh (the refresh links nothing), which records the pin's link count before and after in its finish payload (Q9). Until that run ends the line says `+4 features; records linking…`. Then `+4 features, 3 more records linked here` (the net new links, the same thing the sheet's per-word count estimates); when features left, `−2 features (now in Notify)`, naming at most two places. It is stored with the job, so it stays across app restarts, and is replaced on the next refresh.
- **Survives rebuilds and publish.** Pins live in the profile, so a rebuild, a publish or an import never drops them; the ids are stable through `PinIds` over the mapped repos; overrides keyed on `concept:<id>` keep applying; `alias` links are kept by the link store across rebuilds like every other link. Tested in §4.

## 7. Security

The pin filter only narrows: it runs after repo scope, the audience mask and deny globs, never instead of them, and the pin leg reorders only results that passed all three. The empty-answer counts and the unknown-pin suggestions use only what the caller may see (§3.1, §3.2). Aliases are owner profile input, validated at approval (§3.4). The app's pin writes go through the versioned profile write and the owner's approval; the job only writes, and the approve is the existing Protected `ApproveProfile` called by the app with the hash the write returned, and, while pin changes wait, `ApproveProfile` needs the app or a caller at a terminal (`SND-AUTH-002` otherwise, tested through the real caller-header chain with a readable token and no TTY); without that check a lane could pin and approve in two commands, since Protected lets an owner-started session through and its CLI calls as a human once it reads the start token (`Authorization.cs:28`, `CallerHeaders.cs:34-46`, q93). It guards honest mistakes, not a lane that fakes a TTY. A hash that moved under it is refused as stale (`SND-PROFILE-003`). Name, summary and aliases are fenced as untrusted text wherever they render: the sheet, the cards, the review diff, the glossary, `context_concepts`, the anchor line and `context explain`. Aliases pre-filled from record terms show their record count, and one over 200 records starts unticked, so one click can't quietly re-home half the records. `context.pin.written` records the caller kind and terminal flag, and the review diff shows how each pin was written (`written without a terminal (a script or an agent session)`, or `changed in the file` for a hand edit), with each alias's new-link count. `Within` is not exposed to callers. Sessions read the approved profile's pins only.
