# PR 9: Remaining v1 blocks and loop guards

## Summary
Nine blocks, each a typed C# module with its config record, declared outputs, example and tests, registered in the block
registry from PR 5/6. Parking blocks (`wait`, `ask_owner`) are Temporal waits, not polling. `for_each` must not blow
Temporal history on hundreds of items (risk 4 in the design): it runs items in batches as child workflows of a fixed
size and measures it. Loop guards: a run cannot start its own workflow, `run_workflow` and `workflow_call` stop at
depth 3, and every write a launched session makes carries `session:<id>` and its run.
Rollback: revert.

## Graph context
- `CreateItemService.cs:24` is used by `sindri item add`, the app's New item form and `Features/Items`; the block reuses it
  without changing its request, so `By` and aliasing behave the same.
- The Needs-you page (Features/GetNeedsYou) renders rows by kind; `Question` needs its own row words and UI action
  (PR 17 adds the answer box; until then `sindri answer` and the MCP tool are the way).
- `workflow_seen` readers/writers: only OnlyNewBlock; purged with the workflow's resources (PR 14 treats it as state, not a resource).
- Temporal limits: history events per workflow (51,200) and in-flight activities; child batching keeps the parent small.
  `Aw.Sindri.Engine.Tests` has the time-skipping server (binaries-lock `temporal-test-server`).
- Loop guards read the trigger payload (`callDepth`, `parentRun`) and the caller's launch (PR 7) for the self-start check.
