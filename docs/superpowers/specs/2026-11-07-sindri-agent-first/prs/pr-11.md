# PR 11: Poll triggers, cursors and catch-up

## Summary
Inbound events are polled (owner decision D6, no webhook, no tunnel). A built-in service wakes every 30 s, picks the
connections whose interval (default 2 min, per connection) is due, and for each **event kind** that any active `poll`
node needs makes one provider call, then filters the returned events per trigger locally (this is how many triggers on one
connection cost one poll, risk 3). A cursor per (connection, event kind) records the last `updatedAt`, event id or page
token and is saved only after the runs for those events started. Every event carries a delivery id; the run occurrence is
that id, so a catch-up that overlaps a regular poll cannot start a second run (PR 6's duplicate-id refusal).
Catch-up runs on control-plane start and on wake. Rate limits: `Retry-After` honored, exponential backoff on 429 and 5xx.
Events in v1: GitHub (PR opened, merged, review requested; issue opened, labelled; push to a branch), Linear (issue created,
state changed, labelled; comment added), Slack (message in a named channel matching a filter; mention of the owner), Google
(calendar event starting within N minutes). Spotify has none. The done check uses one GitHub and one Linear event.
Rollback: revert.

Wake has no signal in the code today (a grep for wake/power finds nothing outside the recipe wake). Detection is the gap
between the monotonic clock (does not advance in sleep on macOS) and the wall clock, checked every scheduler tick.

## Graph context
- `SchedulerHost` (Host/Server/SchedulerHost.cs:25) runs `IScheduledService`s; cursors and last runs are in the ledger db;
  `ServiceSchedule.FirstSlot` already means "one catch-up run, never a burst" for services.
- Readers of cursors: only the poll service and `connection_get`. Writers: only the poll service.
- Occurrence ids come from provider event ids; they are stored in `workflow_run.id`, which is the idempotency key.
- A cursor must never advance past an event whose run failed to start (e.g. concurrency skip is a logged start, not a
  failure; a Temporal outage is a failure and keeps the cursor).
- Dependent PRs: PR 12 reuses the same loop for inbox offers; PR 17 shows cursor and trigger status.
