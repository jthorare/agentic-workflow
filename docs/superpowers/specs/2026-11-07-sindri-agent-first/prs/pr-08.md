# PR 8: MCP build tools, `sindri wf` and workflow docs

## Summary
Everything the app will do, an agent can do first (G1, G8). Fourteen tools on `/sindri/mcp`, the same slices behind HTTP
routes and `sindri wf ...` verbs (the CLI is a client of the control plane, as `item add` and `queue` are). Editing is by
small ops against a `baseRevision`, so two agents or an agent and the owner conflict visibly instead of overwriting. The
docs are embedded in the binary and searched by `workflow_docs`; every block page has a full example spec that the test
suite runs. The Part 2 acceptance test (sentence in, running workflow out) is a scripted MCP client over a fixture repo
pair, plus the owner's own run with a real Claude Code session.
Rollback: revert.

Heads up from the code: today `/sindri/mcp` has 15 tools and only `sindri_request` and `sindri_job` write
(McpToolTable.cs:18). So "agents get every verb" over MCP is real work per area; this PR is the template the later
areas copy (connections PR 10, memory PR 13, toolkits PR 16).

## Graph context
- `McpToolTable.Call` dispatches by name to static `Call*` methods that resolve services from the request scope; the new
  tools follow `SindriTools.Actions.cs:22` (`CallJob`) and map `Result` errors with McpToolError.cs.
- Caller attribution: MCP calls arrive as session callers (X-Sindri-Repo header, launch header); `By` on every workflow
  event is `session:<id>` or owner (PR 2 made sure of that).
- Reuses: `IWorkflowStore` (PR 5), `GraphValidator` (PR 5), `GraphRunStarter` (PR 6).
- Loop guard lives here: `workflow_run` refuses when the caller session's launch belongs to a run of the same workflow
  (settled call 5); depth for `run_workflow` is PR 9.
- Readers of the docs: agents through `workflow_docs`, the app's help (PR 17).
