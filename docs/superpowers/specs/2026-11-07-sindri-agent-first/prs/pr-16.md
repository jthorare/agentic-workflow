# PR 16: Toolkit runtime

## Summary
Sindri builds a toolkit (`dotnet build -warnaserror` plus its tests, as a job under the heavy-job lock, NativeAOT publish
when the project allows it), records a source hash of the good build, and refuses to start a stale or unbuilt one. `start`
reads the toolkit's manifest (`--manifest`, PR 15), provisions its resources (PR 14), and runs the binary as a local
process inside the sandbox with only the declared resources and connections, talking MCP over stdio with
`ModelContextProtocol.Core`'s client. Its tools appear on `/sindri/mcp` and in graphs through the `call_tool` block.
Every call is logged (`toolkit_call`: tool, caller, capped scrubbed input and output, duration, error). A toolkit can be
paused (calls refused with a clear error, process kept) or switched off (process stopped).
Rollback: revert.

Two things the design under-sizes:
1. **The sandbox is built around agent launches.** `ISandbox.Plan` takes a `SandboxRequest` with `LaunchId`, `ItemId`,
   `AgentId`, a repo, a Step policy, hooks and canaries (SandboxRequest.cs:29), and `Wrap` wraps "the agent's argv"
   (ISandbox.cs:26-30); `BubblewrapSandbox` and `SeatbeltSandbox` depend on `ILaunchSecrets`. A plain process with a pipe
   needs a second request shape. That work should land first as its own PR (see summary).
2. **Tool names.** `<toolkit>.<tool>` has a dot; clients and the model API restrict tool names to letters, digits,
   `_` and `-` in many paths. Check with Claude Code and Codex first; the fallback is `<toolkit>__<tool>` (the spelling
   lives in one function, `ToolNames.For`).

## Graph context
- `ISandbox` implementers today: Bubblewrap, Seatbelt, `UnavailableSandbox` (Core/Sandbox/Plan), test fakes in Aw.Sindri.Testing;
  all must implement the new members. Callers of `ISandbox`: Launcher (Infrastructure/Launch/Launcher.Sandbox.cs:14), `ISandboxExec`.
- `McpToolTable` is static and read by `McpEndpoint.cs:31` (`AddMcpServer`) handlers; the change is one handler path.
- Toolkit tool results are untrusted text: fenced like other `/sindri/mcp` output (McpFencing.cs:13).
- Resources (PR 14) and connections (PR 10) are the only things a toolkit can touch; network egress = connection host groups only.
- A toolkit that writes a connection token to its output is caught by the same redaction pass as the call log.
- Heavy work: builds take a heavy slot (owner rule: one heavy job at a time); the builder tests run `Lane=integration` with a
  fake toolkit process, never a real `dotnet build` in the unit lane.
