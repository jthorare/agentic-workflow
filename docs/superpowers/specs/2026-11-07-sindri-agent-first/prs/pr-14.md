# PR 14: Resources

## Summary
`resources` on a workflow spec or on a node (and later `Needs(...)` on a toolkit) declares `database { name }`, `disk { size }`,
`sandbox { cpu?, memory, wall }` and `connection { name }`. Sindri provisions on `activate` (first manual run for a draft):
one SQLite file per database at `$AW_SINDRI_HOME/resources/<owner-kind>/<slug>/<name>.db`, one folder per disk with its
size checked before each run (an over-size disk fails the run with the numbers), sandbox limits applied to the session
and clamped by the box's own limits. Each resource's path reaches the block or agent by name. Archiving keeps the data;
`sindri resources purge <owner>` (or the MCP tool) deletes it. No other path touches a resource folder.
Rollback: revert.

## Graph context
- The sandbox plan is the only consumer of mounts and limits: `SandboxPlanner.cs:7` -> `PlanMounts.cs:7` (internal); adding a
  mount kind is a localized Core change, and goldens under Aw.Sindri.Tests/Golden/Sandbox change (new `State` mounts).
- `workflow_node_run` outputs (PR 6) are separate from resources; `workflow_seen` (PR 9) and `memory` (PR 13) are Sindri state,
  not resources, and are not purged by `resources purge`.
- Toolkits (PR 16) use the same `ResourcePlanner` and store; so the owner kind and path layout are fixed here.
- Disk meter cost: a bounded walk (file cap 100k, stops over limit) once per run, never inside the session.
- Readers of `resource` rows: MCP/CLI/app list (PR 18), doctor.
