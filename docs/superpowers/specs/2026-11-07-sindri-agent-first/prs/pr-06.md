# PR 6: GraphWorkflow on Temporal and the first blocks

## Summary
`GraphWorkflow` (new, in Aw.Sindri.Workflows beside the Temporal host PR 3 kept) walks the spec in topological order, ties
broken by spec order, one activity per block execution, waits as Temporal waits. Every node start, finish and failure is
mirrored into the ledger by the same local-activity pattern the old engine used (`RecipeWorkflow.Mirror.cs:14`, deleted in
PR 3). Run ids are `<workflow>@<revision>:<occurrence>` and double as the Temporal workflow id with a reject-duplicate
policy plus a primary-key row, so a re-delivered event or a catch-up overlap never starts twice. Cron triggers are driven by
a built-in scheduled service (like the services in `Core/Scheduling`), which already skips missed slots instead of
bursting (`ServiceSchedule.Advance`, `FirstSlot`: one catch-up run); the new service stores the last fired tick per
workflow and fires only the latest missed one. Blocks: `schedule`, `called` (replaces `manual`; `manual` stays an alias the validator accepts), `condition`, `notify`,
`prompt` (`run_agent` is PR 7). Part 2 (the block list of 2026-11-08-sindri-block-list.md): `IGraphBlockType` gains `title`
(the picker label) and `group`; merged blocks get their labels (Schedule, When called, If, Send notification, Prompt). Proof: a fixture spec run end to end from `sindri wf run`.
Rollback: revert; nothing outside the new files depends on it.

## Graph context
- Temporal SDK `Temporalio` 1.20.0 (Directory.Packages.props:94) is already pinned; the dev server and its worker are
  started by `sindri serve` (SindriWorkerHost.cs:17). `GraphWorkflow` adds a type to the same task queue (StepTaskQueue.cs:10).
- Readers of `workflow_run`: `sindri wf runs` (PR 8), MCP tools (PR 8), the projector (new RunsProjection), sweeps (PR 7).
- Replaces the deleted `RecipeWorkflow` as the only workflow type; `AgentStepActivities` (kept) is called from PR 7.
- Scheduler: SchedulerHost.cs:25 runs `IScheduledService`s on cadences from the profile `services` map; the new service is a
  built-in (not a profile entry) so a fresh profile still runs schedules. Wake: laptop sleep ends -> next tick sees the
  passed slot -> one run for the latest missed tick.
- The host lease (`HeldLease`) gates every write; the activities run in-process, so they hold the same lease.
- Risk: `for_each` history growth is PR 9's problem; nothing here loops.
