## Verdict: ITERATE

One HIGH (#1) drives the verdict. The desk runtime fixes pass-1's "no value moment", but it also becomes the only
runtime every phase uses, and revision 2's other rules make it a poor daily surface. Timeouts sized for agents park
the human's own desk work. Every Step entry sends a desk-task notification that shares the notification budget with
parks and escalations. `--needs-me` lists every open desk task, so the decision queue gets lost among routine work.
The MEDIUMs are definitional gaps that revision 2 introduced or left open: desk-as-fallback weakens W5 (#3); pin drift
on an upgrade strands in-flight instances (#4); `--record` can't bootstrap evals (#5); the bugfix fixture doesn't test
mode B (#6). Each is a short doc edit. No CRITICAL.

## Concerns

| # | Severity | Concern | Recommendation |
|---|----------|---------|----------------|
| 1 | HIGH | **The desk runtime is the only runtime, and the doc's rules make it noisy and self-parking.** (a) `workflow.step`'s timeouts are sized for agents: `checks` 30 m `then: retry`, `produce` 4 h, `verify` 1 h. Under W20 the human is the runtime. A lunch break re-runs `checks` (a new desk task, a new notification) and then parks it with `timeout`. (b) §6.2 sends `notify.desk` for "a new desk task", which is every Step entry: up to ~9 per `workflow.step` with revisions. These notifications share "the notification budget" with park and escalate notifications, so routine work can suppress the decisions the hook exists for. (c) `--needs-me` includes every open desk task, so it lists all running work, not what needs a decision. (d) The desk-task layout (§6.3) doesn't show the input facts (`fact:spec`), so the human has to look the spec up | State a desk rule in W20. While a desk task is open, a state timeout sends a reminder (desk task age) instead of `retry` or `park`. Or say that recipes run on the desk declare human-sized timeouts. P5's `dev-timeout` signal can use a wait state instead. Split notification classes: decisions (park, escalate, `takeoverIdle`) never share a budget with desk-task notices, and desk-task notices are batched or off by default. Split the list into `--needs-me` (decisions only) and `--desk` (open tasks), and make S1's banner count them separately. Add the input fact refs to the desk-task layout and to `GET …/instances` |
| 2 | MEDIUM | **The value moment is still manual, and a deterministic Step is self-reported.** `step.checks` ("Run the Step's deterministic checks") resolves to the desk, so `passed` is whatever the human types. Deterministic checks need no launcher, and pass 1 offered this exact option (an existing port such as `bugfix-state run-test`, `aw-packets validate` or `aw-readiness check`). `ILauncher` still has no phase, condition or owner (§7.2 "when it lands"). Pass-1 question 1 is unanswered | Register one non-desk runtime inside the phases: a `step.checks` runtime that runs a profile-declared check command and reports `passed` or `failed`, with `fact:findings` from its output (P4 or P6, M). Then `workflow.step` has one step the engine actually does. Add one line to §7.2 naming the condition under which `ILauncher` is planned, for example "the first worker recipe (A 17.28.6 step 4)" |
| 3 | MEDIUM | **Desk as a catch-all weakens W5's fail-closed rule.** W20 and §2 say "every Step id resolves to [desk] until a launcher-backed runtime is registered". So `SND-WF-010` for Steps can't happen today, and after `ILauncher` lands, one Step missing its launcher registration quietly becomes a human task instead of a fail-closed park. That is the honest misconfiguration W5 exists to catch. The test `Step_without_runtime_parks` (§10) is then untestable, or it contradicts W20 | Make the desk runtime an explicit choice: a profile entry (`steps.runtime: desk`) or a per-Step setting, recorded in `run.runtime` and shown in `status`. Once any launcher runtime is registered, a Step without its runtime parks with `SND-WF-010` as W5 says, unless that Step is explicitly set to desk |
| 4 | MEDIUM | **Pin drift on an upgrade or a host move has no defined outcome for in-flight instances.** W11 and `RCP-CAP-003` re-check pinned descriptor hashes at start and at dispatch. Any block `Version` bump, even a harmless one, makes every recipe that names the block unapproved. In-flight instances then get a dispatch refusal (`SND-RECIPE-006`), and the doc doesn't say what happens to the instance next. It most likely sits in its wait until a `retry` or `park` timeout with an unrelated reason. Re-approval is one typed challenge per recipe. The same thing happens when a handover lands on a host with a different build (§13 P7) | Say that a dispatch or start refusal for pin drift parks the instance with `spec-conflict`, naming the block and its old and new descriptor, and that the answer path is "re-approve, then answer to retry the effect". Add a `recipe list --stale` view (with `sindri doctor` warning about it) that lists recipes the current build made unapproved. Optionally, pin only the descriptor's semantic fields (inputs, outputs, outcomes, capabilities, parameters, rung), so that a version bump with no semantic change doesn't force re-approval |
| 5 | MEDIUM | **`recipe eval --record` can't produce a new recipe's first eval.** Approval needs eval files (P2 needs them to exist, P3 also runs them). `--record` needs a live instance, and starting one needs an approved hash (`RCP-CAP-003`). So `--record` helps only when re-approving a later version. A new recipe's first eval is still written by hand as JSONL, which was pass-1 #2's main point | Add `recipe eval --scaffold <file>`. It walks the validated graph and writes one case per path to each terminal, with scripted gate answers and the `expect` lines filled in, for the author to review. Or allow an unapproved recipe to run in a throwaway state directory with desk Steps only and effects suppressed, then record that run. Say which in §9.2 |
| 6 | MEDIUM | **The bugfix fixture proves the addendum's sketch, not the real machine.** §12 calls `workflow.bugfix` "the §17.28.1 example in long form". `bugfix-state` (`docs/csharp/bugfix.md`) has mode B, two candidates evaluated in parallel within one attempt, one judge verdict per candidate with a stuck-judge path (`--abandon-judge`), and `needs-human` after an escalation. Mode B is fan-out, which §3.9 puts in schema v2. So the fixture passes while the first worker recipe (A 17.28.6 step 4) may still need v2, and pass-1 question 2 is answered for a simpler machine than the one that exists | Write the fixture from `bugfix.md`'s rules, not the sketch. If mode B can't be expressed in v1, say so in §3.9 ("bugfix mode B needs v2 fan-out; v2 lands with A 17.28.6 step 3, before step 4"), or model mode B as two sequential children and record that compromise |
| 7 | LOW | **The `/new-block` deferral condition is met inside the plan, with no owner.** "Deferred until three real blocks exist": by P6 and P7, `gate.budget.available`, `effect.notify.desk` and `effect.claim.ref` are real, and so is the desk runtime | Name the owner: "after P7, before the first worker recipe", or "with the Judge/Evidence blocks PR" |
| 8 | LOW | **P1's fixture signal can't pass as worded.** "The bugfix and direction fixtures validate" while "without new blocks" and "no fixture code ships in the binary" (W24). The sketch's blocks (`gate.baseline.fails`, `skill.bugFixOrchestrator.*`, which also breaks the block-id grammar in §3.3) aren't in the binary catalog, so `sindri recipe validate` would report `RCP-BLOCK-001` | Say the fixtures validate in the unit lane against a test catalog of fake descriptors in `Aw.Sindri.Testing`. Rename the step ids to `step.bugfix.*` in the long form |
| 9 | LOW | **The adoption metrics leave out the two numbers that show whether the retention hook works.** §11 lists desk task age, parks by reason and escalations, but not park-to-answer latency or time from start to terminal outcome per recipe. §13 P8 says "nothing new is needed" | Add `park.answered` latency and an instance duration on the terminal transition to §11's metric list. Both can be derived from existing `workflow.transition` timestamps |
