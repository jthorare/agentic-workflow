# Product Review: Sindri application design epic (PR #170), cross-spec coherence

_Reviewed by `/productReview` on 2026-10-11 | Mode: growth_

Read as one plan: `docs/sindri/README.md` (the index, X1–X18), the API surface spec, the workflow engine spec (rev 5), and the context retrieval spec, all on `docs/sindri-app-epic`, checked against S1's contract (`origin/feat/sindri-s1-app-shell:docs/csharp/sindri.md`) and `deps.yaml`. Scope: coherence across the specs after X1–X18. Settled internals were not re-reviewed.

"Growth" here means growth for a single owner: Sindri getting used in more repos, providers and sessions, and the factory line taking over more of the work. It does not mean user acquisition.

## Verdict: RETHINK

The rule decides it: there are two HIGH concerns. **#1**: when a launched agent session finishes a Step, nothing lets it report the result, because a `session` caller may not run `CompleteStep` and MCP offers only queries and requests. `ILauncher` moved to API P10 as an interactive "open in Warp" and nothing else. That leaves the factory line's automated half with no owner, and that half is the plan's 10x lever. **#2**: the API spec reserves `SND-API-004` and `SND-API-005` for new meanings, but S1 already uses both codes with other meanings. RETHINK here does not mean the architecture is wrong. The three specs agree on almost everything that matters. It means the reconciliation needs one more pass (an X19+ batch) before the UI design spec is written against it. Most of the 12 MEDIUM concerns are text that X1–X18 changed in one spec and not in the others.

## Strengths

1. **One permission model actually landed in all three specs.** API §4 owns callers, action classes and `SND-AUTH-002`. WF §6.2 adopts it, retires `SND-WF-007` and `SND-RECIPE-004`, makes takeover `pause`, and CTX §3 and API §3.7 classify the context routes. The X2 owner decision ("the app is a full desk client, `protected` actions show the CLI to copy") reads the same way in API §4.2 and WF §6.2.
2. **One write path and one read model.** Engine commands sit behind API's chain (gate, audit, authorization), and gates never run in a handler (WF §5.3). One needs-you list (`GET /needs-you`, with `park` rows that carry the engine's action id), one item timeline (X16), one lock port (X13) and one MCP endpoint (X8). The UI therefore has one catalog (`GET /commands`) to render buttons from.
3. **The cross-spec table is itself the right tool.** X1–X18 name the disagreement, the answer and the sections changed, so this review could check each change. The build-order plan (X17) faces the reality of the stacked PRs #166–#169.
4. **Provider neutrality is a principle now, not an accident** (X15, X18). Model calls go through one port, and sessions go through one launcher with a target. That is what lets usage grow to Codex and Cursor without an interface change.

## Scope Suggestions

### Cut
- **CTX's `SND-CONTEXT-041` and its local confirmation prompt** (#6): the shared challenge already covers them.
- **WF's `workflow.request` event** (#8): `FileRequest` already exists.
- **"Attach to any live session" in API P10** (#15): attach only to the session Sindri launched until the collector spec exists.

### Keep
- **One MCP endpoint, registered per repo** (X8): it is the main growth lever and the privacy boundary between work and personal repos at once. Keep it per repo; reduce the activation friction (#14) instead.
- **`protected` actions copy the CLI in the UI** (X2): this keeps the approval tier a terminal act until passkeys exist, and the catalog's `cli-only` status makes it renderable.
- **The X17 sequence** (S1, then API P0–P2, then rebase S2 and S3, with S1b in draft): it's the right order. Make every spec's wave table say it (#3, #10).

### Add
- **X19 (launcher Step runtime)** with an owner, a phase and the result path for a session (#1).
- **An item-link event** (`item.linked`) and its owner (#11).
- **A WF route table** (#7) and **a unique-code test** across all Sindri error catalogues (#2).
- **What the UI design spec must settle** (the reserved slot), since these specs leave it open:
  1. The launch-target picker (Claude Code, Codex or Cursor; per item or the profile default), each target's failure states and `SND-LAUNCH-001` text, and what "attach" lists (#15).
  2. Desk-task completion forms: outcome choice from the descriptor's outcomes, required `--output` facts as file or text inputs (at most 1 MiB, sent as content), and the run token. That is `CompleteStep` from the app.
  3. How the app gets a nonce for every engine write, and what it shows on `SND-WF-009` or `SND-WF-002`.
  4. Rendering `protected` rows (`cli-only:typed-confirmation`): the copy button, what the copied text contains (the `answer --grant n` form with its address), and how the app notices the CLI finished it (the event stream).
  5. Start-workflow flow: a recipe picker over approved recipes, inputs (`--fact`), attempt handling (`--attempt next`), and what scoping shows before its recipe exists (#13).
  6. Needs-you grouping (decision, park, escalation, idle takeover, desk task, failure, profile) and the badge rule, plus the notification ownership chosen in #9.
  7. Whether context appears in the app at all: a query box, `degraded` sources, the map-review queue (protected, so copy the CLI), and `context sources status`. Today no spec puts any context surface in the UI.
  8. States everywhere: `asOf.rebuilding`, `asOf.stalled`, the 30 s stale rule, the `Sindri-Api-Version` mismatch, "Sindri isn't running", and the `recordedOnly` label before S2.
  9. Repo scope: the app is `human` and sees every repo, so it needs a repo filter and how work and personal repos are told apart on one screen.

## Key Questions for the Team
1. Who owns the launched-session Step runtime (#1): a separate `ILauncher`/runtime spec as WF §13 promised, or an engine phase after API P10? And how does a session's Step result enter the engine without making `CompleteStep` a session-callable command?
2. Until engine P6, should the app raise OS notifications for needs-you `pulse` rows (#9), or should API P4 own a minimal `notify.desk`?
3. Is the scoping recipe in this epic's build order at all (#13), or does the UI ship with "start workflow" limited to `workflow.item` at first?
4. Does `context query`, or the map-review queue, belong in the UI, or does context stay CLI and MCP only for v1?
