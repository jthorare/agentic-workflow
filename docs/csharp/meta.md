# Meta — `aw-meta`

`aw-meta` is the helper CLI the `/meta` skill drives a **meta orchestrator** through: the session that gates and merges
a team's PRs, relays between lane sessions and the owner, and keeps the box healthy. Its job is to make that role
impossible to fail by forgetting. Every inbound lane message is recorded and owes a reply, the Stop hook won't let the
session idle while one is owed, and the lane map, merge gate, owner queue, health check and running log are commands,
not habits.

It is a portable harness for any project. Everything team-specific (lanes, repo, gate scopes, merge order, known
flakes, kickoff prompts, log file) lives in a team config. It runs before the C# switch as an opt-in standalone
NativeAOT CLI (`./setup.sh --with-meta`; the meta itself is Claude Code only, lanes can run other agent CLIs and take part in its obligations, see [Launcher](#launcher) and [Non-Claude lanes](#non-claude-lanes); Linux and macOS, see [OS support](#os-support)) that keeps its state under `$AW_STATE_DIR/meta/` (per team: `teams/<team>/`, see [Named teams](#named-teams)) and
appends to the configured running log. Its gate and merge commands act on the team's checkout and PRs: `git fetch`, a
gate worktree registered in the repo, the configured gate steps, `gh pr merge`, and the removal of finished worktrees (`git worktree remove`, never forced; see "Worktree cleanup"). Sindri absorbs it later (see the
last section).

Source: `src/Meta` (full shape: `Core`, `Features`, `Infrastructure`, `Host`; NativeAOT binary `aw-meta`).
Tests: `tests/Aw.Meta.Tests` (rules, slices, contract bindings) and `tests/Aw.Meta.Testing` (fakes and contract bases).
AOT smoke: `bash src/Meta/aot-smoke/run.sh`. Shell side: `config/hooks/meta-stop-gate.sh`, `config/hooks/meta-outbox.sh` (Claude), `config/hooks/meta-lane-gate.sh`, `config/hooks/session-id-report.sh` (Codex, Cursor),
`scripts/meta-launch.sh`, `scripts/meta-lane.sh`, `scripts/install-meta.sh`; skill `skills/meta/SKILL.md`.

## Why the transcript

No Claude Code hook sees an inbound cross-session message, so `stop-check` reads them from the meta session's transcript
(Claude Code 2.1.300). A message delivered while the session is idle is a `type:"user"` record with
`origin.kind == "peer"` (`from`, `name`, `msg_id`, `body`). A message that arrives mid-turn is a `type:"attachment"`
record with `attachment.type == "queued_command"` and the same `attachment.origin`. Both are recorded once, keyed on
`msg_id` (else the attachment's `delivery_id`). `stop-check` reads from a stored byte offset, so each stop costs only
the new lines.

Sends are seen by the PostToolUse hook: `tool_input.to`, `tool_input.message`, and `msg_id` in the tool response.

## Obligations

An obligation is something the meta owes. They are derived on each `stop-check` from the recorded messages, sends,
merges and owner answers, not stored as state. A new lane map version and a merge open no obligation: lanes read both from the board (`board-line`, below).

| Kind | Opened by | Closed by |
|------|-----------|-----------|
| `reply` | every inbound lane message | a later send to that peer; `inbox-dismiss <id> --reason`; `inbox-defer <id> --until` (reopens when due) |
| `relay-owner` | `owner-answer` | a send of the `OWNER ANSWER` text to the asking lane |
| `rearm-watch` | a started watch whose heartbeat is older than two intervals, or no watch ever beat while mail waits (`no active coordinator consumer`; the command is `aw-meta watch --until-event` run with `run_in_background` on Claude, never `--until-mail`, which exits on its first poll while mail waits, and `aw-meta watch --until-mail --for 29m` in the foreground on Codex and Cursor). `status` calls a watch active while its last beat is at most two intervals old, the same threshold | `watch` running again |

`stop-check` exits 0 silently for any session that isn't the registered meta session (`role-set`), so the hook is safe
to install globally. Loop guard: a stop-check without `stop_hook_active` starts a new turn (it blocks and resets the count); each
continuation with `stop_hook_active` and the same open set counts one block, and after `AW_META_STOP_MAX` (default 3) of
them the next continuation is let through with a one-line warning instead of looping the session. Every turn gets the
full allowance again.

`/clear` in the meta pane gives it a new session id under the same `-n` name. `stop-check` and `outbox-record` treat a
session as the meta when its id is the registered one, or when the live session with that id in the sessions directory
(`AW_CLAUDE_SESSIONS_DIR`, `<pid>.json`) carries the registered name; the new id is then registered (as `role-set` would)
and the hook carries on.

## The ready message

A lane queues a pull request for merge by sending a message whose **first line** is `ready #<n> <sha>`: the pull request number and a commit of 7 to 40 hex digits (the head the lane means). "Ready" and the hex digits are case-insensitive, and the sha may be wrapped in a pair of backticks (both or neither). The words "not ready" and "follows" disqualify the message only when they are on that first line. aw-meta checks the shape, not the head: it has no head lookup where the queue is read, and `merge-check` already refuses a pull request whose head moved after the gate, so a stale sha can't merge. Nothing else queues a pull request: a status line that merely mentions a later ready ("...then ready #250 <sha>", "ready #264 follows once the re-review is clean"), a ready without a sha, or any message containing `not ready` or `follows` is an ordinary request. This changes behaviour only for false positives and for ready messages that omit the sha; lanes now add it (`ready #269 079c2541` and details below). The rule applies to messages synced after the upgrade; entries queued under the old rule stay until a merge, the watch seeing the pull request end, or `queue-drop` removes them. `queue-drop` takes the same view as `status`: a pull request with a recorded merge, or one in `watch.ended-prs`, has no entry to drop (`AW-META-018`, exit 2). Tell every lane the format in its kickoff prompt (`prompts/<lane>.md`): `ready #N <sha>` on the first line, details below; a bare `ready #N` is ignored.

## Commands

Every command takes `--json`. Exit 0 ok, 1 attention (read the output and act), 2 usage or tool error; an error is one
stderr line `AW-META-NNN: <reason>`. Every command but `team-init`, `team-list`, `team-migrate`, `role-*`, `health`, `stop-check`, `outbox-record` and the lane-side `lane-inbox`, `lane-stop-check` and `lane-reply` needs
the team config (`AW-META-002` otherwise); the hook commands must let any session through when no team is set up. Those that need no config still need a *selected* team when several exist (`role-*`, `health`: `AW-META-019`), because they read or write the team's `meta.db`; only `team-list` and `team-migrate` work with none, and the hooks pass through.
`stop-check` prints what is owed on stdout (the hook moves it to stderr for Claude Code).

## Events

aw-meta keeps one append-only event table, `meta_events` in `meta.db` (migration `0006_meta_events.sql`), read by a cursor the way
`sindri ledger --after N` reads the Sindri ledger. The commands that decide a fact write the event for it, on the edge only: once
when the fact starts, once when it ends, never while it stays the same. A failed append never fails the command. `heavy.wait.long`,
`job.*` and `box.health` come later (#3142, #3143).

```
aw-meta events [--after N] [--kind K] [--lane L] [--max N] [--json]
```

- `--after N`: only events with an id above N (default 0, the start).
- `--kind K`, `--lane L`: only that kind, only that lane.
- `--max N`: at most N events, oldest first (default 500).
- Text output is one line per event: `<id> <at> <kind> <lane|-> <fields json>`. Nothing is printed when there are no events.
- `--json` prints `{"events":[{"id","at","kind","lane","fields"}],"next":<n>,"oldest":<n>,"latest":<n>,"gap":<bool>}` (schema: `schemas/meta/events.schema.json`). `next` is the id of the last event returned, or the `--after` value when there are none, so a reader stores `next` and passes it back as `--after`. Ids only rise and are never reused.
- `oldest`, `latest` and `gap` are on every response, an empty one too. `latest` is the highest id ever assigned (0 when none), kept even after the 7-day retention empties the log. `oldest` is the lowest id still kept, or `latest + 1` when the log is empty. `gap` is true when `--after + 1` is below `oldest`: the retention dropped events the reader never saw. The reader then re-reads `aw-meta status --json` and sets its cursor to `latest`. A new reader does the same from the start: `status` first, then `--after <latest>`. Its first call at `--after 0` shows a gap as soon as anything was pruned, and that gap is not an error. Text output prints one warning line first on a gap: `events before #<oldest> were dropped (7-day retention): re-read status`.
- Exit 0 ok, 2 usage: `--after` or `--max` not a whole number, `--max` below 1 (`AW-META-001`), or a `--kind` that is not dotted lower-case (`AW-META-027`). The command never writes.

An event has an id, a time, a `kind`, an optional `lane` (null for a team-wide or box-wide event) and `fields`, one JSON object.
The kind is dotted lower-case with at least two parts (`obligation.opened`, `heavy.wait.long`). Appending refuses anything else, and
fields that are not one JSON object, with `AW-META-027`. The store accepts **any** well-formed kind, so a reader sees kinds a later
writer adds; the schema lists the known ones. Every append also deletes the events more than 7 days older than the new event
(`MetaEvent.Retention`), in the same transaction.

| Kind | Fields |
|------|--------|
| `obligation.opened` / `obligation.closed` | `id`, `from`, `lane` |
| `context.high` / `context.ok` | `lane`, `tokens_k`, `recycle` |
| `lane.down` / `lane.up` | `lane`, `reason` |
| `usage.limited` / `usage.ok` | `lane`, `provider`, `until` (optional) |

Who writes what:

- `obligation.opened`: `inbox-sync` and `stop-check`, for each new message that asks something (notices open nothing), and `lane-reply`, for a reply it stores (id `lane:<lane>:<n>`). `id` is the message id. `from` is the sender's session name. `lane` is the same name without the `<team>-` prefix ("t1-api" is lane "api"). Owner-answer relays write no event.
- `obligation.closed`: `outbox-record` when the send answers a message, `inbox-dismiss` and `lane-recycle` (when it settles the lane's request). Same fields. It is written once, and only for a reply that was owed at that moment: dismissing an answered message, a notice or an already dismissed message writes nothing.

## Merge queue

`queue-gate` gates a train of ready pull requests in one round. The queue is the pull requests lanes said are ready, lowest number first, reordered only by the team's merge-order rules (a pull request waits behind the one the rules say merges before it).

- **Stacking.** Position 1 gates on `origin/main`. Position k gates in its own gate tree (`gates/<pr>/tree`) on the same pinned `origin/main` with the heads of positions 1..k-1 merged in order, then its own head. Nothing is pushed. The record keeps the stack (the pull request and head of every position under it) and the tested tree; `merge-check` accepts a stacked gate when the merge result of the current `origin/main` with the gated head has the tree the gate tested, which holds once the pull requests under it are merged, in any merge style.
- **Conflicts.** A head that conflicts with main or with the heads ahead of it is dropped from the round: `DROPPED #N: conflicts with #M at <sha>`. The later pull requests stack without it.
- **One slot pool.** Every step of every gate takes its heavy slots from one pool of `gate.parallelSteps` (default `heavy.cap`) slots; a free slot goes to the lowest train position, then the earliest step. Steps that are not heavy start as soon as they are free.
- **Failure.** When a step of position j fails, the gates above j that are still running are cancelled: each step's own process tree is killed by the PIDs aw-meta started (never by name). A cancelled gate is not recorded and its pull request stays queued for the next round. Gates above j that had already finished keep their record, but their stack holds j, which is not merged, so `merge-check` refuses them until a new train is run.
- **Status.** The train is kept in the key-value store (`train.state`) and `status` prints it: position, PR, base, state (`GATING`, `PASS`, `FAIL`, `CANCELLED`, `DROPPED`, `SKIPPED`, `ERROR`). Drafts are `SKIPPED`.
- `gate-rerun <pr>` works on a train gate: it reruns in the tree the train built for that pull request.

## Resources and adaptation

The meta watches memory and disk and adapts, so a team never has to be told by hand. All thresholds live in `team.json`
(`resources`, `builders`, `heavy`) and have defaults; nothing is specific to one repo.

**Events** (`watch`, one line when the state flips, never repeated): `DISK LOW` / `DISK OK` (state-disk free space against
`resources.diskFloorGb`), `MEMORY LOW` / `MEMORY OK` (available memory (`MemAvailable` from `/proc/meminfo` on Linux, vm_stat on macOS) against `resources.memFloorGb` only; swap never counts, because a box can sit at full swap with memory to spare). A flip is reported only after two consecutive polls agree on it (the rule `mergeable`
already follows), so a host sitting at its floor does not flap LOW, OK, LOW and make the meta message every lane each time. The
last reported state is kept in the team's store (`watch.resources`), so a re-armed watch does not announce a standing LOW again.
`health` judges memory by the same rule (`ResourceRules.MemoryLow`), so the two never disagree. How each OS reads these figures is under [OS support](#os-support).

**Gate priority and the reservation.** The heavy-job wrapper (`AW_HEAVY` or `$AW_STATE_DIR/bin-r1b/heavy`) shares a
box-wide number of slots between every expensive job. aw-meta stays inside its own state directory: it never writes the
wrapper's files (`heavy-meta-reserve`) and never reads its cap file. It speaks to the wrapper in one way and advises about
the other:

- `gate-run` and `gate-rerun` export `AW_HEAVY_PRIORITY=meta` to every command they start. A job with that priority may take any slot.
- aw-meta **computes** the reservation from the **merge-queue depth**: the pull requests lanes said are `ready` that are not yet
  merged, ended or dropped (what `status` lists as the merge queue), sized against the team's `heavy.cap` (default 3; keep it equal
  to the wrapper's own cap). The tier with the highest `minDepth` the depth reaches decides; with the defaults a depth of 3 or 4
  reserves 1 slot, 5 or 6 reserves 2, 7 or more reserves all but one (`"all"` is `heavy.cap`; every tier is held to `heavy.cap` less one so a lane job always keeps a slot), and 0 to 2 reserves none. It
  keeps the result, the depth behind it and the time in `heavy-reserve` in the team's state directory (`meta/teams/<team>/`, or
  `meta/` for a legacy team), and recomputes it wherever the queue changes: before each `gate-run`, after each `merge-run` (even
  when its log line fails), after each `queue-drop`, on every `watch` poll (a ready message, a drop, or a pull request seen
  merged or closed on GitHub) and on each `status`. Each change of the reservation is one `NOTE` line in the running log
  (`heavy reservation 0 -> 1 of 3 slots (merge queue depth 3); set it with meta-gate-reserve 3`; the argument is explained below). Computing it is advisory: if the
  file can't be written the gate or merge still runs. `heavy.reserve: false` makes aw-meta compute nothing.
- **Applying it is the meta's step**: `gate-run`, `status` and `health` print `heavy reservation: N of C slots (queue depth D) - set
  it with meta-gate-reserve A`, and the meta runs `meta-gate-reserve A` (the installed bash script, the only writer of the
  wrapper's file) before each gate. `A` is **not the queue depth**: the script has its own fixed tiers (depth 0-2 reserves 0, 3-4
  reserves 1, 5-6 reserves 2, 7 or more reserves its cap, and every tier is capped at the cap minus one so a lane job always keeps a slot), which differ from a team's custom `heavy.reserve` tiers or `heavy.cap`.
  aw-meta prints the argument that makes the script keep the slots it computed: 0 slots prints 0, 1 prints 3, 2 prints 5, and the cap less one
  (from 3) prints 7. A count in between has no argument; it prints 5 (the script keeps 2, never more than computed).
  `gate-run` computes before its steps and prints the line after them, so to apply the reservation before a gate read it from
  `status` (which recomputes it). The wrapper then gives every expensive job *without* the priority only the
  slots above the reservation, and does not count a wait for the reservation toward its timeout. A line ending `[stale: computed
  HH:MMZ; ...]` means nothing recomputed it for 30 minutes (no watch is running and no gate, merge, drop or status has run): run
  `status` and apply the new depth, or `meta-gate-reserve --clear` when the queue is empty.
- The reservation assumes every gate runs through `aw-meta gate-run`. A gate run by hand carries no priority and would wait behind
  the reservation it is meant to share; nothing running is ever pre-empted.

**Wait files.** `heavy` writes one file, `$AW_STATE_DIR/locks/heavy-wait/<pid>` (the wrapper's own pid), for each job that has to wait for a slot. The file is one JSON line with `pid`, `session`, `lock` (`session` or `box-wide`), `since` (UTC, when the first wait began), `argv` (raw) and `cwd`. `heavy` removes the file when the job takes its slot, on the lock timeout and when a signal ends it. A job that gets its slots at once writes none. SIGKILL leaves a file behind, so `aw-meta heavy --json` (#3142), the reader, skips a dead pid and redacts `argv`.

**Builders per lane.** `health` (and `status`, one line) advises how many builder subagents each lane should run now, from
`builders.maxPerLane` (none by default: nothing caps it but the host): it is reduced while free disk is under `resources.diskFloorGb + lanes x builders x builders.worktreeGb`
(lanes are the configured lanes but the meta lane), and is 1 while memory is low (the watch's `MEMORY LOW` rule: under `resources.memFloorGb` available; swap alone does not cut it); it is never
below 1. With no `maxPerLane` the number is what the disk holds (floor, then lanes x builders x worktree size) and the line reads `builders: no limit per lane` only when `worktreeGb` is 0. The line reads `builders: 4 per lane (disk 132 GB free, mem 12 GB available)`, or `builders: 2 per lane (disk below
floor+headroom)` / `builders: 1 per lane (memory low)` when something cuts it; `--json` carries `builders` (`perLane`,
`maxPerLane` (null when none is set), `diskFreeGb`, `memAvailableGb`, `limit`) and `heavy` (`cap`, `reserve`, `depth`, `computedAt`, `stale`; absent when no reservation was computed or `heavy.reserve` is false). Without a team config the defaults and one lane apply, and no reservation.

## Usage limits

When a Claude usage limit hits ("You've hit your session limit · resets 2:50am (America/Los_Angeles)", "You've hit your weekly limit · resets Oct 19, 10pm (America/Los_Angeles)", error type `rate_limit`), every lane and the meta's subagents stop mid-turn at once and sit idle until someone notices the window reset. The watch notices for them. Every poll `watch` runs the same look as `usage` and keeps what it announced under `usage.watch` (so a re-armed watch repeats nothing):

- `USAGE LIMITED <lane|meta> <session|weekly|other> resets <UTC time|unknown>`, once per stop (a stop is its kind and reset time; a different one is announced again), with a `NOTE` in the running log.
- `USAGE OK <lane|meta>` when `now >= resets + usage.resumeMarginSeconds`; when the reset is unknown, every `usage.probeMinutes` after the stop was first seen (and again that often while the stop is still the lane's last output, if the resume did not take).
- Also `USAGE OK <lane>` when a limited lane stops reading as limited by itself.
- With `usage.autoResume` (default true), a lane that is **idle** types the resume line: the lane's pane shows the stop as its last output (no `⏺` output or echoed prompt after it), an empty `❯` prompt (or Claude's `Try "..."` placeholder) and no `to interrupt` spinner. The line is `continue — the usage window has reset; resume where you stopped, including paused builders`; it goes in the way `lane-recycle` types: literally, Enter as a separate key press after 1.5 s, the pane read back, Enter pressed again while the line is still in the input box (up to 3 more times). A busy lane, a lane with a draft in its input box, a non-Claude lane whose pane is not at the stop, and a lane limited only in its transcript are never typed into; a lane found busy at `USAGE OK` is resumed at the first poll it is idle. A resume that cannot be verified prints `USAGE RESUME FAILED <lane>: <reason>` and is not retried before the next probe interval. Each resume is a `NOTE` in the running log.
- The meta is never typed into. When its own window is back the watch prints `USAGE OK meta` and `USAGE OK meta: resume your subagents (SendMessage them) and re-arm the watch`; the meta runs `aw-meta watch` in the background and is re-invoked by its output. Because the meta's watch is a process the meta started and the meta may itself be limited, the meta can also run `aw-meta usage-wait` in the background: its exit is the wake.

Team config `usage` (`{resumeMarginSeconds?, probeMinutes?, autoResume?}`, defaults 120, 15 and true; a margin below 0 or a probe below 1 is AW-META-003 at load).

## Usage across providers

A limit on one provider stops every lane on it. `aw-meta usage` shows where each lane runs and what its provider says is left. `aw-meta route` turns that into a list of lanes to move, using a table of equivalent models that the team config holds. The meta decides; nothing moves on its own.

**What each provider shows.**

| Provider | Usage figure | Where it comes from |
|----------|--------------|---------------------|
| Claude Code (`claude-code`) | The limit stop only: `ok` or `limited`, with kind and reset time. No share left. | The pane and transcript, as in "Usage limits" |
| Codex (`codex`) | Two windows, 5h and weekly: percent used and reset time. | The last `rate_limits` line in the lane's rollout file, `~/.codex/sessions/<y>/<m>/<d>/rollout-*-<session>.jsonl` (last 256 KB read). A window whose reset time has passed counts as unused. The figure is as old as the lane's last turn |
| Cursor (`cursor`), any added agent | None. `usage` says "<agent> shows no usage figure". The meta does not guess | |

**Codex limits in `watch`.** A Codex lane whose rollout says its limit is reached (`rate_limit_reached_type` set and the window it names, or any window when it names none, has not reset; or a window at 100% that has not reset). A reset time that is not in seconds (milliseconds, say) gives no figure for that window counts as limited everywhere a Claude lane at its stop does: `usage` shows it `limited` (source `codex rollout`), and `watch` prints `USAGE LIMITED <lane> session|weekly resets <UTC time>` once per crossing (`weekly` when the weekly window is full, else `session`; the reset time is the latest reset of the full windows) and `USAGE OK <lane>` once the window is back (its reset time plus `usage.resumeMarginSeconds`, or the next rollout line that shows room). The resume line is never typed into a Codex lane: there is no pane stop to find idle. A Codex lane with room left and no readable pane reads `ok`, not `unknown`.

A Codex lane with no session id yet, or no rollout file, shows the reason instead of a figure. The figure belongs to the account, not to the lane: two Codex lanes show the same windows.

**Config.** `routing` in `team.json`. Every key is optional.

| Key | Meaning |
|-----|---------|
| `models` | `{<agent id>: [<model>, ...]}`. The model names each agent offers. A model sits under one agent only. Example: `{"claude-code": ["opus", "sonnet", "haiku"], "codex": ["gpt-5.5", "gpt-5.4-mini"]}` |
| `equivalents` | `{<model>: <model>}`. Pairs of equal performance on two different providers. A pair reads both ways: `{"opus": "gpt-5.5"}` also moves `gpt-5.5` to `opus`. When several models point at one target, the reverse is not guessed; list it. Example: `{"opus": "gpt-5.5", "haiku": "gpt-5.4-mini"}`. Without any pair no switch is suggested |
| `lanes` | `{<lane>: {agent?, model?}}`. Where a lane is assigned to run. A lane with a `model` and no `agent` takes the agent that lists the model. `route --apply` writes here. Not the meta lane |
| `defaultModel` | The model a lane runs when `lanes` names none, for example `"opus"`. A lane on another provider takes this model's equivalent there. Without it a lane has no model and `route` says to set one |
| `switchWhenLimited` | Default `true`. A lane stopped at a limit should move |
| `minRemainingPct` | Default 10, 0 to 100. A lane whose provider shows less than this share left in its fullest window should move. 0 turns the check off. Providers that show no share never trigger it |

Load refuses (AW-META-003) a model listed under two agents, an agent key that is not an agent id, a pair that names an unlisted model or two models of one provider, a `defaultModel` or lane model that is not listed, a lane agent without an entry in `models`, a lane that is not in `lanes` of the team or is the meta lane, a lane routed to `claude-code` when `team.json` `agent` names another agent (a non-Claude meta has no `SendMessage`, so it could not reach the lane), and a `minRemainingPct` outside 0 to 100.

**When a lane is suggested.** Both must hold:

1. The lane is limited (limit stop, or Codex reports its limit reached) with `switchWhenLimited`, or its provider shows less than `minRemainingPct` left.
2. The model has an equivalent on another provider (never `claude-code` unless the meta runs `claude-code`: the reason says "the meta can't message a Claude lane"), and no other lane on that provider is limited or under the floor. When no lane on the target provider shows a reading, the suggestion ends with `; <agent> usage unknown`.

A lane already moved by `--apply` (its `routing.lanes` agent differs from the agent it still runs) is not suggested again; `route` says to relaunch it.

**Applying a move.** `aw-meta route --apply` writes `routing.lanes.<lane>` and starts nothing. The lane moves at its next start:

1. `aw-meta-launch` and `meta-lane.sh` read `routing.lanes.<lane>`: the lane starts on that agent (a model with no agent takes the agent that lists it in `models`) and with that model as the CLI's own flag right after the binary (`claude --model <m>`, `codex -m <m>`; Cursor has no model flag the launcher applies, so the model is not passed and `meta-lane.sh` says so on stderr). The model name goes to the CLI as written, so it must be a name that CLI accepts (for Codex, a `slug` in `~/.codex/models_cache.json`: `gpt-5.5`, `gpt-5.4`, `gpt-5.4-mini` on the box this was written on; `route` warns about a name that is not there). A model that starts with `-` is refused.
2. `aw-meta lane-recycle <lane> --digest <path>` on a Claude lane that `routing.lanes` assigns to another agent does not `/clear`. It types `/exit`, waits up to 60 s for the Claude to be gone, runs `aw-meta-launch --team <team> --lanes <lane> --no-open` (which restarts the exited pane on the routed agent; an `aw-meta-launch` that finds a Claude lane routed under a non-Claude meta refuses it) and logs a `NOTE` (`switched lane <l> from claude-code to <agent>`). The new agent starts from its kickoff prompt, not the digest: the response carries a warning with the `aw-meta lane-send` line that hands it the digest. `AW-META-022` when the Claude is still there after 60 s (nothing is launched); `AW-META-012` when the launcher fails. A lane that already runs a non-Claude agent is not recycled (as before): exit it and run `aw-meta-launch --lanes <lane>`.
3. A lane with no `routing.lanes` entry starts and recycles exactly as before.

**Not known.** Claude Code's share left; Cursor's usage; which model a running lane really uses (the model comes from the config, not from the session); Codex usage when the lane has not run a turn since the window rolled over.


## OS support

aw-meta runs on **Linux** and **macOS** (`scripts/install-meta.sh`, `./setup.sh --with-meta`; the host RID is whatever
`dotnet --info` reports: `linux-x64`, `linux-arm64`, `osx-arm64` or `osx-x64`; NativeAOT needs the platform's C toolchain, Xcode's
command line tools on macOS). On any other OS the installer exits 1 and says so; `setup.sh --with-meta` finishes the rest of setup, then exits non-zero with that message. Nothing is
skipped quietly, so a reinstall never leaves an old binary in place without a signal: the installer prints the installed
version, and the launcher warns when the binary is older than the Meta sources it runs from (below).

What reads the host differs; everything else (the SQLite stores, the team config, the CLI, gate and merge, the launcher) is the same
code. One internal function (`AddHostAdapters`, over a `HostPlatform`) picks the adapters for the process table, host resources, process liveness and process locations when the host composes (`AddMetaInfrastructure`); on an OS that is neither Linux nor macOS those four answer `AW-META-010` "unavailable on <OS>", and `lsof` and the tools below are never run. Nothing sniffs `/proc` at run time to pick one.

| Need | Linux | macOS |
|------|-------|-------|
| Memory total and available (`health`, `status`, `watch`'s `MEMORY LOW`) | `/proc/meminfo` (`MemAvailable`) | `sysctl -n hw.memsize`; available is the free, inactive and speculative pages of `vm_stat` times its page size |
| Swap used and total | `/proc/meminfo` | `sysctl -n vm.swapusage` |
| The process table (orphans, duplicate MCP servers, process groups, `health`'s counts) | `/proc/<pid>/stat` and `cmdline`; age from the process start time | `ps -axww -o pid=,ppid=,etime=,rss=,stat=,args=`; age from `etime`, so no time-zone or boot-time arithmetic. Zombies are left out on both |
| Is this pid running, and is it the process the file names (live sessions, heavy-lock holders; `IProcessLiveness`) | `/proc/<pid>/stat` start time against `/proc/uptime` | `ps -o etime= -p <pid>`: the start time is now (read before `ps` runs) minus the elapsed time. Many pids at once (`IProcessLiveness.Running`: the session list, the heavy-lock holders) go through one `ps -axo pid=,etime=` |
| What a process holds (worktree cleanup's idle test) | `/proc/<pid>/cwd` and `fd` | `lsof -w -n -F pcnR` (cwd, open files, executables, parent pid), run like the other tools. The scanning process and its ancestors (the shell that ran it) are marked as invokers, from lsof's parent field here and the `/proc` stat there, so a wrapper shell is never counted as a running gate |
| Termination (`health`'s orphan kill) | `kill -TERM` | `kill -TERM` |
| Disk free space, the heavy-job lock directories | the same on both | the same on both |

**`lane-recycle --detach` needs `setsid` or perl.** The waiter must leave the caller's process group, or it could die with the caller's shell. Linux has `setsid` (util-linux). Stock macOS has none, so the waiter starts under `/usr/bin/perl -MPOSIX`, which calls `POSIX::setsid()` and then execs the command. A failed `setsid` stops it before the command runs. With neither found, the command fails with `AW-META-010` "unavailable on <os>: setsid not found and no perl to call POSIX::setsid, so the waiter can't outlive this turn; recycle the meta by hand" and starts nothing.

**A reused pid is not the session.** A session record (`~/.claude/sessions/<pid>.json`) or a heavy-lock owner file names a pid, and the OS hands a
pid to a new process once the old one exits. Liveness therefore also compares the process's start time with the file's last write: a
process that started more than 2 seconds after the file was written (`ProcessStart.Tolerance`; `ps` and `/proc` count whole seconds) is
another process, and the session or lock is not live. The check is as good as the file's modified time: a record that is rewritten
later by something other than its own process would hide a reuse, and a start time that cannot be read (a failed `ps`) makes that
pid unknown, not dead: the session or lock is kept (one pid the host can't be asked about never fails the whole listing), and on Linux a `/proc/uptime` that is unreadable or earlier than the process's start (inconsistent clocks) is `AW-META-010`, never "not running" or a reused pid.

A macOS tool that cannot run, times out, exits non-zero (`lsof` exiting 1 with output is still read, since it could not read some files), prints 16 MiB or more, or prints something unreadable makes the figure unavailable: the command fails with
`AW-META-010` and a reason that starts "unavailable on macOS: <tool> ..." (for example `/usr/sbin/sysctl -n vm.swapusage exited 1: ...`; at most 300 characters of the tool's stderr are quoted). A number too large for a 64-bit integer in a tool's output is the same error, never an exception. Each tool runs by the absolute path macOS ships it at (`/usr/sbin/sysctl`, `/usr/bin/vm_stat`, `/bin/ps`, `/bin/kill`, `/usr/sbin/lsof`) so a PATH that something else controls can't substitute another program; a tool missing at its path fails to run, which is the `AW-META-010` above, never a lookup by bare name. It is
never replaced by a made-up value, and `health` does not guess from the rest. The tools' output is read up to 16 MiB (`ps` lists far
more than the command runner's default 64 KB tail; 16 MiB is about thirty times a busy machine's list, and output that reaches it is refused, because the runner keeps only the end: `AW-META-010` "... output over the cap"). Symlinked paths: git reports a worktree's physical path (`/private/var/...`),
while a team config may name it through a symlink (`/var/...`); put worktree roots in `worktrees.roots` by their physical path on
macOS.

**The launcher on macOS.** `scripts/meta-launch.sh`, `meta-lane.sh` and `launcher-lib.sh` run on macOS's bash 3.2 and BSD tools: no `flock`,
`exec {fd}>`, `BASHPID`, `mapfile`, associative arrays or `readlink -f`. The team start lock is the symlink `lane-sessions/.reported.lock`
(`ln -s` is atomic and records the owner pid in one step): a lock whose owner is dead is taken over, a live holder is waited for. macOS
`uuidgen` ids are lowercased. `scripts/tests/meta-launch.test.sh` runs on both OSes (it builds a one-line C `sleep` with `cc` on macOS: a
copy of the system `sleep` is killed there). It was run on macOS for this section (a throwaway team on a private tmux server, one Claude lane and
two lanes whose agent reports its session id, started one at a time); it has not run on a real Warp window here, and `aw-meta-launch` on
macOS opens Warp with `open warp://launch/<team>%20team`. `scripts/tests/meta-version.test.sh` covers the staleness check on both.

**OOM policy (#2931).** With systemd's default `DefaultOOMPolicy=stop`, one OOM kill inside a lane's tmux scope stops the whole scope, agent included. On Linux, when `systemctl --user show -p DefaultOOMPolicy --value` says `stop`, `scripts/install-meta.sh` writes `${XDG_CONFIG_HOME:-~/.config}/systemd/user.conf.d/10-oom-continue.conf` (`[Manager]` `DefaultOOMPolicy=continue`), leaves an identical file and every other drop-in alone, and prints the `systemctl --user daemon-reload` step without running it (the reload blocks `systemctl --user` for a minute or two). `scripts/meta-launch.sh` prints one stderr warning when the policy is known and not `continue`; `AW_META_NO_OOM_CHECK=1` skips both. Covered by `scripts/tests/oom-policy.test.sh`. `aw-meta health` prints the same warning as an `oom policy: ...` line before `HEALTH OK` / `HEALTH ATTENTION` (and `oomPolicy` in `--json`, left out when there is none). It runs `systemctl --user show -p DefaultOOMPolicy --value` with a 10 s timeout; a missing `systemctl`, a non-zero exit or a timeout gives no line, which covers macOS. The line never raises attention.

**Version and staleness.** `aw-meta version` is how a stale install shows. `scripts/install-meta.sh` stamps the publish with the tree's
`git rev-parse HEAD` (`<HEAD>-dirty` when a file under a build path has uncommitted or untracked changes) and a UTC time and prints `aw-meta commit <commit>, built ..., <os> <rid>` when it finishes (`... predates 'aw-meta
version'` for an older binary). `scripts/meta-launch.sh` runs `aw-meta version --json` at each launch and prints one stderr line, never
failing the launch, when the binary is older than the sources of this checkout: the last commit that touched a build path (`scripts/meta-build-paths.txt`, the one list: `src/Meta`, the Kernel, Redaction and Analyzers projects and the root build files; the installer, the staleness check and the NativeAOT smoke all read it) is not an ancestor of, or
equal to, the binary's commit (`git merge-base --is-ancestor`); an unstamped binary, one with no `version` command, and a commit this
checkout lacks, and a `-dirty` stamp warn too. After copying the binary the installer runs `aw-meta version --json` and fails (exit 1, "install didn't take") unless its commit is the one stamped, and fails when the publish produced no `aw-meta`. Docs-only commits after the binary do not. `AW_META_NO_STALE_CHECK=1` turns it off; `AW_META_BIN` names the
binary (default `$AW_STATE_DIR/bin/aw-meta`).

## Worktree cleanup

Worktrees pile up (a gate tree per pull request, a worktree per lane or builder). `aw-meta` removes the finished ones
itself, on **triggers**, never on a timer: work builds up over time, so how long a worktree has sat there is no reason to
remove it, and no rule reads a commit date or an age. The one time rule is a change trigger, not an age timer (rule 7).

**Triggers.** Each one sweeps only the worktrees that belong to the pull requests it concerns (their head branches and
their gate trees `gates/<pr>/tree` and `gates/<pr>/main-tree`), then logs one `NOTE` line to the running log ("worktrees
merge-run #7: removed 2 (...); kept 1 (path: reasons)") and keeps it as `worktrees.last`.

| Trigger | When |
|---------|------|
| `merge-run <pr>` | after a successful merge (also when it records a merge that already happened); the line is part of its output. A sweep that cannot run never fails the merge |
| the watch | when a poll sees a pull request merged or closed that is not yet in `watch.ended-prs`; one `WORKTREES watch #n: ...` line. A sweep that could not run (GitHub or git unreachable) leaves the pull request in `worktrees.pending-prs` and the next poll tries again |
| `worktree-sweep` | by hand, e.g. when a lane reports a builder done; also the way to retry a worktree that was kept for a reason that has since gone (a process exited, a commit was pushed) |

With `worktrees.enabled: false` the two automatic triggers only report ("would remove"); `worktree-sweep` still removes.

**The rules.** A worktree is `removable` only when all of these hold; any other is `kept` with every failing reason:

1. Finished: a worktree on a branch is removable when that branch's pull request is MERGED (a fetch precedes every sweep) or CLOSED, when nothing is unpushed in either case (a squash or rebase merge never puts the head in `origin/main`, so a MERGED pull request is ended by its GitHub state, not by ancestry, #2659). Such a tree is still kept when its HEAD has commits that the head GitHub recorded for the pull request lacks (`git rev-list --count <pr head>..HEAD` above 0: "HEAD <sha> is not PR #N's head <sha> (commits after it merged)"): a lane that commits and pushes on the branch after the merge or close has new work there, and nothing is unpushed. A tree whose HEAD is behind that head (it never pulled the last push, made from another tree or by GitHub's "update branch") holds no new work and may go. When git can't count (the recorded head is not a local object after the fetch), the tree is kept with the same reason. A branch with **no pull request** is kept by every sweep ("kept: no PR (pass --include-no-pr to remove)"; a fresh branch cut from main looks finished, and rules 4 and 7 only see the instant the sweep runs), unless `worktree-sweep --include-no-pr` is given; with that flag it is removable only when its HEAD is reachable from `origin/main`; a pushed branch whose HEAD is not in `origin/main` is kept ("unmerged branch, no PR (in-progress work)"), because a lane pushes its fix branch before it opens the pull request and its queued gates run in that tree (#2703). Nothing in rule 1 stops a fresh branch just cut from `origin/main` (the 2026-10-16 incident removed a live worktree on one): rule 4 (a process in it) and rule 7 (changed since the last sweep) are what protect it, together with rule 2. A branch whose pull request is still open is kept even when its head is merged. A detached worktree that is not a gate tree is kept ("detached, not a gate tree") unless the owning lane runs `worktree-sweep --path <dir> --done`: then it is removable when its HEAD is reachable from `origin/main` or every commit of it is on a remote branch, and every other rule still holds (clean beyond build output, no process in it, not locked, not the main or shared checkout, the change trigger and "no previous sweep" are waived because the lane said it is finished, as for `--discarded`, so `--done` works on a box where no full sweep has run yet). `--done` on a tree that is on a branch is kept ("--done: the tree is on a branch, not detached"); nothing is forced and no branch is deleted; the main checkout says "main checkout (never swept)". `worktree-sweep --pr <n>` and the triggers consider only the worktrees of pull requests, so they never remove a no-PR branch. The one exception is `worktree-sweep --path <dir> --discarded`: a tree that a `state.json` under `$AW_STATE_DIR/bugfix` names as an evaluated candidate that did not resolve the bug, at the same branch and commit as its HEAD, in a run that is finished or settled on another candidate, may go although its fix commit is unpushed or has no pull request; rule 7 (changed since the last sweep) and "no previous sweep" are waived for such a proven loser, so one `--path <dir> --discarded` run is enough, and a `--path` sweep never moves the last-sweep marker; every other rule still holds, a reason starting "--discarded:" says why a tree did not qualify, and branches are never deleted. A **finished bugfix run's trees** are the other exception, in every sweep (#2753): the run's red tree (the `checkout` of its `baseline` evidence, at `baseline.commit`) and each candidate tree (its `worktree`, on its `branch`, at its `commit`) whose HEAD is that recorded commit are finished work when the run's ticket is a GitHub issue that is CLOSED and one of its closing pull requests (`closedByPullRequestsReferences`, read with `gh api graphql` once per issue per sweep, since gh 2.45 has no `issue view --json` field for it) is MERGED. For such a tree "kept: no PR", "unmerged branch, no PR", unpushed commits and "detached, not a gate tree" don't apply; dirty, in use, locked, outside the roots, rule 7 (changed since the last sweep) and "no previous sweep" still keep it. A tree whose HEAD moved past the recorded commit, an open issue, a closing pull request that did not merge, a ticket that is not a GitHub issue (Linear, pasted text) and a failed `gh` read all keep it, as before; `--path <dir> --discarded` stays the way to free a losing candidate of those. `worktree-sweep --pr <n>` (the sweep merge-run starts) also takes the trees of the runs whose issue pull request n closed, so they go in the same step.
2. Clean: `git status --porcelain --untracked-files=all` is empty, ignoring only untracked files under a directory named like a build output (`worktrees.buildOutputs`, default `bin`, `obj`, `artifacts`, `node_modules`, `dist`). Any other untracked file, and any change to a tracked file, keeps it.
3. Nothing unpushed: every commit of its HEAD is reachable from a remote branch (`git rev-list HEAD --not --remotes` is empty); for a branch with no pull request, a HEAD in `origin/main` also counts.
4. Idle: no live process has its working directory or an open file inside it (`/proc/<pid>/cwd` and `fd` on Linux, `lsof` where there is no `/proc`). This covers a lane or builder still sitting in it. A scan that cannot run fails the sweep: nothing is removed.
5. Not protected: not the main worktree, not the team's shared checkout (`repo`), not locked (`git worktree lock`), its directory not missing.
6. Under an allowed root: `worktrees.roots` (default `~/repos/aw-wt`, `<repo>/.claude/worktrees` and the repo's worktree root from `AW_WORKTREE_ROOT` or `.agentic-workflow/worktrees.json`, when it is set; a root inside the repo is ignored here), plus the selected team's gate directory (`$AW_STATE_DIR/meta/teams/<team>/gates`, or the flat `meta/gates` on the legacy layout) always. After `team-migrate` the old flat `meta/gates` is no longer a root, so sweep it first (`worktree-sweep` with the legacy layout) or remove those throwaway gate trees by hand. The other roots (`worktrees.roots`) default to the same directories for every team: teams on one repo share them, so a team's sweep may remove another team's finished worktrees (rules 1 to 5 still apply); set `worktrees.roots` per team to keep them apart. A path outside every root, a root itself, or a sibling that shares a root's name prefix is kept.

7. Not changed since its cutoff: the directory, or any file in its top two levels (build output and `.git` left out), has a modification time later than the cutoff, a change trigger and not an age timer. A tree whose pull request merged or closed is compared with the later of the time it merged or closed (`mergedAt` or `closedAt` from `gh`) and the start of the last sweep of every worktree; the reason names the later one: "changed since PR #7 merged" / "changed since PR #7 closed", or "changed since the last full sweep (2026-11-08 11:43Z)", naming when that sweep started (a `--path` or `--pr` pass never moves the marker, so it can be well before the pass that prints it). When GitHub gives no end time the tree is kept ("PR #7 ended, but when could not be read (kept)"). Any other tree (only a full sweep with `--include-no-pr`, or `--path`, reaches one) is compared with that sweep's start alone. The start is `worktrees.sweep-start` in aw-meta state: a sweep records it after it removes, and only a sweep of every worktree moves it (`--pr`, `--path` and the merge-run and watch sweeps never do, though they read it); `--dry-run` and `worktree-list` record nothing. A removing `--path` run records its own start for that one tree (`worktrees.sweep-start.<path>`), and the next `--path` run on it compares with the later of that and the global one, so `--path` works on a box where no full sweep has run. With no recorded sweep a tree whose pull request ended is compared with its end time alone, while a branch with no pull request is kept ("no previous sweep to compare with"), so the first removing sweep only records its start. A tree whose files can't be read is kept. Gate trees are exempt (they are aw-meta's own and rule 1 for them already needs an ended pull request).

A **gate tree** (`gates/<pr>/tree`, `gates/<pr>/main-tree`) is aw-meta's own throwaway checkout, so rule 1 reads: its pull request is merged or closed (looked up on GitHub; unknown or open keeps it), and its HEAD is reachable from `origin/main` or is the merge commit the gate made itself (committer `aw-meta@localhost`); rule 3 does not apply. It is also kept while a `gate-run`, `gate-rerun` or `merge-run` of that pull request runs (found by command line, leaving out `aw-meta` itself and its parent shells).

**How it removes.** One worktree at a time, judged again just before its removal (a process may have started since), with
`git worktree remove <path>`: never forced and never a recursive delete, so git itself refuses a worktree that is not clean
(an untracked `obj/` that is not in `.gitignore`, for one); that refusal keeps the worktree and is reported (`git refused to
remove it: ...`, exit 1 for an explicit sweep). `git worktree prune` runs after any removal. **Branches are never deleted.**
A worktree git cannot read is kept with the reason.

## Named teams

Every team has its own config and state, so several meta sessions (one per team) run at once and never see each
other's messages, obligations, role, gates or lane sessions. A team name is `[a-z0-9][a-z0-9-]*` (it is a directory
name, a tmux socket name and the prefix of the session names).

**Selecting a team**, for every command: the global `--team <name>` option (it wins), else `AW_META_TEAM`. The
launcher exports `AW_META_TEAM` and `AW_META_DIR` (the team's state directory) into every lane it starts, the meta pane
included, so lane commands, the lane hooks and the Claude Stop and outbox hooks need nothing more; the two Claude hooks
also fall back to the tmux socket name (the launcher runs the team on `tmux -L <team>`) when the variable is unset,
and only for a team that exists on disk. `aw-meta-launch --team <name>` takes the same option.

**Resolution** (`TeamResolver`, mirrored by `scripts/meta-team-lib.sh`):

| Selected | On disk | Acts on |
|----------|---------|---------|
| `X` | `teams/X/` | `teams/X` |
| `X` | no `teams/X`, legacy `team.json` whose `team` is `X` | the legacy flat layout |
| `X` | neither | `teams/X` (`team-init` creates it; others report `AW-META-002`) |
| none | a legacy `team.json` | the legacy flat layout, exactly as before |
| none | one `teams/<t>/team.json` | `teams/<t>` |
| none | several | error: `AW-META-019`, exit 2, the teams listed; `stop-check` and `outbox-record` pass through (exit 0) so a hook never blocks an unrelated session; `team-list` and `team-migrate` need no team |
| none | none | the flat paths (no config: `AW-META-002`) |

A name that is not `[a-z0-9][a-z0-9-]*` is a usage error before anything is read or created (except `stop-check` and `outbox-record`, which pass through with exit 0 like they do on ambiguity). `AW_META_CONFIG` still
overrides the config file path (the state directory is still the team's), unless a team is selected and the file's `team` names another one: a lane's own `AW_META_CONFIG` is then ignored, so `aw-meta --team B` in team A's pane acts on B.

**Legacy layout.** `$AW_STATE_DIR/meta/team.json` with `meta.db`, `lane-sessions/` and `gates/` beside it keeps
working untouched. `team-migrate` moves it into `teams/<its team name>/` on request only.

## Launcher

`aw-meta-launch` reads `launcher.json` (`$AW_LAUNCHER_CONFIG`, else `$AW_STATE_DIR/launcher.json`; the contract is
`docs/csharp/sindri-launcher.md`, the design `docs/superpowers/specs/2026-10-15-sindri-session-launcher-design.md`, phase
SL-1). With no file the launcher is what it was apart from the team's own tmux socket (`-L <team>`, below): the Warp layout, Claude Code in every lane (a golden in
`scripts/tests/meta-launch.test.sh` pins the Warp YAML, every tmux command and every claude command line).

| Setting | Effect on `aw-meta-launch` |
|---|---|
| `viewer.kind: warp` (the default with no file) | The multi-pane Warp layout, written to `AW_WARP_LAUNCH_DIR` and opened |
| `viewer.kind: exec-template` | One window per lane (the lanes of this run, so `--lanes` opens only those) running `viewer.argv` with `{title}` and `{name}` = `<team>-<lane>`, `{cwd}` = the repo, `{cmd...}` = `tmux -L <team> attach -t =<team>-<lane>`; `--no-open` opens none, `--dry-run` prints each argv. A terminal that is not installed never stops the sessions: the attach command is printed |
| `viewer.kind: print` | Prints `tmux -L <team> attach -t =<team>-<lane>` per lane |
| `host` | Checked, not used: lanes always run in tmux |
| `meta.lanesAgent`, `meta.lanes.<lane>` | The catalog agent that runs the lane, when `team.json` has no `agent`. `lanesAgent` is the default for the lanes and never reaches the meta lane, which is Claude Code unless `meta.lanes.<metaLane>` names another agent. Every lane must resolve to the meta lane's agent (see "One agent per team" below). `team.json` `agent` replaces both fields for that team, including the meta lane. The catalog is `config/launcher/builtins.json` plus the file's `agents` |
| `agents.<id>` | `open`/`resume` argv templates (`{bin}`, `{cwd}`, `{name}`, `{seed}`, `{sessionId}`), `processName` (the pane check that restarts a lane whose agent exited) and `transcripts` (the glob that decides resume) |

**One agent per team.** Without `routing.lanes`, a team is all Claude Code or all Codex (or another single catalog agent): there is no mixed team and no
meta-to-lane delivery across agents. A lane that `team.json` `routing.lanes` names is the exception: `aw-meta-launch` skips it in the check below
and starts it on its routed agent (see "Usage across providers"), so a team that routes lanes runs mixed agents. Lanes with no entry still must agree with the meta lane. A routed lane may not be a Claude lane under a meta on another agent: the meta has no `SendMessage` to reach it, so `aw-meta-launch` refuses it (`the meta can't message a Claude lane`). Set that agent with `team.json` `agent` (every lane, including the meta lane). Without it,
`launcher.json` decides, and `lanesAgent` alone still does not reach the meta lane. Before it creates anything (the `--dry-run` too) `aw-meta-launch` resolves every lane of the
team config, not only those `--lanes` selects, and exits 1 when any differs from the meta lane's agent:
`meta-launch: a team runs one agent: the meta lane 'meta' runs claude-code, but api (codex), ui (codex) do not. Make them agree in
launcher.json ...`. An all-Claude team (no `launcher.json`) is unaffected. A Codex team is written with `meta.lanes.<metaLane>`
naming `codex` next to `meta.lanesAgent: codex`; a `launcher.json` that only set `lanesAgent` (Codex lanes under a Claude meta, which
worked before) is now refused with that message.

**Codex meta role.** A Codex meta reports its session id after it starts, so `meta-lane.sh` has no id to hand `role-set` on a fresh
start (it still does on a resume, where the id is known). `session-id-report.sh` registers the role instead: in the lane whose name is
the `metaLane` of the team config `AW_META_CONFIG` names (default `meta`), once it has written `lane-sessions/<lane>`, it runs
`aw-meta role-set --session <id> --name <team>-<lane>`. The hook, not the launcher's id watcher, because a later session of the meta
lane (a new id after `/new`) must take the role too, and the watcher has ended by then. A failing `role-set` is a `session-id-report`
fail-open cause (`role-set-exit-<n>`), and the id stays recorded. `meta-lane-gate.sh` passes the meta lane straight through: it runs
none of `lane-inbox`, `lane-reply` or `lane-stop-check` for it (the meta has no lane inbox; see [Codex or Cursor meta](#codex-or-cursor-meta)).

**Non-Claude lanes.** A lane on `codex`, `cursor` or an added agent starts and resumes, under a meta lane on the same agent (a Claude meta with Codex lanes is refused, see "One agent per team" above). `aw-meta-launch` prints
`lane <l>: <agent>, takes part in the obligations through its hooks (scripts/install-meta.sh installs them)` for an agent whose
catalog entry has `reportedId.hook: true`, and `lane <l>: <agent>, launch-only: no obligations` for one without a hook system. A
lane takes part once its hooks are installed and trusted (see [Non-Claude lanes](#non-claude-lanes)); a launch-only lane is not
messaged (`lane-send` stores the message and exits 1). An agent with `sessionId: reported`
chooses its own id: lanes of that kind start one at a time, each waiting up to `AW_META_ID_WAIT` seconds (30) for its id
(the `lane-sessions/<lane>` file a hook writes, else the single new file the catalog's `newestFile` glob finds that no other
lane has recorded; two candidates are refused and leave `<lane>.ambiguous`). "New" means a path that did not exist when
the lane started (a snapshot taken before the agent runs), not a recently modified one. The one-at-a-time start is the
lane's own: `meta-lane.sh` takes a team start lock (the symlink `lane-sessions/.reported.lock`, no `flock`: macOS has none) before the agent runs and releases it
when the id is recorded or refused, or after a timeout plus a grace window (`AW_META_ID_GRACE` seconds, default 10, during which the lane still watches for its late file and keeps it if it arrives, so the next lane cannot take it), so lanes created together (a Warp pane that creates its session, a
reboot, `--lanes`) are safe too. A lane that cannot start leaves `<lane>.failed` (the reason, the line the launcher prints as `lane <l> failed to start: ...`) and `<lane>.settled`, so the launcher reports it at once instead of waiting out the timeout. A lane refused by the launcher reader (a kickoff prompt starting with `-` once a
`launcher.json` exists) starts no agent and records no id.

**The team's own tmux socket.** `aw-meta-launch` runs every tmux call as `tmux -L <team>`, where `<team>` is `team.json`'s `team` (for example `-L sindri`): the has-session, new-session, respawn-pane and display-message calls, the `tmux -L <team> new -A` lines of the Warp layout, the printed attach lines and the exec-template viewer's attach argv. The team's server is therefore no longer tmux's default one, and a bare `tmux ls` or `tmux kill-server` in another terminal doesn't touch it. Attach by hand with `tmux -L sindri attach -t sindri-ideas`. The switch takes effect when the team is next relaunched: a server already running on the default socket is left alone (no migration, nothing kills it), but `aw-meta-launch` looks, read-only, for the lanes' `<team>-<lane>` sessions there before it creates anything and refuses (exit 1, naming them) while any exist, because starting them again would run a second agent on the same transcripts: stop the old team, then relaunch. `--allow-legacy` (or `AW_META_ALLOW_LEGACY=1`) skips the check; the meta session never passes it, because a second agent on the same transcripts is the harm the check prevents; `AW_META_LEGACY_TMUX_SOCKET` names a `-L` socket to check instead of the default one (tests). Tests never run tmux directly: they source `scripts/test-tmux.sh`, which unsets `TMUX`, uses a temp `TMUX_TMPDIR` and a `-L` socket of its own (`ttmux`), and refuses a socket outside its temp dir.

**Precedence** (environment, then the file, then the defaults): `AW_META_CLAUDE` replaces the `claude-code` entry's `bin`
and `AW_META_CLAUDE_ARGS` is inserted after `{bin}`; both stay for tests and are deprecated for users in favour of an
`"override": true` entry for `claude-code`. `AW_WARP_LAUNCH_DIR` is where the `warp` viewer writes its YAML (the file has no
such field). `AW_LAUNCHER_CONFIG` is passed on to every lane's tmux session.

**Lane variables.** Every lane's environment has `AW_SINDRI_CHILD=1`, `AW_META_TEAM`, `AW_META_LANE` and `AW_META_DIR` (the team's state directory, which the lane hooks write `lane-sessions/` under). `meta-lane.sh`
exports them (L-12, SL-1 section 10.2) instead of passing `-e` to `new-session`, so tmux's global environment, the Warp
layout and every tmux command stay as they are with no file, `-L <team>` aside (the owner's condition). The effect is the
same: a `sindri` run inside the lane is a session caller, whatever the agent. A shell left in the pane after the agent
exits still carries them, so run the human's `sindri` approvals from another terminal.

**Writing the file.** `aw-meta-launch --init-launcher [--viewer warp|print|<terminal id>] [--force] [--stdout]` detects the
terminal (no GUI session: `print`; Warp installed: `warp`; `$TERM_PROGRAM` naming a terminal in
`config/launcher/terminals.json`; else the first of those on PATH; else `print`) and writes `launcher.json` (0600, never over
an existing file without `--force`; exit 0 ok, 1 refused, 2 usage). The reader refuses unknown keys, unknown placeholders
and wrong JSON types with `SND-LAUNCH-011` before any session is created; `sindri launch show` is the full check.

## Non-Claude lanes

A lane on Codex, Cursor or an added agent has no `SendMessage` and no transcript the meta can read, so its obligations go through
aw-meta's own files (SL-1b). The shell half calls them from the CLI's hooks: `scripts/install-meta.sh --provider codex|cursor`
installs `config/hooks/session-id-report.sh` and `config/hooks/meta-lane-gate.sh` user-wide through the provider adapters, and
`scripts/meta-lane.sh` writes the `.agent` record and exports `AW_STATE_DIR` and `AW_META_CONFIG` into the lane's environment.

- **Install.** `install-meta.sh` takes any provider (the Claude-only check is gone) and publishes and links `aw-meta` and `aw-meta-launch` for each. Claude Code gets `meta-stop-gate.sh` and `meta-outbox.sh`, unchanged. Codex gets `session-id-report.sh` at SessionStart and `meta-lane-gate.sh` at UserPromptSubmit and Stop; Cursor gets `session-id-report.sh` and `meta-lane-gate.sh` at `sessionStart`, `meta-lane-gate.sh` at `postToolUse` and `stop`. The hook configs are `~/.codex/hooks.json` and `~/.cursor/hooks.json`, the scripts and adapters are staged in `$AW_STATE_DIR/hooks`. Codex records trust against each hook's hash, so every install prints "open `codex` and run `/hooks` to trust the `aw:*` hooks"; until then the lane shows "hooks never ran: trust them with /hooks in codex ..." in `health`. The hooks are user-wide, so both pass straight through (exit 0, no work) for every session that is not a lane: `meta-lane-gate.sh` unless `AW_META_TEAM` and `AW_META_LANE` are set, `session-id-report.sh` unless those or `AW_SINDRI_LAUNCH` are. Both skip `AW_JUDGE_CHILD` and run fail-open (`HOOK-FAILOPEN`, `meta-lane-gate` and `session-id-report` causes). The lane never installs aw-meta itself.
- **Session id.** `session-id-report.sh` writes the hook's `session_id` to `lane-sessions/<lane>` (and, for a Sindri launch, to `$AW_SINDRI_HOME/launches/<launchId>.session-id`), keyed on the variables the launcher set on that one session, so lanes started together record their own ids. `meta-lane.sh` waits for it as before and falls back to the newest-file glob only when the hook didn't fire.
- **Delivery and stop.** `meta-lane-gate.sh` also runs `board-line` next to `lane-inbox` (same events; its line follows the inbox text in one block; a failing `board-line` leaves the inbox alone, and the meta lane and Stop never run it). It runs `lane-inbox` at Codex's UserPromptSubmit (plain stdout is developer context) and at Cursor's `sessionStart` and `postToolUse` (`additional_context`). At Stop it takes the turn's last assistant text (`last_assistant_message`; the Cursor adapter reads it from the transcript), pipes the text after the last line that starts `REPLY TO META:` to `lane-reply --stdin`, then runs `lane-stop-check` (`--stop-hook-active` on a continuation). Only `lane-stop-check` exit 1 blocks (Codex: the stop is blocked with the reason; Cursor: `followup_message`, capped by `loop_limit`); exit 0, exit 2 and anything else pass. The hook runs outside the agent's sandbox, so a Codex lane in `workspace-write` never needs to write the state directory. A reply is recorded once: the hook keeps a checksum of the last recorded reply in `lane-sessions/<lane>.replied` and skips a Stop whose reply text matches it (a continuation, a turn with no new text, Cursor's transcript tail, the `afterAgentResponse` that already recorded it). Any delivery makes the same words recordable again: mail that `lane-inbox` prints clears the marker, and so does a `lane-stop-check` block that shows a new owed list (checksummed in `<lane>.owed`; the same list blocked again, as in the stop-cap loop, does not), which is how a Codex lane busy mid-turn gets mail. A relaunch (`meta-lane.sh`) and a new session (`session-id-report.sh`) clear both files. The Cursor adapter reads the last assistant text of the transcript, so a lane that answers a new message without any new text re-sends its previous reply: the hook cannot tell, and `health` does not flag it.
- **Only the lane's own agent acts.** A `codex exec` or `cursor-agent -p` that the lane's agent starts inherits the lane variables, and a Claude lane that runs one must not have it write the Claude lane's session id. `meta-lane.sh` exports `AW_META_LANE_PID` (its own pid), `AW_META_LANE_AGENT` (the catalog id) and `AW_META_LANE_PROC` (the agent's process name) in **every** lane, a Claude lane included (additive: nothing on the Claude path reads them). Both hooks pass straight through unless they run under the lane's own agent:
  - no `AW_META_LANE_PID` (not started by a lane script) or `AW_META_LANE_AGENT=claude-code` (a Claude lane's hooks are Claude's) means not a lane;
  - the lane's agent **root** is the ancestor of the hook whose parent is `AW_META_LANE_PID`, whatever it is called: a native binary (`lane script -> codex -> hook`) or the node wrapper of an npm install (`lane script -> node -> codex -> hook`);
  - a **nested instance** is a second stretch of ancestors named like the agent (`AW_META_LANE_PROC`, by command name or argv[0]) below the first, behind a tool process such as a shell (`codex exec` run from the agent's shell tool); it passes straight through, so it neither takes the lane's session id nor consumes its inbox nor blocks at Stop. Forks of one instance share its command line and count as one stretch;
  - no lane script among the ancestors passes through; a codex a human starts after the pane fell back to `exec bash -i` keeps the lane script's pid and counts as the lane's own; if `ps` can't answer, the hook acts.
- **Codex runs hooks under the lane, not in its shared daemon (#2286).** Codex 0.16x starts one app-server daemon per box and runs hooks and tools in it. The daemon keeps the environment and process ancestry of whoever started it first, so a second team's lane would run its hooks as the first team (`AW_META_TEAM`, `AW_META_LANE_PID` of another team) and `own_agent` rightly rejects them. `meta-lane.sh` therefore starts every Codex-derived catalog entry (the built-in `codex` and any alias that keeps its process name, `model: codex-flag`, `policy: codex-overrides`, or a binary named `codex`), fresh and resumed, with `--no-daemon` right after the binary (`codex --no-daemon resume <id>`). It first runs `<bin> --help` once (bounded by `AW_LAUNCHER_PROBE_SECONDS`, default 5) and adds the flag only when the output names it: an older Codex has none and would refuse to start, so it launches as before and `meta-lane.sh` says so on stderr. The result is recorded in `<lane>.agent` as `codex: true` and `noDaemon: true|false`; `health` then names the cause (`; if they are trusted, codex's shared daemon may be running them as another team (this lane started without --no-daemon...)`) instead of generic install advice, for an alias too. The `own_agent` ancestry check is unchanged, so a nested `codex exec` is still rejected. Proof with a fake daemon topology: `scripts/tests/meta-launch-codex-daemon.test.sh`.
- **Pane name.** `lane-send`'s guard compares `#{pane_current_command}` with the agent's `processName`, and tmux reports the foreground process group's leader. `meta-lane.sh` therefore runs a non-Claude agent under job control (`set -m`), so the agent leads its own group and the pane reads the agent, not `bash`; a Claude lane runs exactly as before. The name the pane shows is not always the catalog's: the npm install of Codex is a node wrapper that spawns the native binary, so the pane reads `node`. Once the agent leads the foreground group, `meta-lane.sh` reads the leader's name the way tmux does and records it as `processName` in the lane's `.agent` record (never a shell's name, which is what a downed lane's fallback shell shows), so the guard compares against what tmux shows. The lane's id watcher polls the lane script's pid and ends when the script is gone (the pane closed: the kernel hangs up the agent, and the watcher stops on its own), so it never holds the team start lock for a lane that is gone; no signal traps are involved.
- **Kickoff.** A non-Claude lane with hooks and a kickoff prompt file gets one extra paragraph at the end of it: end a turn that answers the meta with a `REPLY TO META:` line. The message `lane-inbox` shows says the same.

- **Lane identity** is `AW_META_TEAM` and `AW_META_LANE` and nothing else: no lane command on the lane side has a `--lane` flag.
- **Lane source.** The lane map and `health` see a non-Claude lane as `<team>-<lane>` when `lane-sessions/<lane>` holds a session id, `lane-sessions/<lane>.agent` names the agent, and the lane's tmux pane (`tmux display-message -p -t =<team>-<lane>:`) runs the agent's `processName`. With no `.agent` record nothing changes: a team of Claude lanes makes no tmux call and prints what it printed before.
- **State** is in `meta.db` (`lane_mail`, `lane_replies`, and the replies as ordinary `messages` rows) and the key-value store (`lane.<lane>.beat`, `.woke`, `.stop-fingerprint`, `.stop-count`, `.stop-cap`). A reply is an inbound message of the meta with id `lane:<lane>:<n>` from `<team>-<lane>`, so the meta's `stop-check` opens a `reply` obligation from it; the next `lane-send` to that lane closes it. Its fix text is `aw-meta lane-send --lane <lane> ...`, not `SendMessage`.
- **Wake.** `lane-send` types one fixed line into an idle lane only when all of: the lane is idle (its last hook was `lane-stop-check` and it hasn't been woken since), and its pane runs the agent's `processName` (a bare shell is "lane down"). An attached viewer no longer blocks it (the send says `woken (a viewer is attached)`). It sends `tmux send-keys -t =<team>-<lane>: -l '<line>'`, pauses 300 ms, then sends `Enter` (literal mode, exact session; the trailing colon is what lets tmux resolve the pane). The wake counts only when the lane answers: `lane-send` waits up to `AW_META_WAKE_CONFIRM_SECONDS` (default 10) for a hook beat newer than the wake, presses `Enter` once more if none came, and waits again. Only a confirmed beat records `.woke`; otherwise the send says `typed the wake line but no hook answered in <2N> s: ...` and the lane stays idle for the next send. Otherwise the message waits for the lane's next hook. Only a hook's call (one with `AW_META_HOOK`) writes `lane.<lane>.beat`; a hand-typed `lane-inbox` delivers the mail and records `lane.<lane>.cli` instead. `AW_TMUX` names the tmux program. Every call runs on the team's own socket, `tmux -L <team>` (the same server the launcher starts the lanes on); `AW_META_TMUX_SOCKET` names another socket instead (tests and proofs). With no team config and no override there is no socket to look on, so a lane probes as down. Every aw-meta test and the AOT smoke set `AW_TMUX` to a fail-closed stub, never the real tmux.
- **Stop gate.** `lane-stop-check` blocks a stop while the lane owes a reply. A check without `--stop-hook-active` starts a new turn (blocks, resets the count); each continuation with the same owed set counts one block; after `AW_META_STOP_MAX` (default 3) the next is let through with a warning, an incident in the running log and the mark `lane.<lane>.stop-cap`. Only exit 1 blocks; exit 2 (variables unset, a tool error) must pass.
- **Health.** `health` and `lanes` show, for non-Claude lanes only: `taking part`; `launch-only: no obligations` (the CLI has no hook support, so `.agent` says `hooks: false`); why the hooks are not verified, from the hook trace (`lane-sessions/<lane>.hook`, a trace older than the session id counts as none): `hooks never ran: ...` (no trace: Codex says to trust them with `/hooks`, Cursor to check `~/.cursor/hooks.json`), `hooks ran but skipped the lane: ...` (`not-own-agent`), `hooks ran but found no aw-meta binary ...`, `hooks ran but aw-meta <cmd> failed at <time>Z ...` and `hooks ran (<event> at <time>Z) but recorded no heartbeat`; `hooks not verified: only manual aw-meta runs seen (last <time>Z); <why>` when only hand-typed `aw-meta` calls (no `AW_META_HOOK`) were seen, which deliver mail but are not hook proof; `mail not delivered for <N> min: <why>` when the lane's oldest undelivered mail is older than `AW_META_UNDELIVERED_MINUTES` (default 5), ahead of `taking part`; `obligation not delivered (stop cap)`; `obligation not delivered (Cursor loop_limit)` (a Cursor lane blocked as many times as Cursor's default `loop_limit`, 5); `ambiguous session id`. A lane that needs attention makes `health` exit 1.
- **Migration 0003 is one-way.** The first time a build with this change opens `meta.db` it applies migration 0003 (`lane_mail`, `lane_replies`; additive, in a transaction, after copying the database to `meta.db.bak-v2`). From then on an `aw-meta` that doesn't know 0003 refuses the database with `AW-DATA-007`, so the installed binary and the database move together: install the new build before anything else opens the live `meta.db` (run proofs and `dotnet run` against a temp `AW_STATE_DIR`). To roll back, stop the team, restore `meta.db.bak-v2` over `meta.db` and reinstall the old binary; the lane mail written since is lost.
- **Cursor reply capture (`afterAgentResponse`).** Cursor's `stop` payload carries no assistant text, so `install-meta.sh` also installs `meta-lane-gate.sh` at `afterAgentResponse`. The Cursor adapter maps it to `AfterAgentResponse` with `last_assistant_message` = the event's `text` (no transcript read) and prints `{}` (Cursor ignores the output). The gate records the reply there (same `REPLY TO META:` extraction and `.replied` checksum as Stop) and never runs `lane-stop-check`; the Stop that follows skips the same text. The marker may carry markdown decoration: after optional leading whitespace and any of `>`, `-`, `*`, `#`, `_`, backtick, the line starts `REPLY TO META:`, and a `**`, `__` or backtick that closes the marker (`**REPLY TO META:** x`) is dropped from the reply. Mid-line text (`see REPLY TO META: x`) is not a reply.
- **Hook calls and the trace.** Every `aw-meta` call the gate makes carries `AW_META_HOOK=<event>` (`UserPromptSubmit`, `SessionStart`, `PostToolUse`, `Stop`, `AfterAgentResponse`), so a call typed by hand can be told from a hook's. Each run of `meta-lane-gate.sh` and `session-id-report.sh` in a lane also overwrites `lane-sessions/<lane>.hook` with one line, `<UTC ISO time> <hook-name> <event> <outcome>`. Outcomes: `ran`, `not-own-agent`, `aw-meta-missing` (gate only), `meta-lane`, `lane-inbox-failed`, `lane-reply-failed`, `lane-stop-check-failed`, and `reply-unmarked` (a Stop where `lane-stop-check` says the lane owes a reply and the last answer has no `REPLY TO META:` line; the block text then starts with a line telling the agent so). A failure outcome is not overwritten by a later `ran` of the same run. The write never fails the hook.

### Codex or Cursor meta

When the team's meta lane (the `metaLane` of the team config, `meta` by default) runs on Codex or Cursor, `meta-lane-gate.sh` gives it its mail instead of a lane inbox: at Codex's `UserPromptSubmit` it prints `aw-meta inbox --once` as plain text, at Cursor's `sessionStart` and `postToolUse` it prints the same text as `additionalContext`. `--once` keeps it silent on an empty inbox and shows each open message once, not on every prompt or tool call. It runs no `lane-inbox`, `lane-reply` or `lane-stop-check` for the meta lane, and its Stop passes. The trace outcome is `meta-lane`. So the meta sees new mail at each prompt. `--once` marks a message shown when the hook prints it, so after a `/clear` or a recycle a Codex or Cursor meta never gets that message from the hook again: its recycle step runs plain `aw-meta inbox` first (that, and the `watch --until-mail` INBOX line, list every open message whatever its `shown_at`).

Between turns nothing prompts it. It runs `aw-meta watch --until-mail --for <N>m` in the FOREGROUND. The watch returns as soon as mail is waiting, or at `--for` (default 29m, `--interval` default 120 s) if none comes. On the first poll that finds messages still owed a reply (the ones `aw-meta inbox` lists) it prints `INBOX <n> open message(s)` and exits 0; the meta then runs `aw-meta inbox` and handles it, and starts the next watch. Background watches do not work there, because Codex and Cursor only show background output when polled. Pick `<N>` as the longest the meta can sit without acting; a bad duration exits 2.

## Threat model

`aw-meta` guards against an honest orchestrator forgetting, not against a deliberately hostile one: the session can
always dismiss an obligation, and the loop guard lets a stuck stop through. The hooks fail open (`HOOK-FAILOPEN`,
`.agents/rules/hooks.md`): a missing or broken `aw-meta` never blocks a session. Inbound message bodies are lane text,
stored and printed but never executed. `health --kill-orphans` kills by pid only after the full rule matches; it never
matches a pattern against every process.
