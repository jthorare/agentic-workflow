    Chapter 1 · Overview

    Sindri grows Sindri.

    Sindri is a local, always-on harness that picks up work, sizes it, starts agent sessions with cited context, keeps them on track and ships them through a fixed recipe. It asks the human only when it has to. Named after the dwarf smith who forged Draupnir, the ring that multiplies itself.

    The human approves direction. Sindri does the finding, the building and the proving. §17 core tenet

    New here? Start with the interactive course, How Sindri Works: six short modules with animations, real code and quizzes. To see how the pieces connect and what using it looks like step by step, open How Sindri fits together. These pages are the full reference.

    Part of the finding is looking outward. Sindri {{field harvest|harvests other software factories}}: it reads their designs, checks each practice against its own spec, and builds the ones it lacks through its own factory. See chapter 22. §17.25

    It started from a measurement. A transcript audit of one month of work (406 sessions, 2,911 human turns) found that the human's effort went mostly to the least judgment-heavy parts of agent work. §1

    The shape of the whole thing

    Plans 1–5 built the control room in TypeScript: measurement, the {{ledger}}, the code index, the scoping harness and offline self-evolution, with evolve's privacy gate after them. That TypeScript sindri runs at the desk today and is the reference for what each part does. The factory addendum (§17) designs the production line: from a {{scope map}} through a desk design studio to a frozen {{packet}}, then a factory build of narrow sessions run by {{lens|lenses}}, reviewed from anywhere, and merged by the human.

    The production line runs inside the {{Sindri app}}, a new C# application, not a port of the TypeScript one (decision Q7, §17.29). Its first stage, the app shell, is merged. The API, the {{workflow engine}} on {{Temporal}}, the {{context engine|context retrieval engine}} and the Avalonia UI are being built now in five parallel lanes. Plan 6's dashboard became that UI. Nothing of the C# build is installed until {{the switch}}. See chapter 4 for the app and chapter 21 for what's merged and what's in flight.

    Every feature on these pages carries a status: ● built merged on main, ◑ building has an open PR, ◐ specced has an approved spec and plan, ○ designed in a design spec but not planned, ✧ dream vision, scouting seeds or deferred.     Chapter 2 · Rules that never bend

    Nineteen invariants, three principles

    The main spec fixes eleven invariants; the factory addendum adds eight. Three architectural principles follow from the core tenet: Sindri can only evolve parts it can isolate, measure and swap, and it can only afford to run them if most decisions cost no model turn.

    Principle 1

    Modularity

    Every part is a module with a typed contract, an eval suite, telemetry and a registry entry. A part that can't be swapped alone is a design defect.

    Principle 2

    Context management

    No session gathers its own context. Code assembles a budgeted, cited {{injection plan}}. Modules declare what they need; they never load everything that might help.

    Principle 3

    The decision ladder

    Each decision takes the cheapest {{rung}} that can make it with enough confidence: code, a decision model, a small model, then an agent turn. See chapter 5.

    Chapter 4 · Architecture

    One process, three engines, every surface a client

    sindri starts one process per host under the host lease and opens the UI app beside it; sindri --headless skips the UI on the always-on box. The process holds three engines: the control plane, the {{workflow engine}} and the {{context engine}}. The CLI, the app, the phone and agent sessions are all clients of one API. launchd only keeps the process alive; today's launchd jobs become background services inside it. §17.29 · docs/sindri/README.md

    Play the flows through this picture, from starting your day to shipping a recipe change: How Sindri fits together.

    Built new, not ported §17.29 · Q7 · readiness §4c

    The TypeScript sindri/ package is a guide to what each part does, never to how. The C# app keeps no byte or state compatibility with it, and no TS state is migrated. The one exception is the hook contract: the commands, JSON fields, exit codes and files that the bash hooks and statusline rely on stay frozen until {{the switch}}, checked in CI by running the real hook scripts against the C# binaries. Until then nothing in setup.sh, the providers, MCP registration or launchd points at the C# build, and every proof runs in a temp home through scripts/sindri-prove.sh.

    Recipes, blocks and Temporal §17.28 · engine §0, §5 · Q8

    • A {{recipe}} is declarative YAML, checked by a JSON Schema: states, transitions, gates, evidence, effects, loop caps, timeouts and budgets. A new workflow, or a change to one, is a config change; sindri recipe validate and recipe eval already run.
    • A {{block}} is a typed C# module with its own contract and tests: a gate, an evidence provider, a Step implementation or an effect. New code is needed only for a new block. Tools become blocks; a skill's phase sequence, such as /bugFixOrchestrator's, becomes a recipe.
    • {{Temporal}} runs the instances (decided 2026-10-11, no spike). One RecipeWorkflow interprets every recipe; commands are Updates keyed by a nonce, Steps are activities, events are signals, children are child workflows. Every transition is mirrored into the {{ledger}}, which stays the one public log. Timers fire on wake after downtime: a timeout parks or escalates, which is visible and harmless.

    How you step onto the line README X55, X56 · API §8.1

    Every agent session Sindri runs lives in a tmux session it owns (snd-<run>), whether you or the factory started it. Attach (sindri open <item> --attach, or the app's button) opens a Warp tab joined to it, so you type into the live agent whatever Step it is on. The first thing you type is a {{takeover}}: the workflow pauses with its timers stopped until you hand back. With no live session, open starts Claude Code, Codex or Cursor in Warp, seeded with the item id; the session pulls the item's state, packet, evidence and context through Sindri's MCP endpoint. Headless -p runs are never used for Steps, because nobody can join them. Each launched command runs under sindri session wrap, which heartbeats and reports its exit.

    The Step contract §6

    Every unit of work is a {{Step}}: inputs, an output schema, deterministic checks, a verifier, max rounds, a budget and an escalation. The producer never verifies itself.

    Chapter 5 · Cheapest rung first

    The decision ladder

    Each decision takes the cheapest {{rung}} that can make it with enough confidence. It climbs only when the lower rung is below its threshold, and self-evolution keeps pushing decisions back down. §17 principle 3

    Every decision records which rung made it, its cost and its later outcome. "Agent turns that a cheaper rung could have made" is a tracked metric, and the share of decisions made at rungs 1–2 should rise month over month. §17.2

    Chapter 7 · Front of the line

    Find the surfaces before the code does

    Projects sprawl when surfaces and implications are found during implementation. sindri scope turns a brief into a cited {{scope map}} up front, and --backtest proves it on a project's original brief. §7.5

    Scope map contains

    • Surfaces (UI, API, job, data, integration), each with a citation
    • Implications: migration, permissions, reporting, notifications, mobile, flags
    • Workstreams with dependencies
    • Acceptance checks per workstream
    • Open product questions, batched

    Verification loop

    1. Deterministic: every surface cites a source; acyclic dependencies; every surface in a workstream
    2. Adversarial missing-surface pass on a different model, until nothing new appears
    3. Scoping {{direction check}} (from rollout step 5)

    A backtest, in one picture

    Scoping v2: intake, a loop that retrieves, and edits that re-run it §17.26

    Today scoping starts by hand, and its challenger re-reads the drafter's evidence, so it can only find what was already gathered. In v2 the same pipeline runs at intake, in every round, and at the desk. A human edit is just another seed.

    • Two triggers. sindri scope by hand, or tracker intake: assign an item to yourself and, if triage routes it to scoping, a map is waiting in the desk queue. Intake holds while review is full (invariant 18).
    • Every round retrieves. The challenger writes typed {{expansion query|expansion queries}} (symbol, neighbours, similar, tracker, notes, route or flag). Sindri runs them against the code index, call graph, embeddings and tracker, and the drafter revises with only the new evidence. Models still get no tools.
    • Every round prunes. Surfaces with keyword-only or unsupporting evidence move to a Considered and dropped list with a reason, so you can bring them back.
    • Honest stopping. The map says converged (queries found nothing new) or capped, and lists its open queries.
    • File-level candidates. Each surface lists ranked candidate files and symbols with the query that found them. They become proposed write scopes and read seeds in the packet.

Human adds are never pruned. freeze refuses unconfirmed proposals. Labels come from the net difference at freeze, so removing and then restoring something teaches nothing wrong: what you finally added is a recall miss and what you finally removed a precision miss.

    Chapter 8 · Freeze, then compile

    No build without a frozen packet

    The design studio turns a scope map into a {{packet}}: a schema-validated directory frozen by hash. For each Step, a {{task compiler}} (code, no model) computes a {{session spec}}, and the {{sandbox policy}} is compiled from it. Agents don't decide their own scope. §17.4, §17.5, invariants 13–14

    The capability ceiling §17.19 C1–C2

    Every registered artifact is split in two. Prompt text (instructions, questions, rubrics, rule wording) may self-adopt. Capability fields (tool, command, MCP, network, write-scope and budget allowlists; trust tiers; workflow templates; security rules) are always approval-tier, and no model output may set them.

    Chapter 14 · More at once

    From one host to a team, in four rungs

    Today: one active host, a session cap, one heavy job at a time. Inside a packet, tasks with non-overlapping write scopes can already run in parallel. The ladder below adds scale without a rewrite, and each level reuses the one below. §17.20

    Limits that don't go away with more machines

    Model quota

    The capacity router spreads Steps across allowed accounts, never across the work/personal line.

    Human review

    The {{human-minutes}} budget caps how much work Sindri starts, however many workers exist.

    Merge contention

    Conflict-aware dispatch and small write scopes; a task that conflicts twice is serialized.

    Chapter 15 · Serving several people

    Two channels

    The harness always runs from a pinned stable install of itself. Proposed changes land on next, are evaluated by stable, soak, then promote with a typed confirmation. A change may never modify the eval suite that judges it (invariant 11). §7.7

    Chapter 17 · Deny by default

    Hooks force patterns; the sandbox enforces security

    A hook that fails open costs a missed nudge, never a breach. The security boundary is a dedicated session container and user, server-side branch protection, and sindri-side re-verification of what a session pushes. §5.3, §8

    Always denied in sessions §8.1

    No allowlist entry can grant these in v1: undraft, merge, close or cancel items, create items, chat posts, gh api writes, workflow triggers, production-mutating MCP tools, and kubectl or exec tools. A denied call parks the item with a typed reason; the session never sits on a permission prompt.

    Chapter 18 · Where the human decides

    The right surface for each decision

    One command layer is the authority; the CLI and the Sindri app are two clients of it, so every action gets a UI form (§17.27). The Avalonia app talks to the loopback API and shows the queue, what needs you and every item's timeline; over a tailnet, a phone handles binary, low-context decisions, signed with a passkey. Open questions, freezes and protected approvals stay at the desk. §10, UI spec, §17.12, §17.19

    Every step from the UI §17.27

    Every action, from Scope on a tracker item to editing, freezing and promoting, is a command with one handler. The CLI and the app call the same handler, with the same checks, errors and ledger event; the app has no logic of its own. Protected actions are never run from the app: it shows the CLI command to copy and type at a terminal. Long jobs stream the same progress to both and can be cancelled from either.

    Chapter 22 · What the field already knew

    Twenty-five practices from other software factories

    A read of other factories (addyosmani/factory, SuperPlane, loki-mode, chainloop, robi42/factory, planwright, dev-sdd-kit and the Actual AI workshop) found practices Sindri didn't have or had only in part: sixteen on a first pass and nine more on a second. Ideas only; no code is copied. Each source also seeds the scout. §17.23

    Three new invariants §17.1, §17.23

    Invariant 17

    Sessions don't edit the tests that judge them

    Existing tests are read-only unless the frozen packet names the change, and a test change always gets a human read.

    Invariant 18

    Production stops when review is full

    No new Step whose result needs a human decision starts while the {{back-pressure|pending-decision queue}} is at its limit.

    Invariant 19

    Every verdict says what it didn't prove

    An item's outcome lists every planned check that didn't run or couldn't decide. Silence is never a pass.

    Merge-confidence card §17.23.7

    Five dimensions, scored 1 to 5: blast radius and drift from the packet (lower is better), reversibility, security and performance (higher is better). Names and thresholds live in Sindri code; a model supplies only a score and a one-line summary. A critical dimension moves the decision from the phone to the desk.

    Never loosened, whatever the evidence: the human merges to the default branch; existing tests are read-only to sessions; the producer never verifies its own work; protected modules need approval; models never grant capabilities. §17.23.8
